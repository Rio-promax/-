# GitHub 视频分析总结方案研究与产品启发

> 研究范围：以 Bilibili 视频分析、转写、摘要项目为主，补充 YouTube 和跨平台视频方案。
>
> 研究时间：2026-07-27 至 2026-07-29。
>
> 当前约束：`summary` skill 只使用字幕或音频转写，不分析画面、OCR、关键帧或视频内代码；登录受限时通过辅助登录（登录弹窗、辅助浏览器弹窗）获得用户授权。

## 1. 结论摘要

GitHub 项目主要解决四类问题：

1. 稳定获取视频、字幕和音频；
2. 对长音频进行切分、并发转写和时间戳恢复；
3. 将转写结果交给 LLM，生成结构化摘要；
4. 保存任务历史、缓存、知识库和批处理结果。

当前 `summary` skill 的优势在于边界清晰、字幕优先、动态决定总结粒度、失败时不编造内容；GitHub 项目的优势在于把大量固定流程做成可重复执行的代码。

推荐的产品方向是：

```text
脚本执行层：校验、获取、转写、分块、缓存、导出、清理
AI 理解层：主题提炼、论点归纳、章节组织、知识问答
skill 编排层：根据来源状态选择路径，并控制输出粒度和安全边界
```

## 3. GitHub 项目的共同技术路线

典型流水线为：

```text
视频链接
  → 平台解析和元数据
  → 官方字幕
  → 无字幕时获取音频
  → ASR 转写
  → 分段、压缩和时间戳恢复
  → 分块摘要
  → 全局合并
  → Markdown、知识库或问答
```

### 3.1 来源适配

多数项目使用 `yt-dlp` 作为跨平台获取层，或者使用 Bilibili 专用 API。跨平台项目通常只让来源层负责：

- URL 规范化；
- 视频 ID 解析；
- 标题、时长、封面和分 P 信息；
- 字幕列表；
- 音频获取；
- 登录状态和失败原因。

后面的字幕解析、ASR、分块和摘要流程保持统一。

### 3.2 字幕优先、ASR 兜底

较成熟的项目不会无条件下载完整视频，而是优先寻找人工字幕或自动字幕。没有可用字幕时，才处理音频并调用 Whisper、faster-whisper、SenseVoice、FunASR 或云端 ASR。

这是最值得保留的共同路线，因为字幕路径通常更快、更省资源，也更容易保留原始时间戳。

### 3.3 长视频分块

常见做法包括：

- 按静音点或时间范围切分音频；
- 并行调用 ASR；
- 给字幕段落保留 `start`、`end`、`text`；
- 相邻摘要块保留少量重叠，降低主题被切断的风险；
- 先生成分块摘要，再生成全局摘要；
- 合并重复章节并恢复时间定位。

这是一种 Map-Reduce 式摘要流程，适合长视频，也能控制单次上下文长度。

### 3.4 结构化中间数据

多数成熟实现不会只保存纯文本，而是保存结构化片段：

```json
{
  "start": 120.5,
  "end": 136.2,
  "text": "转写内容",
  "source": "official_subtitle",
  "language": "zh",
  "confidence": "high"
}
```

结构化片段可以同时服务于时间轴、章节、摘要、搜索、重跑和质量报告。

### 3.5 本地任务系统

BiliSum 等项目使用 SQLite 保存：

- 视频资产；
- 分 P 目录；
- 任务状态；
- 阶段事件；
- 转写结果；
- 摘要结果；
- 收藏夹和标签；
- 知识库索引。

这样可以做到任务恢复、失败重试、已有转写重新总结和跨视频检索。

## 4. 与当前 summary skill 的差异

### 4.1 当前 skill 的优势

当前 `summary` skill 已经明确：

- 只使用字幕或音频转写；
- 用户需要登录时，保持原浏览器标签页等待用户完成登录（辅助登录）；
- 官方字幕优先；
- 字幕无效时才进入音频和 ASR；
- ASR 只做轻量质量检查；
- 总结长度根据视频时长、信息密度和结构动态决定；
- 没有可靠来源时输出失败文档，而不是依据标题、简介或评论猜测；
- 清理失败时报告残留路径。

这些边界比很多 GitHub 项目更严格，应保持不变。

### 4.2 GitHub 项目的工程优势

与当前 skill 相比，代表性项目通常多出：

- 统一的平台适配层；
- 本地任务数据库；
- 缓存和去重；
- 断点恢复；
- 长音频并发转写；
- 多 ASR provider；
- 已有转写的重新总结；
- 多 P 或全集处理；
- token 和阶段状态统计；
- 收藏夹、频道和批处理；
- Obsidian、RAG 或问答输出。

### 4.3 不应直接照搬的做法

部分项目提供以下能力，但与当前 skill 边界冲突：

- 使用关键帧、OCR、VLM 或视频视觉模型；
- 没有字幕和音频时仅凭标题、简介、评论生成完整总结；
- 默认下载完整视频而不是优先处理音频。

这些功能可以作为独立产品的研究对象，但不能直接并入当前“仅字幕/音频”的 skill。

## 5. BiliSum 的具体实现启发

BiliSum 的 `RealPipelineRunner` 大致采用：

```text
URL
  → yt-dlp 探测
  → Bilibili WBI / dm/view 字幕
  → yt-dlp + FFmpeg 音频
  → SiliconFlow / FunASR / Whisper 等 ASR
  → 2200 字符左右分块、2 段重叠、并发和重试
  → 分块 JSON 摘要
  → 全局 JSON 摘要
  → 知识笔记和导出
```

它还保存 LLM 的 prompt、completion 和 total token，可以为后续成本分析提供依据。

BiliSum 的局部摘要和全局摘要提示词要求 LLM 输出结构化 JSON，包括：

- `title`；
- `overview`；
- `bulletPoints`；
- `chapters`；
- `chapterGroups`。

其中章节数量可以根据内容变化，但 overview 和要点数量有较明确的范围。当前 skill 的“非固定长度”要求更灵活，不应完全复制 BiliSum 的固定数量约束。

## 6. 哪些部分应脚本化

### 6.1 适合固定脚本运行的部分

| 阶段 | 是否需要 LLM | 说明 |
|---|---|---|
| URL 校验和 BV/AV 提取 | 否 | 正则和 URL 解析 |
| 元数据和时长获取 | 否 | 官方接口或解析器 |
| 多 P 识别 | 否 | 读取平台元数据 |
| 字幕获取 | 否 | API 请求、格式检查和 JSON 解析 |
| 音频获取 | 否 | 官方音频接口或辅助登录会话 |
| 音频切分 | 否 | FFmpeg、静音点或时间分段 |
| ASR 转写 | 不需要 LLM | 使用预装本地模型或明确启用的 ASR 服务 |
| 时间戳恢复 | 否 | 片段偏移量计算 |
| 分块和重叠 | 否 | 字符数、时间或主题边界 |
| 重试和并发 | 否 | 任务调度逻辑 |
| 章节去重和时间对齐 | 否 | 规则和结构化数据处理 |
| Markdown/JSON 导出 | 否 | 模板和序列化 |
| 清理和失败报告 | 否 | 文件系统和状态记录 |

### 6.2 仍适合由 AI 完成的部分

- 判断中心主题和核心结论；
- 区分事实、观点、证据和推测；
- 识别论证关系、因果关系和限制条件；
- 决定内容章节边界；
- 按信息密度调整总结粒度；
- 生成自然语言摘要、知识卡片和思维导图；
- 对多个分 P 进行主题合并；
- 回答基于转写内容的追问。

因此，`summary` skill 最适合调用固定脚本准备可靠材料，再让 AI 专注于语义理解和最终表达。

## 7. 新的产品思路

### 7.1 脚本准备器 + AI 总结器

建议将流程拆成三个层次：

```text
prepare_video
  → 校验 URL、获取字幕/音频、ASR、输出 transcript.json

summary skill
  → 读取结构化转写、分块理解、全局总结、生成 Markdown

finalize_video
  → 校验输出、记录 token、保存结果、清理临时文件
```

这样可以避免 AI 参与重复的文件查找、格式转换和状态判断。

### 7.2 可追溯摘要

每一个摘要要点绑定来源片段：

```text
要点 → 起止时间 → 原始字幕/ASR 片段 → 来源类型 → 置信度
```

用户可以从要点回到原始转写，减少“摘要看似合理但无法核验”的问题。

### 7.3 摘要配置档

同一套来源和转写材料可以生成不同版本：

- 快速摘要；
- 学习笔记；
- 技术细节版；
- 决策简报；
- 章节时间轴；
- 问答材料。

重新生成时直接复用字幕或转写结果，不重复下载和 ASR。

### 7.4 收藏夹和频道批处理

在用户明确授权的浏览器会话中，可以提供：

- 收藏夹逐条读取；
- 已处理结果跳过；
- 单条失败不阻塞整个批次；
- 每个视频生成独立 Markdown；
- 汇总知识模块和内容类型；
- 输出成功、跳过和失败清单。

批处理应有限速、并发上限和失败重试，不能设计成无限制抓取。

### 7.5 增量监控

可借鉴 `briefing` 的订阅模式：

```text
频道/UP 主
  → 定期发现新视频
  → 只处理未见过的视频 ID
  → 生成摘要
  → 推送简报
```

该功能应作为独立模块，不改变单视频总结的核心流程。

### 7.6 成本和质量仪表盘

每个任务记录：

- 字幕字符数；
- ASR 时长和耗时；
- 分块数量；
- LLM 请求次数；
- prompt/completion/total token；
- 失败重试次数；
- 来源类型；
- 最终置信度。

这样可以比较“字幕路径”和“ASR 路径”的成本与质量，也能定位自动化瓶颈。

## 8. 推荐落地顺序

### P0：可靠性和节省 token

1. 统一 `TranscriptSegment` 结构；
2. 建立字幕、音频、ASR 三层状态；
3. 增加转写缓存和摘要缓存；
4. 记录阶段耗时和 token；
5. 长视频使用分块摘要和全局合并；
6. 保留当前无画面分析边界；受限内容通过辅助登录（登录弹窗、辅助浏览器弹窗）读取。

### P1：批处理和跨平台

1. 抽象 Bilibili/YouTube 来源适配器；
2. 支持多 P 视频；
3. 支持收藏夹批处理；
4. 增加 YouTube 的字幕优先路径；
5. 增加可选 ASR provider，但本地 ASR 仍作为隐私优先路径。

### P2：知识产品化

1. 可追溯摘要；
2. 多版本摘要配置档；
3. 跨视频检索问答；
4. 频道增量监控；
5. 用户反馈驱动的摘要偏好。

## 9. 最终设计原则

1. 让脚本处理确定性工作，让 AI 处理语义工作。
2. 字幕可用时不下载音频、不运行 ASR、不浪费 token。
3. 长视频按结构分块，不按固定字数机械压缩。
4. 每个结论都尽量保留时间和来源片段。
5. 缓存转写结果，重新总结时不重复消耗 ASR 和下载资源。
6. 登录由用户完成，登录态在用户授权后仅保存在本机供本次会话使用。
7. 没有可靠来源时明确失败，不用标题或简介补全视频内容。
8. 产品能力可以扩展到 YouTube 等平台，但来源适配不能破坏当前安全边界。
