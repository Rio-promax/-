# pm-critic findings: 多源内容知识库项目实现

## 审核范围

- 主基线：00 产品全景决策总览、01 功能能力结构、02 信息对象结构、03 页面与导航结构、04 状态与产品缺口。
- 实现证据：`product/src/services/core/app`、相关自动测试与当前产品入口文档。
- 审核口径：五图之间先保持概念一致，再检查代码、界面、数据对象与测试是否足以支撑目标结构。
- 状态原则：自动测试不等于用户验收；五图中的目标能力不自动视为已实现。

## Findings

### P0

#### F-01 凭据与本地音频链路尚未达到可发布验证状态

本轮完整自动测试结果为 `148 passed, 5 failed`。其中 4 项失败发生在 Windows DPAPI 凭据保存路径，另 1 项是本地音频配置 ASR 后任务未完成。由于总结模型和 ASR 密钥是核心处理链路的前置条件，目前不能把“本机凭据保护、云端 ASR、本地音频处理”整体标为已自动验证。

建议修复：先区分 DPAPI 失败究竟来自测试隔离环境还是产品调用错误；测试中使用可控凭据存储替身，另保留一组真实 Windows DPAPI 集成测试。修复本地音频失败后，以常规虚拟环境执行完整测试并要求全部通过，再进入人工验收。

### P1

#### F-02 目标四区导航与当前三入口界面不一致

03 图将一级区域定义为“内容接入区、任务区、知识库、设置”，但当前界面仍把接入和任务合并为“开始与任务”，并使用“内容库”命名。证据位于 `product/src/services/core/app/ui/index.html:14`。这会使页面归属、后续任务区设计和跨图术语持续分叉。

建议修复：先完成四区信息架构骨架及路由/视图状态拆分，再迁移现有组件；同时在五图中统一选择“知识库”或“内容库”作为唯一产品术语。

#### F-03 集合是一种输入类型，但还不是完整业务对象

02、03 图要求作者、内容集合、批次文件夹、集合详情和聚合总结之间存在明确关系。目前集合链接只能被识别为 `collection`，收藏夹不能预览导入；批次文件夹主要是归档结构，尚没有可维护的集合实体、集合详情页和聚合结果关系。`summary_mode` 只存在于请求结构，未接入执行链路。

建议修复：先定义 `ContentCollection`、成员关系、来源类型、扫描快照和聚合总结版本，再实现集合预览、成员选择、批次执行、集合详情与聚合结果。避免继续用文件夹隐式代替集合领域对象。

#### F-04 多 P 已部分实现，但交互与需求仍不一致

多 P 链接已经能够自动拆分全部分 P、分别生成总结并写入同一文件夹，相关自动测试位于 `product/src/services/core/tests/test_link_import.py:799` 和 `:838`。但 01、03 图要求用户先选择分 P，并决定多个结果是否归入文件夹；当前实现缺少选择和确认步骤。

建议修复：把多 P 预览建模为候选列表，默认全选但允许取消；提交前显示任务数和归类方式，后端仅处理所选分 P。04 图应拆成“自动拆分与归类待人工验收”和“用户选择未实现”两个状态。

#### F-05 UP 主与收藏夹批量接入能力不对称

UP 主公开视频分页扫描和候选勾选已存在，但候选只有发布时间、时长等字段，界面没有按时间、播放量、点赞数、时长排序；收藏夹链接仍不能进入候选预览。扫描数量上限也尚未形成产品规则。

建议修复：复用统一的集合扫描协议，补齐播放量与点赞数字段、排序参数、分页游标、上限和中断恢复；随后分别实现 UP 主与收藏夹适配器，而不是维护两套批量交互。

#### F-06 本地文档与图文能力在目标图中被高估

当前本地文本选择器和适配器只支持 TXT、Markdown、SRT、VTT，证据位于 `product/src/services/core/app/ui/index.html:38` 与 `product/src/services/core/app/adapters/sources/local_text.py:12`；DOCX、PDF 未实现。Bilibili 专栏、动态和 opus 能提取文字，但图片材料、视觉理解、逐图证据和跨帖聚合仍缺失。

建议修复：在 04 图中把“文字正文导入”和“图片理解”拆开；按 TXT/MD/字幕、DOCX/PDF、音视频、图文平台四类建立清晰的材料能力矩阵，再逐类补适配器与验收样例。

#### F-07 总结强度只有领域默认值，没有用户可操作闭环

01、02、04 图要求大、中、小三档总结强度，但当前工作流固定使用 `SummaryStrength.STANDARD`，例如 `product/src/services/core/app/workflows/analyze.py:370`；导入请求和界面没有对应选择项。

建议修复：先定义三档对输出长度、章节密度、证据数量和模型预算的可测差异，再把强度写入任务快照、归档元数据和版本记录，最后增加界面选择与回归测试。

#### F-08 04 状态图此前不能准确反映代码与测试事实

旧状态把多 P 整体标为未实现，也把若干设置、ASR 和恢复能力整体标为已自动验证；这与本轮代码和测试证据不一致。旧说明还引用即将归档的《进度现状》《待做任务》作为权威来源。

建议修复：04 图只引用 00–03 与代码/测试审核结果；将“部分实现”“自动测试通过”“人工验收通过”和“测试阻塞”分开表达。每次改动只更新有直接证据的最小节点。

### P2

#### F-09 内容详情与设置页仍是功能堆叠，缺少目标页面层级

03 图要求内容详情中的版本、正文、侧边锚点和操作区，也要求设置内存在二级目录。当前产品可以展示和导出结果，但没有基于总结标题生成的侧边目录；设置仍是一个较长的单页表单。

建议修复：先补内容详情的稳定页面状态和标题锚点生成，再把设置按平台、ASR、总结、存储、运维分组为二级导航。两项均应在浏览器中完成键盘操作和窄窗口验收。

#### F-10 03 图残留占位节点且跨图命名未收敛

03 图仍有“子主题 3”占位节点；00 使用“内容库”，03 使用“知识库”。占位和同义名称会降低五图作为主基线的可执行性。

建议修复：删除无业务含义的占位节点；由用户确认唯一术语后，一次性同步 00–04、界面文案、路由名称和文档入口。

## Status Summary

项目已经具备单条链接、本地文本/媒体、Bilibili 单视频与 UP 主候选、任务执行、基础队列、总结模板、归档、搜索、收藏和设置等主体能力，不是从零开始。当前最大风险不是功能数量，而是目标四区信息架构尚未落到界面、集合/聚合缺少领域闭环，以及核心凭据与本地音频测试仍有失败。下一阶段应先恢复可信的全量测试基线，再建立四区页面骨架和集合对象，之后补多 P 选择、收藏夹、聚合总结与总结强度。
