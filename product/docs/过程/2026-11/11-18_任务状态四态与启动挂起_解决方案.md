## 产品问题 1：现在的「等待中」有一半是假的

**用户原话区（逐字，不许改写）**

- U-01-1

  > 嗯，不改后端什么意思啊？比如目前的等待中没有进行中的视状态视频，这个就需要改后端呀。

**AI 解释区**

1. 状态机真实取值（`domain/jobs.py:13-25`）：`queued / acquiring / extracting / transcribing / chunking / summarizing / archiving / indexing / completed / paused / failed / cancelled`，共 12 个。
2. **重启后只有「租约过期的运行态」会被捡起**：启动时唯一动作是 `main.py:1823-1829` 把 `store.recover_expired_jobs()` 的结果逐个丢线程。`recover_if_expired()`（`domain/jobs.py:197-209`）第一行 `if self.lease_until is None: return False`——`queued` 的 `lease_until` 恒为 `None`，永远进不了这条路径。
3. **内存队列不会自己捡起库里的 queued**：`submit()`（`queue.py:49-76`）只接受 `state == "queued"`，但启动时没人替库里的 queued 调它；`_run()` 的下一项只从内存 `_pending` 取（`queue.py:219-237`）。重启后 `_pending` 为空。
4. **现场实例（不是推演）**：`/api/v1/queue` 返回 `active=0, queued=1, persisted_queued=1`；`job_e0b08bd…` 是 `state=queued, attempt=0, queue_position=2`，`updated_at` 停在 `2026-11-17 07:55`。服务已跑 40 多分钟、期间处理过别的任务，这条一次没启动。
5. 结论：库里 `queued` 在重启后既不会自己跑，界面上又显示成「等待中」——**语义是假的**。v3 的修法不是给它加一条自动续跑泵，而是**把它改成诚实的「已暂停」**（见问题 6）。

## 产品问题 2：排队与暂停是两种「所有权」

**用户原话区（逐字，不许改写）**

- U-02-1 · 场景

- U-02-2 · 词义追问

  > 已暂停和待启动不是差不多的吗？

- U-02-3 · 用户对该词自己的理解

  > 待启动不就是排队中的吗？你说的待启动意思不就是说不会进行，就是不用人点就会慢慢后续自动进行吗

**AI 解释区**

| 库里 `state` | 谁负责让它继续 | 用户可见文案 |
|---|---|---|
| `queued` | **系统**：同一轮运行里，前一条跑完自动接上 | **排队中** |
| `paused` | **用户**：必须点「继续」 | **已暂停** |

两者「表现」一样——都没在跑、都在等。差别只有一条：**等谁动手**。这个差别是真的，数据里本来就是两个枚举值（`resume_job` 只认 `paused`，`main.py:3845`）。

但**不需要第三个词**。v1 的 `待启动` 定义是 `paused + restart_hold`（要人点），而用户在 U-02-3 里把它读成「不用人点、会自动进行」（＝`queued`）——同一个词两个方向都能读懂，说明词本身不能用。已删，只保留「排队中」「已暂停」。

`preempt_yield`（被插队让出的任务）已有现成机制：`_is_switch_requeue()` 把它折算成 `execution_state="waiting"`（`main.py:6653-6655`），前端显示「排队中」，不需要新字段。

## 产品问题 3：四态确认，后端要动哪几处

**用户原话区（逐字，不许改写）**

- U-03-1

  > 因此方案重构中四个状态全部进行中，已完成未完成是 OK 的，但是后端可能也需要进行对应的修改，只是目前还没有确定修改方案，目前只确定修改方案

**AI 解释区**

判据只有一条：**系统还会不会自己接手**。会 → 进行中；不会 → 未完成。

| 标签（tab） | 后端 `execution_state` | 行内状态 | 行内右侧按钮 |
|---|---|---|---|
| 全部 | 全部 | 原样 | 按行内状态 |
| **进行中** | `running` / `waiting` | 进行中 / **排队中 · 第 K 位** | 暂停 / 插队 |
| **已完成** | `completed` | 已完成（父集合行见问题 5） | 查看结果 |
| **未完成** | `failed` / `cancelled` / `paused` | 失败 / 已取消 / **已暂停** | 重试 / 重试 / 继续 |

后端只动两件事（v1 是四件）：

1. **启动挂起**：跨会话遗留的 `queued` 与被打断的运行态，统一转 `paused`，不自动跑（问题 6）。
2. **「继续」幂等与批量保序**：`resume_job` 对 `queued` 现在 409（`main.py:3845`），且写死 `front=True`（`main.py:3855`），批量继续逐条插队会倒序（`app.js:1390-1406`）。

## 产品问题 4：「保存进度」与 `job state` 分别指什么

**用户原话区（逐字，不许改写）**

- U-04-1

  > 行列标签中保存进度。……然后续跑上限 2 是什么意思啊？为什么要设置这样一个续跑上限？如果用户直接把300个都纳入续保上限中。不也可以吗？这里一上线300个全跑，但是我们目前产品的计划不是只能单一单一的跑吗？这里的 job state 是什么意思啊？

**AI 解释区**

**（1）「保存进度」是死文案。** 后端 `_job_execution_state()`（`main.py:6653-6664`）只返回 `waiting / paused / completed / failed / cancelled / running` 六个值，**从不返回 `switching`**；`app.js:1025` 的 `raw === "switching"` 分支永不命中，`main.py:3627`、`:6503` 只是防御性判断。出处是 09 月旧枚举（`_legacy/app.js:1775`）。v3 四态表已删掉它。

**（2）续跑上限 20 是多余的，已撤。** 队列严格单并发：`queue.py:39` 默认 `lambda: 1`、`queue.py:88` 返回 `concurrency_limit: 1`、`queue.py:69-73` 只有 `_active` 一个槽。所以「300 条全纳入」＝ 1 条在跑 + 299 条排队，不存在同时开跑。v1 说「一上线 300 条全跑」是把串行队列误当并发池，判断错位。真实代价是 ASR 占 CPU / 模型额度，该由用户决定停不停，不该由系统拍一个 20。

**（3）`job state` 是库里字段，用户看到的是两层折算之后的结果。**

| 层 | 取值 | 位置 |
|---|---|---|
| ① 库里 `jobs.state` | 12 个：`queued` + 7 个运行阶段（`acquiring / extracting / transcribing / chunking / summarizing / archiving / indexing`）+ `completed / paused / failed / cancelled` | `domain/jobs.py:13-25` |
| ② 接口 `execution_state` | 6 个：`waiting / running / paused / completed / failed / cancelled` | `main.py:6653-6664` |
| ③ 前端 `jobState().key` | 与 ② 基本一一对应，另有 `switching`（死分支）与 `partial`（父集合合成，不是后端值） | `app.js:1018-1035` |

改四态只动 ②③ 的映射与文案，**不动 ①**。因为 `paused` 已被三处逻辑当「用户态停止」用（`analyze.py:1790`、`:1137` 的停止判定，`main.py:3845` 的 resume 前置条件，`domain/jobs.py:109` 的转移表），新增枚举要连带改 5～7 处，漏一处就是「停不下来」或「继续 409」。

## 产品问题 5：「部分失败」没有归宿

**用户原话区（逐字，不许改写）**

- U-05-1

  > 这里的部分失败又是什么？部分失败不就是未完成，不就是失败吗？

**AI 解释区**

`部分失败` 不是后端值，是前端给**父集合行**合成的一个汇总标签（`app.js:1119-1127`）：

```
有 running/switching → running
有 waiting          → running（对外显示"进行中"）
有 paused           → paused
全部 completed      → completed
有 completed 但不全 → partial   ← 「部分失败」
有 failed           → failed
兜底                → cancelled
```

三个事实：

1. **只有父集合行会出现**（一个合集里 ≥2 条任务时才建父行，`app.js:1130`）。单条任务永远是 失败 / 已取消 / 已完成。
2. **它不精确**：判据是「有成功但不全成功」，所以「3 成功 + 2 已取消」也会显示「部分失败」，里面可能一条失败都没有。
3. **它和四栏天然冲突**：`partial` 的组里一定既有一个 `completed` 子项、又有一个未完成子项。按「一行一个状态」分栏，它同时属于「已完成」和「未完成」。

v3 的裁定（用户 2026-11-18 22:15 采纳）：**父集合行不挂状态词**，改用已有的计数「第 X 项 · 已完成 3 / 5」（`app.js:1303` 本来就在显示），归栏规则改为：

- 组内有 `running / waiting / paused` → 归「进行中」；
- 组内全结束且全部 `completed` → 归「已完成」；
- 组内全结束但有 `failed / cancelled` → 归「未完成」；
- `partial` 这个状态词从标签表里删掉。

这样标签词表只剩 6 个，每个都能唯一落进四栏，不再有「一个组同时属于两栏」的问题。

归栏时父行的判定不看它自己显示什么，而看子项集合（`app.js:1119-1127` 的合成结果只用于排序与展开态，不再写进 `.job-state`）：组内有 `running / waiting / paused` → 进行中；全 `completed` → 已完成；其余（含 `failed / cancelled`）→ 未完成。`partial` 从 `JOB_STATE_LABEL` 删除，但「有成功但不全」这个中间态仍要参与上述分支判断，避免「3 成 2 败」被错判成已完成。

## 产品问题 6：重启之后一律不自动跑

**用户原话区（逐字，不许改写）**

- U-06-1

  > 重启之后并不默认全量跑。比如上一次关闭之后就暂停了，那么这一次需要用户手动进行启动

**AI 解释区**

这条裁定把 v2 的 R1「启动续跑泵」整条推翻，也顺手简化了方案：

| | v2（已作废） | v3 |
|---|---|---|
| 启动时对遗留 `queued` | 按序装回内存队列，自动接力 | **转 `paused`**，一条都不跑 |
| 启动时对被打断的运行态 | `recover_expired_jobs()` 后自动续跑 | 同样**转 `paused`**，保留断点 |
| 用户怎么让它跑 | 不用管，它自己跑；想停就批量暂停 | **手动勾选 + 点「继续」**，选几条跑几条 |
| 需不需要上限常量 | 需要（20） | **不需要**，用户选多少就是多少 |
| 需不需要 `enqueue_many` 泵 | 需要 | **不需要** |
| 界面效果 | 一打开就在跑 | 一打开全是「已暂停」，等用户决定 |

用户原话里的「只让 20 个视频重跑」由此变成纯操作问题：勾 20 条 → 点「继续」→ 第一条跑、其余排（同一次会话内 `queued` 正常接力）。**同一个「排队中」在不同会话里语义一致，不需要任何新状态。**

实现要点（R1）：

1. 启动时先调 `store.recover_expired_jobs()`（复用它的 lease 清理，把租约过期的运行态变回 `queued`，`domain/jobs.py:204-208`），**但不 schedule**。
2. 再取 `store.list_jobs(states={非终态})`，逐条：`_remember_stable_checkpoint(job)` 记断点（`main.py:3827` 现有写法）→ 若不是 `paused` 则 `transition(PAUSED)` → 清 `worker_id` / `lease_until` / `queue_position` → 同步 `run.status="paused"`（否则 run 停在 queued，后续 `resume` 状态不一致）。
3. 打一条日志 `startup_hold count=N`，便于核对。
4. **只在启动时做一次**。同一次会话内新导入的 300 条仍是 1 跑 + 299 排队，正常接力。

## R1 启动挂起

- 状态：**已实施**（范围含上次正在跑的那条，2026-11-18 22:15 用户确认）。落点 `main.py` 模块级 `_hold_interrupted_jobs(store)` + `create_app` 内 `held_jobs = _hold_interrupted_jobs(store)`；`queue.py:_run` 改 `while` 循环。
- 现状：`main.py:1823-1829` 只把 `recover_expired_jobs()` 的结果丢线程自动续跑；库里的 `queued` 永远躺在那里，界面上显示「等待中」（问题 1 的现场实例）。
- 原因：没有「跨会话一律先停住、等用户点」的语义。
- 方案（22:16 已按转移表核验做减法）：
  1. 启动流程改为 `_hold_interrupted_jobs()`：**直接** `store.list_jobs(states={非终态})` 逐条挂起。**不再先调 `recover_expired_jobs()`**——它唯一的作用是「lease 过期 → 运行态转 queued」（`domain/jobs.py:204-208`），而我们下一步就把 queued 转 paused，等于白写一次库、多一个中间态；而且它跳过 lease 未过期的运行态（`lease_until > now` 直接 False），反而漏挂。
  2. 挂起单条：`_remember_stable_checkpoint(job)` → `if job.state is not JobState.PAUSED: job.transition(JobState.PAUSED)` → `store.save_job(job)` → `run.status="paused"`、`store.save_analysis_run(run)`。**不需要手写 `worker_id=None / lease_until=None / queue_position=None`**：`transition()` 命中 `target is PAUSED` 时已清这三个字段（`domain/jobs.py:142-145`）。
  3. 日志 `startup_hold count=N`。
  4. `_run()` 尾递归改 `while` 循环：现在 `finally` 里调 `self._run(next_item, runner)`（`queue.py:237`），用户手动批量继续 300 条时就是 300 层栈帧，加 `run_analysis_job` 内部几十层，逼近 Python 默认 1000 层。改法：外层 `while True` 取 `_pending.pop(0)`，`runner` 返回后继续；不动 `_active` / `_save_positions` / `revive_provider` 语义。
- 可行性核验（22:16 只读查证，未改代码）：
  - `QUEUED → PAUSED` 在转移表里合法（`domain/jobs.py:87`）；`ACQUIRING / EXTRACTING / TRANSCRIBING / CHUNKING / SUMMARIZING / ARCHIVING / INDEXING → PAUSED` 全部合法（`:88-108`）。所以「全量非终态转 paused」不会抛 `InvalidTransitionError`。
  - `PAUSED → PAUSED` **不合法**（`:109` 只有 `{QUEUED, CANCELLED}`），第 2 步的 `is not PAUSED` 判断是必需项，不是防御性冗余。
  - `AnalysisRun.status` 是无枚举约束的 `str`，默认 `"queued"`（`domain/models.py:168`），写 `"paused"` 不会撞校验。
- 验收：
  - [自动] 临时库造 3 条 `queued` + 1 条 `acquiring`（**lease 故意设为未过期**）+ 1 条已是 `paused` → 跑启动挂起 → 前 4 条全 `paused`、`queue_position=None`、`metadata.resume_checkpoint` 存在、对应 run 的 `status="paused"`、`persisted_queued=0`；第 5 条不抛 `InvalidTransitionError` 且状态不变。
  - [自动] 同一次会话内新导入 3 条 → 仍是 1 跑 + 2 排（挂起只在启动时生效）。
  - [自动] 1200 条手动继续只跑空任务，不得 `RecursionError`。
  - [实测] 重启 8765 后 `/api/v1/queue` 的 `queued` 为 0、`stats.waiting` 为 0；任务页「未完成」里出现这批「已暂停」，勾选点「继续」能跑。
  - [人工] 点「继续」后是否从断点阶段接着跑，而不是从头。
