# AI 交互与任务状态术语解决方案

2026-11-22。范围为桌面端界面。本文是拟定方案，实施与人工验收未开始。以 [已核实问题台账](../审计/2026-11-22_产品交互与状态同步问题台账.md) 为证据，任务实际队列规则另见 [任务 PRD](../../基线/prd/02_任务_PRD.md)。优先修正会让用户误判任务是否在跑、是否已停止，以及操作影响哪条任务的用语。

## 现状审核

| 区域 | 当前入口或文案 | 实际动作及混淆 |
|---|---|---|
| 新增任务 | 内容接入「查询」「提交」，成功提示「已提交，任务已生成」 | 查询只预览。提交接受后创建任务，有的输入复用已有结果，有的失败。「任务已生成」容易与 AI 结果生成混读。任务工具栏没有独立新建按钮，内容接入是主入口。 |
| 列表筛选 | 「进行中」「未完成」 | 「进行中」含排队与保存进度。「未完成」包含暂停、失败与取消。排队状态既可被理解成未完成，也还没有开始处理。 |
| 暂停 | 执行中和保存进度均显示「暂停」 | 保存进度是队列切换过程。点击暂停等待响应时按钮仍显示原动作，已暂停时才是真正停止等待用户恢复。 |
| 继续 | 行内和批量都叫「继续」，行内成功提示「已开始」 | 行内默认排到队首，批量排到队尾。恢复接口先写入排队，可能尚未执行。 |
| 插队 | 成功固定提示「已开始，原任务已让出」 | 有当前任务时，它保存进度后回队列，目标会优先处理。没有当前任务时，原任务让出无对应对象。接口接收也不证明目标已开始。 |
| 重试 | 失败、取消后的行内「重试」；批量也叫「重试」 | 行内用于失败、取消。批量可把暂停项转为继续，也会跳过处理中等状态。一组结果可能同时含重新排队、恢复及未处理。 |
| 取消与删除 | 任务有已取消状态和服务接口。当前任务栏检查到「删除」，未找到独立的「取消任务」入口 | 批量删除部分状态会先暂停或取消再删除任务记录。最终反馈把这段内部过程称作「暂停转取消删除」。问答的「取消」只是清空输入，已发送请求仍可能返回。 |
| 上一项与当前执行任务 | 笔记页有「上一条／下一条」。任务区有插队逻辑 | 笔记翻页切换查看对象。插队改变谁先执行。当前任务栏未见名为「上一任务」的按钮。 |
| AI 生成与结果 | 问答「继续」提示「已继续生成」。详情「重新生成」打开名为「重新总结」的弹窗 | 「已继续生成」先依据请求成功提示，仍需确认生成状态。重新总结会提交生成任务。两处入口应使用一致且对象明确的名称。 |

## 拟定状态与动作

状态表统一由已确认的服务状态渲染。按钮等待用户操作时用动词，请求处理中在按钮或行内显示即时反馈，服务确认后用结果状态。请求失败保留对象与重试入口。

| 场景 | 动作 | 请求等待 | 确认后显示 |
|---|---|---|---|
| 提交新任务 | 提交任务 | 提交中 | 已创建 N 项任务。复用和失败分别计数 |
| 手动暂停 | 暂停 | 正在暂停 | 已暂停。若仍在保存或处理中，显示当前状态 |
| 恢复暂停任务 | 继续 | 正在恢复 | 已重新排队 / 已开始处理，按实际状态 |
| 变更执行优先级 | 优先执行 | 正在切换 | 等待时显示已移到队首，运行后显示已开始处理。原任务已回队列仅在可核对时显示 |
| 失败或取消后重跑 | 重试 | 正在提交重试 | 已重新排队 / 重试失败 |
| 停止任务并保留记录 | 取消任务 | 正在取消 | 已取消。独立入口如需新增，需先确认适用状态、检查点后果和重跑语义 |
| 移除任务记录 | 删除任务 | 正在删除 | 已删除 N 项任务，另列未删除项。需确认时说明对正在处理和已归档结果的实际影响 |
| 看相邻结果 | 上一条笔记 / 下一条笔记 | 按需显示加载态 | 切换到相邻笔记。首尾禁用对应按钮，不作任务状态变更 |
| 问答 | 发送 / 清空草稿 / 停止生成 / 继续生成 | 等待回答 / 正在停止 / 正在继续 | 回答、已停止或失败。停止和继续需绑定本次请求和实际后端状态 |
| 笔记更新 | 重新总结 | 提交中 | 已创建重新总结任务。新版本只在实际生成后显示 |

建议把聚合筛选「进行中」改为「处理中」，范围仍含排队、执行与保存进度，状态列分别写「排队中」「执行中」「正在保存进度」。聚合筛选「未完成」拟保持现有筛选含义，评审时可比较「需处理」是否适合同时涵盖已取消。批量重试对混合选择应明确列出各类动作。优先方案是「重试」只处理失败或取消项，暂停项用「继续」，上线前核对既有批量操作是否依赖自动恢复。行内继续排队首、批量继续排队尾是否统一是一项产品选择，当前方案先按真实结果反馈。

## 已知交互缺陷的处理与验收

| 项目 | 拟定处理 | 验收条件 |
|---|---|---|
| 返回与恢复 | 设置保存进入时来源。任务结果保留来源任务列表。笔记正文工具区保留快捷栏恢复按钮，并随折叠调整列布局 | 从任务、问答、知识库进设置分别返回原页。任务结果回原列表。折叠后可在当前页恢复且正文可读 |
| 等待与重复点击 | 给刷新、暂停、提交、环境检查、ASR 切换加相应进行状态与请求期防重。完成和失败显示可验证结果 | 受控慢响应期间有可见状态。失败后按钮恢复。环境检查能定位待处理项，ASR 失败可重试 |
| 问答 | 将草稿操作与已发送请求的停止分开。显示等待和终态，失败时能用原问题重试 | 对照请求 ID 验证停止、失败和恢复。切换会话后结果仍归属原会话 |
| 链接提交失败 | 保留输入并让「重试提交」能重新查询和提交，或在当前界面明确提供重新查询动作 | 失败后下一次有效操作可发出新请求，输入保留 |
| 后端已保存后的同步 | 进入任务刷新列表和队列，进入库刷新内容、标签和收藏夹。已打开笔记支持原地刷新，是否自动跨会话同步按产品需求裁定 | 另一客户端已保存后，切出切回显示新列表。笔记原地刷新后显示新分类。同页新建仍立即出现 |

实施后的 XState 回归以「操作 → 请求接收 → 等待或处理中 → 业务结果 → 下一步」建模。重点组合为新增任务和复用、暂停与回队列、插队有无原任务、取消和删除、上一条笔记首尾、问答取消和继续。服务端写后读回、UI 实际显示、人工可理解性分别记录。


## 本轮复核证据

Playwright MCP 使用受控七状态任务队列观测界面。单条「继续」返回 queued，行内显示「插队」，同时弹出「已开始」，同屏反馈冲突。「插队」同样在目标仍为 queued 时显示「已开始，原任务已让出」。暂停样本返回 paused 时显示「已暂停」。编辑态按钮实际为「暂停／继续／重试／删除」。真实笔记页实际显示「上一条／返回知识库／下一条」。批量分流、取消服务能力和上一条按钮的动作归属来自代码核对，未对线上或真实活动任务执行取消、暂停或删除。

## 修复批次与验收

| 编号 | 修复内容 | 完成条件 |
|---|---|---|
| R1 | 任务动作与状态。行内的继续、优先执行、暂停和重试在请求期间显示对应动作并防重复，响应后读回任务和队列，再据实际执行状态反馈。批量反馈按动作结果计数 | 行内继续和优先执行返回排队时均显示排队。空闲时优先执行无原任务提示。有活跃任务时只在确认原任务回队列后提示。保存进度期间不重复发同一操作。 |
| R2 | 任务新增和接入失败。查询反馈保持识别，提交时显示提交队列的进度。接受、复用、失败分别计数。失败保留原输入，通过重试重新查询再提交 | 慢响应期间按钮有进度并防重复。失败后无需猜测下一步。新任务在任务页可见后才称已创建，复用时能区分未新建。 |
| R3 | 任务、设置、笔记的导航和恢复。设置保存来源页，结果页保存任务来源和列表上下文。快捷栏在正文工具区保留恢复入口，折叠后正文重新占用可用空间。笔记翻页明确对象 | 三个来源进设置后返回原页。任务结果返回任务筛选和滚动位置，合集笔记仍逐层返回。收起和展开互相可达。首尾翻页不能误操作。 |
| R4 | AI 问答的发送、等待、停止、继续和终态。复用 POST 接受后返回的 query_id、GET 查询状态、POST cancel 和 continue。发送时立即显示等待。已接受请求按 ID 拉取状态，只更新其所属会话 | 慢请求有等待反馈。cancel 返回 cancelling 期间保持停止中，终态再更新，若先完成则展示实际完成结果。continue 返回 queued 时显示排队。失败提供原问题重试，切换会话或离开再回来时仍能找回原问题和结果。 |
| R5 | 列表同步和读操作反馈。进入任务刷新任务与队列，进入知识库刷新内容、标签和收藏夹。笔记提供原地刷新。列表刷新、环境自检及 ASR 加载区显示等待、完成或失败 | 隔离副本写入后，切页能看到新数据。读请求失败保留当前有效数据和重试入口。ASR 标题及内容属于同一分区，空模型与加载失败可区分。环境自检展示可定位的异常项。 |
| R6 | 任务取消和批量动作策略。保留记录的取消、移除记录的删除、恢复暂停的继续、重跑终态的重试分别定义。按产品裁定补入口或限制适用状态 | 每个动作按适用状态可见或可用。确认文案和终态能反映是否保留记录及归档。混合批量选择在执行前明确处理对象，并分别报告跳过和失败。 |

建议实施顺序为 R1 与 R2，接着 R3 与 R5，随后 R4。R6 涉及操作后果及队列策略，评审时与下列选择一并裁定。各批次独立验收，人工项记待人工验收。

## 方案待裁定项

- 任务区是否新增独立「取消任务」。建议先支持可安全停止的任务，并保留任务记录，和删除分开。需要明确适用状态及检查点处理规则。
- 行内继续是否仍优先回队首。建议本轮先保留现有行内队首、批量队尾规则并如实提示，队列规则调整单独确认。
- 批量重试是否继续兼容恢复暂停项。建议只重试失败或已取消项，暂停项由「继续」处理，先检查既有使用路径再实施。
- 已打开笔记是否要自动接收另一客户端改动。建议此轮验收原地刷新和重新进入。自动跨客户端同步另作产品决策。

验证分三层。第一层用受控慢响应、失败和成功，覆盖提示和防重复。第二层用隔离真实服务写后读回，对齐任务列表、队列和结果。第三层用 XState Graph 生成回归路径，由 Playwright MCP 逐步确认，另留人工文案可理解性验收。
