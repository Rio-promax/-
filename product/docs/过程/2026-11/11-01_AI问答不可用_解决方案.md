## 产品问题 1

### 用户原话

> 本地ai问答项目一直不可用 @image#1:Clipboard_Screenshot.png，核实原因并解决

### AI 解释

界面上的"无法连接总结服务"不是网络故障。真实链路为：检索耗尽了整条路径的时间预算，回答阶段拿到的超时只剩 1~2 秒，请求必然超时，而超时被统一包装成"无法连接总结服务"。

证据（`rag_queries` 表 `aq_746328135e224b00a65a25feac20774b`，2026-11-01 21:04）：

| 阶段 | 结果 | 耗时 |
| --- | --- | --- |
| P-ROUTE | ok | 1875 ms |
| 检索 search | ok | 22141 ms |
| P-RESPOND | TimeoutError | 1094 ms（超时预算仅 1 秒） |
| 路径总预算 | `path_deadline_seconds = 20` | 总计 25.5 s |

复核重建：`aq_e4e9862413e84948afcd80878f1f7f9a` 同样失败，检索 15031 ms 后回答阶段只剩 2 秒。

同一批失败记录里另有 3 类独立成因，逐条见 R2、R3、R4。

## 产品问题 2

### 用户原话

> ai问答在今天进行修复后还是显示这样无法进行使用 @image#1:Clipboard_Screenshot.png

### AI 解释

超时与预算已修好（R1~R5 生效：路由 1.9 秒、检索 4.8 秒、回答 1.7 秒，全程无超时），但答案仍未产出。界面上的"证据不足"不是没检索到：范围 34 条、索引 34/34 全覆盖、召回 26 个证据块来自 13 条资料。真正成因在证据文本被截断时切掉了关键词。

证据（`rag_queries` 表 `aq_70c7dad50d044ee8820e7b77ade638a9`，2026-11-01 21:56）：

| 环节 | 观察值 |
| --- | --- |
| P-RESPOND 输入 | 9245 字节 / 上限 10000 字节；送入 8 块，**8 块全部被截断** |
| 命中证据 | 26 个候选块中只有 2 块含 `RAG`，其中 rank 1 为 `summary:paragraph:3` |
| 关键词位置 | `RAG` 在该块第 141 字符（第 411 字节）；单块只分到约 380 字节 |
| 模型判定 | `slots[0].score = 0`，missing = `Evidence text snippets do not contain the term 'RAG' or related context.` |
| 召回别名 | `lexical_aliases = [{"alias": "检索增强生成", "hit_count": 1}]`，`RAG` 未参与检索 |

两个缺陷叠加：

1. `rag.py:136` 的 `_retrieval_query_aliases` 把用户写的 `RAG` 换成中文别名"检索增强生成"并**丢弃原词**。检索别名只命中 1 块，真正含 `RAG` 的资料（如"大厂AI产品经理到底要会啥？"）根本没被召回。
2. 同一函数同时充当截断锚点（`rag.py:1605` 的 `focus_terms`）。既然锚点是"检索增强生成"，而证据原文写的是 `RAG`，`_truncate_bytes_around_term` 无锚可用，退化为从头截断；`RAG` 位于第 411 字节，超出 380 字节窗口，被整段切掉。模型看到的 8 块文本确实不含 `RAG`，于是按规则给 `score=0`，最终 `status=insufficient`。

## 统一范围与实施顺序

只改问答链路的预算、文案与查询别名表，不动索引结构与校验规则。顺序 R1 → R2 → R3 → R4 → R5 → R6，R1/R2/R5/R6 改完各自重启后端实测。

## R1 回答阶段保底超时

- 状态：已解决
- 现状：`app/knowledge/rag.py:952` 用 `min(20, _remaining(started, path_deadline))` 取超时。检索常耗 15~22 秒，非复杂路径总预算只有 20 秒，进入回答阶段时剩余被压缩到 1~2 秒，而历史成功生成需要 2.4~7 秒。
- 原因：把"总预算剩余量"直接当作单次调用超时，预算耗尽后没有保底。
- 方案：改为 `min(60, max(20, _remaining(started, path_deadline)))`，回答阶段至少保留 20 秒生成时间，上限 60 秒。
- 验收：同一提问 `哪些资料讲rag` 返回 `completed / answer`，P-RESPOND `timeout_seconds=20`、耗时 2937 ms。

## R2 枚举类纳入复杂路径

- 状态：已解决
- 现状：`rag.py:595` 的 `complex_path` 只含 `synthesize / compare / relation`，`enumerate` 被当作简单路径：总预算 20 秒、总输出 2000 token、首轮输出上限 650 token。而枚举提问的输入上限已是 10000 字节，输出 650 token 装不下多条引用，实测出现 `问答服务未返回有效 JSON`（JSONDecodeError）与只给 1 条引用的空壳答案。
- 原因：输入按枚举放宽，输出与时间预算没有同步放宽。
- 方案：`complex_path` 集合加入 `enumerate`，使其获得 45 秒预算、4500 总输出、3 次回答调用。
- 验收：`哪些资料提到了AI产品经理` 由 `failed / unavailable` 变为 `completed`，不再报 JSON 解析失败。

## R3 超时文案不再指向网络

- 状态：已解决
- 现状：`app/adapters/summary/openai_compatible.py:490` 把 `TimeoutError` 与 `URLError / OSError` 合并成"无法连接总结服务，请检查网络、API 地址或请求超时设置"，把预算不足说成网络故障，掩盖了真实原因。
- 原因：异常分类过粗。
- 方案：`TimeoutError` 单独成句"总结服务请求超时，请稍后重试；反复超时请在设置页调大超时时间"，网络类异常保留原文案。
- 验收：源码核对两分支存在；后续超时场景文案可区分。

## R4 状态 `unavailable` 显示中文

- 状态：已解决
- 现状：`app/ui/app.js:7516` 的状态映射缺 `unavailable`，界面直接显示英文 `unavailable`（见原图01）。
- 原因：映射表漏项。
- 方案：映射表补 `unavailable: "不可用"`。
- 验收：源码核对；前端刷新后生效。

## R5 检索耗时压到 1/8

- 状态：已解决
- 现状：`search` 单次 15~22 秒，占整条问答 65%；其中向量检索 34 个内容逐个 KNN 占 99%，FTS5 只有 72ms。
- 原因：`app/db/store.py:261` 的连接事件只设 `PRAGMA foreign_keys=ON`，全项目无 `mmap_size`；默认页缓存 2MB。每次向量查询都要走磁盘 read()，113MB 的库上 34 次查询累计 10 秒。
- 方案：连接事件补 `PRAGMA mmap_size=536870912` 与 `PRAGMA cache_size=-65536`（只加 mmap 仍会在 0.6~3 秒抖动，页缓存会反复淘汰）。
- 验收：34 次循环 10 033ms → 248ms；端到端三轮 `search` 3578 / 1359 / 3719 ms，总耗时 8.8 / 7.8 / 8.9 秒（修复前 24.4~28.5 秒）。

## R6 英文缩写原词同时参与召回与截断锚点

- 状态：已解决
- 现状：`app/knowledge/rag.py:136` 的 `_retrieval_query_aliases` 对 `RAG` 只返回 `("检索增强生成",)`。该返回值同时被两处使用：`rag.py:2197` 作为补充召回别名，`rag.py:1605` 作为证据截断锚点。于是英文原词 `RAG` 既不参与召回，也不参与截断定位，含 `RAG` 的资料召不回来、召回来的也被切在关键词之前。
- 原因：把"同义词扩展"实现成了"同义词替换"，别名列表里缺原词。
- 方案：返回 `("RAG", "检索增强生成")`，原词与别名并列。检索侧 `RAG` 与已有 trigram 同源，去重后不重复计分；截断侧 `_truncate_bytes_around_term` 能命中 `RAG` 并把窗口居中到关键词。
- 验收：同一提问 `哪些资料讲 RAG` 返回 `completed / answer`，引用 2 条（`2026年AI产品经理面试总结与9月面试规划`、`大厂AI产品经理到底要会啥？`）；`retrieval_stats.lexical_aliases` 由 `[{"检索增强生成": 1}]` 变为 `[{"RAG": 3}, {"检索增强生成": 1}]`；`slots[0].score` 由 0 变 2。
