| 编号 | 位置 | 机制 | 证据 |

## 解决方法

### 原则

- **先交付一致性，再状态一致性，最后才是体验与耗时。** 顺序颠倒会把旧壳的缺陷误判成新代码的缺陷，上一轮已发生过一次。
- **R1 单独成轮、复测后再裁剪 R3～R5**；U2 未闭合前不一次性押注全部新代码。
- 不改后端 API、不新增消息类型、不新增弹窗；沿用 `platform-session-result` 与 `progress` 标记。
- 界面只出现状态词与结果，不写解释句（界面文案规则）；R1 不产生代码提交。
- **本文件行号均为快照，实施时以符号名为准**；落地前先对齐最新 HEAD 并确认并行改动方已收口。

### 范围与顺序（四步裁决，顺序不动）

R1 交付一致性（单独成轮 + 真实导入复测，回填 U2） → 按复测结果裁剪 R3／R4 → R2 状态一致性 → R3 等待与提示 → R4 耗时 → R5a 诊断／R5b 修复 → R6 验证与回填。

## R1 让壳与源码一致（C1、C9、C10）——单独成轮

- **状态**：未实施。
- **现状**：`LoginShell.dll` / `.exe` 构建于 2026-11-12 18:08:52；源码此后两次提交共带来四项能力——`a58ba44`（11-12 18:16，构建后 8 分钟）引入 `scope` 与 `albums`，`28135eb`（11-13 17:36）引入扫描前 `Show()` 与 `FavoriteScanProgress`；运行进程里四项一项都没有。壳于 18:07:32 重启过（PID 5624），加载的仍是 11-12 的旧 DLL——**重启不等于重建**。
- **方案**：
  1. 先结束壳进程：`taskkill /IM LoginShell.exe /F`（按镜像名，避免 PID 过期；18:20 复核现行 PID 为 5624，E1 的 19640 已不存在），避免 E3 记录的输出目录被占用导致 build 失败。

  3. `product/start-product.cmd` 重启（它会拉起服务与壳）。
  4. 防复发守卫放在**正常启动路径**（主流程，不是 `:error_shell` 报错退出分支）：比较 `LoginShell.dll` 与 `Program.cs` 的 `LastWriteTime`，源码较新则先 build 再启动并打印一行提示；build 失败即停并提示，不回退到旧壳。**build 必须用绝对路径 `"C:\Program Files\dotnet\dotnet.exe"`**：PATH 上的 `dotnet` 指向 `C:\Program Files (x86)\dotnet\dotnet.exe`，`--list-sdks` 为空，直接调会报找不到 SDK（E10）；该文件不存在时只提示、不启动新壳。`start-product.cmd:83` 给用户的提示同样是裸 `dotnet build`，一并改成绝对路径。
  5. **跑一次真实导入复测，把结果回填 U2**；按复测结果决定 R3～R5 是否保留，再进入下一轮。

## R2 状态只写不校（C5–C8）——重写

- **状态**：未实施。
- **现状**：设置页连接状态是 15:28 的库快照，连接行与检查结果都按「已连接／未连接」二元渲染；扫描失败不回写；16:25 的「刷新连接状态」只读库且已于 16:47 被删除；后端 `/check` 对小红书不探测却返回旧记录。公共「检查连接」入口已由 `6f6dc58` 落地（B站 `POST /platform-connections/{p}/check` + 小红书壳 `check_session`），**双平台检查本身已不需要本轮新建**。
- **方案**：
  1. `requestDesktopShell` 在 reject 时把壳返回的 `result` 挂到 `error.result` 上。
  2. **失败回写只对会话类状态生效**：三处 `startXhs*` 的 catch 中，仅当 `error.result?.status` 属于 `NOT_CONNECTED` / `EXPIRED` / `RISK_CONTROLLED` 时调 `saveXhsSession(error.result)` 并 `refresh("connections")`。**`REAUTH_REQUIRED` 与 `PARTIAL` 不回写**——C11 的「已登录但读不到正文」返回 `REAUTH_REQUIRED`，回写会把读取失败误判成会话失效，重新制造 P2 的状态矛盾；这也与 R5a 的「已登录，但没读到收藏数据」保持一致。**由此 P2-2 在「已登录但读不到」这条路径上不由状态翻转表达，而由弹窗三档文案 + 连接行的 `last_checked_at` 表达——这是有意设计，不是漏改**，下一轮不得据此判为未修。
  3. **二元渲染改多状态**：连接行的 `status === "CONNECTED"` 判断、以及公共检查结果拼接的「已连接／未连接」两处，都改为呈现 `CONNECTED` / `NOT_CONNECTED` / `EXPIRED` / `RISK_CONTROLLED` / `REAUTH_REQUIRED`，并补 `RISK_CONTROLLED` 的「需要人工验证」映射。函数名与行号以实施时文件为准。
  4. **复用届时存在的公共检查入口，不新建、不改名**：`6f6dc58` 已实现 B站 + 小红书双平台核实（`app.js:637` 的 `checkAllConnections`，按钮 `:1843`，分支 `:2584`）；本轮只补「结果按平台分别呈现、不做一句全局提示」——要改的就是 `:652` 的 `toast(parts.join(" · "))`——与「完成后统一 `refresh` 再渲染」（`:650-651` 已具备，确认即可）。**不再写「扩展 `conn-verify`」或「把刷新连接状态改名」——两者均已不存在**。
  5. 连接行加 `last_checked_at` 的日期时间，让「已连接」带时间戳，不是无限期断言。
  6. **顺手修 `result.healthy`**：`app.js:2586` 的环境自检读 `result.healthy`，而 `EnvironmentCheckResponse`（`schemas.py:38-47`）只有 `status`，所以无论环境多好都恒弹「环境存在待处理项」；改为 `result.status === "ok"`。这条与本轮三组问题不直接相关，但它在同一设置页且已被 R2 验收引用，不修则验收无对应步骤——若不修，则把该项从 R2 验收删除，二选一，不留「有验收无步骤」。
- **验收**：自动 — 契约测试断言「只回写三类状态」「`REAUTH_REQUIRED` 不回写」「B站与小红书都被检查」「不再读 `healthy` 之类不存在的字段」；`node --check`。人工 — 导入失败后回设置页，状态与原因同步且两处不矛盾；点一次「检查连接」两个平台都被真实核实。
