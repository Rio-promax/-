## 产品问题 1 · 知识库已有的内容仍留在未完成区

### 用户原话区（逐字，不许改写）· U-R1-01

> 还有一个问题，这里已失败，就是未完成中，怎么感觉好多它和已经成功的重复了呀。就是。感觉知识库已经有了，但是还在未未完成圈里面。我希望增加一个逻辑，就是如果未完成或者说新增的是属于知识库中已有的。那么可以增加一条提示，叉叉叉已有确定要归档吗？确定，或者说放弃舍弃这几条，放弃或者继续。然后点了之后就可以继续其他还没有进行过的，然后把那几条就进行跳过相当于是不进行了，相当于是删除了，就比如现在一失败中可能有个几十条，有十条是已经重复的。那么点击之后就会提示这十条已经重复，是否要继续导入，点击确认导入的话，那么就继续导入，导入出的产品后面加个 12，然后就巴拉巴拉的，但是如果用户选择了放弃重复的那个当然它的 UI 的按钮叫什么还要斟酌一下，不能叫取消，取消的话就有点像取消全部的也不能字也不能太多，然后点了那个之后给出的操作就是把 OK 的就纳入到进行中。把重复的并且用户选择取消的，那么就从任务栏中进行删除，相当于就不显示这条任务了

### 用户裁决区（逐字）· U-R1-02

> 重复提示在哪个时机弹出来？ → 批量操作时先检测（推荐）
> 你说「继续导入的产品后面加个 12」，具体指什么？ → 标题后加递增序号（推荐）
> 弹窗两个按钮叫什么？（要短、不能叫「取消」） → 继续导入 / 舍弃
> B站同一视频（同 BVID+P）在知识库会按来源身份折叠成一条、只显示最新那条。那"继续导入"生成的带序号副本，应该怎么处理可见性？ → 改折叠键让副本独立显示（推荐）
> "舍弃"和批量删除统一走 cancel+DELETE 现成两端点。可行吗？ → 统一复用现成两端点（推荐）

### AI 解释区（R1，v2 补正）

- **用户直觉成立，但 v1 的数字口径不严**：v1 说"178/210 条重复"，那只是"样本中有旧 `completed` 任务的比例"，**不等于当前知识库可见性**。v2 改用知识库活跃口径判定（见下），并保留 178 作为历史背景数据，不作为弹窗依据。
- **"重复"的真相**：未完成（failed+paused）任务里有大量条目的 `content_id` 与某个 completed 任务相同（v1 实测 178/178）。不是两条不同内容重复入库，而是**同一条内容既有 completed 任务进了知识库，又残留了 failed/paused 的历史任务**——`retry_job()`（`main.py:4225`）传 `content_id=previous_content.id` 复用同一内容，每重试一次多一条 job；11-21 的按内容归并只保留最新一条，未完成筛选下若最新那条是 failed/paused，就显示在这里。
- **"知识库已有"的判定口径（v2 新增，审核要求）**：以**当前有效、已归档的内容**为准，即 `GET /history` 活跃列表中 `archived_only=true`（`JobRow.state=completed`）且 `deleted_at is null` 的内容；回收站（`/trash`）内容不算"已有"。用 `S.jobs` 的 completed 集合判重有两个已证实的盲区：① `/jobs` 最多 2000 条（现 393 条未触及，但旧成功记录可能被挤出）；② 现测 393 条里 183 条 completed job 有 12 条内容不在活跃 history、回收站有 4 条 completed 内容。判定分两层：**相同 `content_id` 直接匹配**活跃归档内容；跨 ID 时沿用产品已有的来源身份规则（`store.find_duplicate_content()`，`store.py:571`，按 canonical_url/content_hash + BVID+P 兜底），不另造算法。
- **"继续导入加序号"的真相**：对同一 `content_id` 点 retry 只复用原内容、永不加后缀。能新建带「（N）」后缀内容的是现成管线 `resummarize_content()`（`main.py:4250`）→ `find_duplicate_content()` → `_source_with_duplicate_title(..., "regenerate")`（`main.py:8024`）→ `next_duplicate_title()`（`store.py:609`）→ `workflow.submit()`。用户选的"递增序号"正是这条既有行为。
- **副本可见性缺口（v2 新增）**：`store.list_history()` 按 `_history_identity_key()`（`store.py:2896`）折叠 B站 `bili:BVID:pN` 同身份条目、只留 run 最新一条。带「（1）」副本若 canonical_url 同源，**会被折叠，原件看不到**——v1 承诺的"原件+副本同时可见"不成立。用户裁决改折叠键，见 R4。
- **批量删除失败（另见产品问题 2）**：与重试 409 同型，是批量操作没按状态分流。

## 产品问题 2 · 批量删除部分成功部分失败

### 用户原话区（逐字，不许改写）· U-R2-01

> 然后还有一点就是我点了删除之后为什么删除，批量删除之后为什么删除失败了。它显示两条删除成功，其他的删除失败是为什么？

### AI 解释区（R2，v2 补正）

- **已定位且有逐项日志证据**：`store.delete_job()`（`store.py:1489`）只允许 `completed/failed/cancelled`；`paused` 抛 `job_not_deletable` → HTTP 409（`main.py:3999`）。`backend.log` 14:41:16 那批删除 **36 项：204×2、409×34**，正好对上用户说的"两条成功，其他失败"——这是审核要求补的逐项请求结果，已坐实。
- 前端 `jobAction()` delete 分支（`app.js:1618`）把 409 计入 `failed`，最终只提示"N 项未成功"，`humanizeApiError()`（`app.js:1127`）把 snake_case 错误码泛化成"该项当前不可用"，用户看不到真正原因。
- 修法：按状态分流，暂停项走现成的 `cancel` → `DELETE`（见 R2/R3），并让失败原因可见。

## R1 · 批量操作前置查重与重复清单

- **状态**：已实施，自动验证通过；待人工验收。
- **现状**：勾选未完成任务点重试/继续直接逐条执行，不区分知识库是否已有；用户无法在失败项里看出哪些已经进过知识库。
- **原因**：`jobAction()`（`app.js:1588`）无查重分类；前端数据基本够用（`S.jobs` 含 `content_id`/`source_url`/`state`，`S.history` 含活跃归档内容），但用 S.jobs 判重有 2000 上限与回收站两个盲区，需以活跃归档为准。
- **方案**：
  1. 判重数据源：优先用 `S.history` 中活跃且 `archived_only` 的内容（回收站不计）；若当前页 history 未含全量，增加一个后端只读接口 `POST /api/v1/jobs/duplicate-check`，接收 job id 列表，服务端用 `store.list_history(archived_only=True, include_deleted=False)` + `find_duplicate_content` 判定并返回每项 `{ job_id, is_duplicate, matched_content_id, matched_title }`。**首选后者**——判重口径在服务端统一，避免前端 2000 上限与 history 分页盲区；若实施时确认前端已持全量 history 且盲区不存在，可退化为纯前端判定，二者选一，不留两套。
  2. 两层匹配：① 未完成项的 `content_id` 命中活跃归档内容 → 重复（v1 实测 178/178 属此类）；② 跨 `content_id` 时用 `find_duplicate_content(canonical_url=job.source_url)` 判重（BVID+P 兜底）。
  3. 只标记 `jobState(job).key` 为 failed/paused 的项；running/waiting/queued 即使同内容也不算（系统本就会接手）。
  4. `jobAction("retry"/"resume")` 进入时若 `duplicates.length > 0`，先弹 R5 双主动作框，展示重复条数 + 清单；选"舍弃"→ 重复项走 R3、`fresh` 项走原流程；选"继续导入"→ 重复项走 R4、`fresh` 项走原流程。
  5. `jobAction("delete")` **不弹查重框**（删除即移除任务），只走 R2 状态分流。这是唯一触发入口口径，全文一致。
  6. 弹窗结果随勾选集合传递，不在关闭后重算；重复清单按 `matched_content_id` 去重，同一内容的多条任务在弹窗里合并计为一条、提示"共 N 条任务命中"（副本数见 R4）。
- **验收**：
  - [自动] 契约测试断言两层匹配口径（同 content_id 命中/跨 ID 用来源身份）、failed/paused 才标记、running 不误判、删除入口不弹查重。
  - [人工] 见 R7 第一组最小复现。

## R2 · 批量删除按状态分流

- **状态**：已实施，自动验证通过；待人工验收。
- **现状**：批量删除时暂停项全部 409，最终只报"N 项未成功"，原因被泛化；日志 14:41:16 批次 36 项中 34 项 409。
- **原因**：见产品问题 2。
- **方案**：
  1. 前端 `jobAction("delete")` 按每项状态分流：终态（completed/failed/cancelled）→ `DELETE /jobs/{id}`；`paused` → `POST /jobs/{id}/cancel` 成功后 `DELETE /jobs/{id}`；`running/waiting/queued` → **先 `POST /jobs/{id}/pause` 成功再走 cancel→DELETE**，pause 失败则计入"跳过并保留"并明确提示（固定规则，不再二选一）。
  2. **唯一删除路径**：批量删除与"舍弃"共用同一个 helper `deleteJobWithState(job)`（前端函数），内部按上条分流；`cancel` 与 `DELETE` 都是现成端点（`main.py:4092-4112`、`:3990`），**不新增后端接口**。`cancel` 与 `delete` 都调 `cleanup_job_artifacts`，重复调用基本幂等，不去重。状态机允许 PAUSED→CANCELLED（`jobs.py:109`）。
  3. `humanizeApiError()`（`app.js:1127`）为 `job_not_deletable` 增加明确文案（如"该任务已暂停，需先取消再删除"），不再走 snake_case 泛化分支。
  4. **部分失败的反馈与重试**：每条记录独立结果；最终提示分四类"直接删除 N / 暂停转取消删除 M / 跳过 K / 失败 J"。**取消成功但删除失败**时，任务已处于 cancelled 终态、不会卡在中间态：计入"失败 J"并给出任务标题，用户再次点删除时按终态直接 DELETE 即可完成清理（重试安全）。
- **验收**：
  - [自动] 契约测试断言 delete 分支三态分流、暂停项先 cancel 后 delete、无新接口调用、错误码文案存在。
  - [人工] 见 R7 第二组最小复现。

## R3 · "舍弃"动作

- **状态**：已实施，自动验证通过；待人工验收。
- **现状**：无此动作；用户只能逐个删，且暂停项删不掉。
- **原因**：缺批量"确认重复后直接移除任务记录"的入口。
- **方案**：
  1. "舍弃"只对 R1 判定为重复的任务生效，逐条调用 R2 的同一个 `deleteJobWithState(job)`——**不另写删除逻辑、不新增接口**。
  2. 只删任务记录，不删 content、不删归档（知识库里已完成的必须保留，见 R1 口径）。
  3. 完成后 `syncJobsAfterMutation()` 刷新 jobs+queue 并重绘，重复项当场消失。
  4. 结果提示"已舍弃 N 条重复任务，知识库内容保留"；部分失败按 R2 的反馈与重试规则呈现。
- **验收**：
  - [自动] 契约测试断言"舍弃"调用 `deleteJobWithState`、不调用任何删 content/归档接口、不出现新接口路径。
  - [人工] 见 R7 第一组最小复现。

## R4 · "继续导入"动作与副本可见

- **状态**：已实施，自动验证通过；待人工验收。
- **现状**：重复项点 retry 复用原 content、不加后缀；即便新建带后缀内容，B站同源 URL 在知识库会被折叠，原件不可见。
- **原因**：见产品问题 1 的真相与副本可见性缺口。
- **方案**：
  1. "继续导入"对每条重复任务复用 `resummarize_content()` 管线：`find_duplicate_content()` → `_source_with_duplicate_title(..., "regenerate")` → `next_duplicate_title()` 生成「（N）」→ `workflow.submit()` 新建 content+job；原 run 的语言/强度/模板从 `settings_snapshot` 读取（retry 已有同型做法，`main.py:4175-4195`）。**逐条调用现成 `POST /api/v1/contents/{id}/resummarize`，不新写导入逻辑**。
  2. **副本数（审核要求）**：同一批多条任务命中同一 `matched_content_id` 时，**只创建一份副本**——按 `matched_content_id` 去重后每条内容调一次 resummarize；弹窗提示"共 N 条任务命中 M 条内容，将生成 M 份副本"。避免十几条同内容任务生成十几份。
  3. **副本可见（用户 16:03 裁决）**：改 `store._history_identity_key()`（`store.py:2896`），B站身份键由 `bili:{bvid}:p{n}` 改为 `bili:{bvid}:p{n}:{title_key}`，其中 `title_key` 取内容标题末尾的「（N）」后缀；无后缀仍用空串，保证原件与历史重复导入继续折叠。非 B站内容仍按 `content:{id}` 折叠，不受影响。这样原件与「（1）」副本在知识库各占一行、同时可见。
  4. **部分失败的反馈与重试**：**创建成功但旧任务清理失败**时，新 content+job 已入队、旧重复任务仍在：计入"J 项副本已生成但旧任务待清理"，保留旧任务不删（宁可重复显示，不丢数据），提示后可对旧任务单独点"舍弃"完成清理。**创建失败**时不动旧任务，按 `humanizeApiError()` 呈现原因，可重试。
  5. 旧任务的删除时机：仅在该内容的新任务**成功入队后**才按 R3 清理；清理调用同一个 `deleteJobWithState`，不用单独逻辑。
- **验收**：
  - [自动] 契约测试断言"继续导入"走 resummarize 而非 retry、同批同内容只建一份、`_history_identity_key` 带后缀键与无后缀键不同、创建失败不动旧任务。
  - [人工] 见 R7 第一组 B站同分 P 样本。

## R5 · 双主动作确认框

- **状态**：已实施，自动验证通过；待人工验收。
- **现状**：`requestConfirmation()` 只有一个可改文案的确认按钮 + 固定的"取消"，消息用 `textContent`，不能放清单。
- **原因**：R1 需要"继续导入 / 舍弃"两个主动作 + 清单。
- **方案**：
  1. 沿用 `requestConfirmation()` 的**回调式**契约（存 `S.confirmAction`、点击时 `await action()`、`closeConfirmation()` 归还焦点），不改成 Promise；"继续导入"与"舍弃"各自绑一个回调。
  2. 消息区与清单**用 `textContent` 逐条填充**（审核要求，不用 innerHTML 拼列表防 XSS）：标题栏一句话 + 每条重复项一行文本（最多显示前若干条，超出提示"等 N 条"）。
  3. 按钮严格用"继续导入"与"舍弃"，不出现"取消"。
  4. **锁的三条释放路径（审核要求写明）**：`jobsBatchBusy` 在 `jobAction()` 内置锁**之后**打开弹窗、期间保持、按钮禁用；① 点任一动作 → 关闭弹窗 → 执行分流 → 整批结束在 `finally` 释放；② Esc / 点遮罩 → `closeConfirmation()` 关闭、**不执行任何分流**、同一次 `finally` 释放锁、勾选集保留；③ 执行中失败 → 逐条计入失败数、不中断整批，最终仍在 `finally` 释放。三条路径都不会遗留锁或禁用态。
- **验收**：
  - [自动] 契约测试断言两个按钮文案、无"取消"字样、Esc/遮罩不触发分流、三条路径都释放锁。
  - [人工] 见 R7 第一组 Esc 分支。

### 第一组 · 查重分流（继续导入 / 舍弃 / Esc / 副本可见）

| 步 | 样本与操作 | 预期（任务 / 队列 / 知识库） |
|---|---|---|
| 1 | 混选三类：A「已有归档且最新任务暂停」、B「从未归档且失败」、C「已移入回收站且有历史成功任务」，点批量重试 | 弹窗只列 A；B、C 不列为重复；C 不计入"知识库已有" |
| 2 | 在弹窗点"舍弃" | A 的任务从任务栏消失，队列无新增，A 对应的知识库内容与归档仍在、标题不变；B 正常重试进入进行区；C 原样不动 |
