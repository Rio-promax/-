## 产品问题 1

### 用户原话区（逐字，不许改写）

> 1.小红书收藏依然无法打开，且用户无法知道无法连接的原因。

（图片引用标记 `@image#1:Clipboard_Screenshot.png` 属系统标记，见「图片与需求映射」，未计入原话区。）

### AI 解释区

- 「依然无法打开」= 原图01：点导入后弹窗停在「没有收到小红书收藏分页」，既没有目录也没有候选；同时底部 toast 是同一句。
- 这句话的出处是壳 `desktop-shell/Program.cs:4010`：`ScanFavoritesAsync` 导航到 `?tab=fav&subTab=note` 后 `WaitForResponseAsync(firstWaiter.Task)` 等到 `null`，直接 `RiskOrUnavailableAsync("没有收到小红书收藏分页")`；`Program.cs:4572-4589` 只在「页面有可见验证入口」时改成 `RISK_CONTROLLED`，其余一律返回 `REAUTH_REQUIRED` + 这句内部现象描述。
- **用户看不到原因**：这句只是「没抓到响应」的现象，没有区分「未登录」「被平台限制」「已登录但页面没发出可识别的业务响应」。而原图02 证明壳里账号已登录、收藏页正常可见 → 实际不是没登录，是**响应捕获没命中**（页面已停留在该 URL 时导航可能不再触发同一 XHR，或业务响应路径变化），但产品按「无法确认」处理。
- 前端 `app/ui/app.js:610-611` 只 `reject(new Error(result.message))`，`status` 与 `result` 一起丢掉；`startXhsScan`／`startXhsNotesScan`／`startXhsAlbumScan` 的 catch（`app.js:684-689`、`:727`、`:764`）只把 message 写进 `state.message`，**不回写连接记录**。于是出现原图03 说「已连接／登录已通过页面业务响应确认」、原图01 却导入失败且无原因说明的矛盾状态。
- 待确认：用户说的「无法连接的原因」是指导入失败原因，还是也包含连接状态本身的原因；AI 按「两者都要能判断」理解。

## 产品问题 2

### 用户原话区（逐字，不许改写）

> 2.设置中小红书显示选择未连接，但是打开连接后壳内有账号，然后退出来之后依然显示没有连接，过了一会之后自动显示为连接，这一部分缺少一个衔接，如果打开可灵有账号退出来之后要么给个提提示然后立马能进行连接，而不能这样退出来之后先显示不能连接，然后突然某个时候显示连接然后在新开的窗口中重新进行跑分，进行任务的执行。3。其实这个倒也挺爽的。

### AI 解释区

- 现象链已由代码完整复现：
  1. `app.js:2325` 点「连接」→ `requestDesktopShell("open_login", …, timeoutMs: 30min)`；`Program.cs:1775-1780` **只设置 `_pendingLoginRequestId` 并 `Show(this)`，不回传任何结果**，前端 Promise 一直挂着，连接行保持「未连接」。
  2. 原图02＝壳窗口里账号已登录。窗口里的「重新检查」是 `Program.cs:4534-4548` 的 `RecheckSession`：调 `CheckSessionAsync()` **但丢弃返回值**，结果只经 `Program.cs:4504` 的 `Result()` → `UpdateWindowStatus()` 写进窗口顶部那行文字（即「小红书收藏业务响应未能确认登录状态」），**不回传产品**。用户在窗口里检查过，产品状态毫无变化。
  3. 只有用户点窗口关闭才触发 `Program.cs:4487-4496` → `OnXhsLoginUserRequestedClose`（`:1931-1950`）→ **重新跑一整套** `CheckSessionAsync()`（`:3825`）：`_checkGate.WaitAsync()` 无超时 + 导航 12s + 等 `/user/me` 12s + 导航收藏页 12s + 等收藏业务响应 12s + `IsLoginWallAsync()`。这就是「过了一会之后自动显示为连接」——延迟几十秒的异步回执，不是实时衔接。若用户只是切回产品窗口而非点关闭，连这个回执都不会发生。
  4. 状态突然变化后用户再去导入，`Program.cs:1788-1792` 的 `scan_favorites` 又会 `login.Show(this)`／`BringToFront()` 弹壳窗口重跑扫描 → 对应原话「在新开的窗口中重新进行跑分，进行任务的执行」。AI 把「跑分」理解为重新跑扫描／任务，属含混处，按「状态变化不应触发任何新窗口或扫描」落地。
- 「打开可灵有账号」按语音转写理解为「打开壳里有账号」；「给个提提示然后立马能进行连接」＝**退出登录窗口时立刻给出核实结果并让连接态立即可用**，不要先显示未连接再异步突变。
- 末尾「3。其实这个倒也挺爽的。」语义指向不明（可能是编号笔误或对「自动变已连接」的调侃），**逐字保留，不作为可执行需求**，待用户确认。

## 产品问题 3

### 用户原话区（逐字，不许改写）

> 3.这里的几个键的作用是不是存在重复啊，首先总的下面有刷新连接状态，刷新连接状态是不是就包括检查连接，如果包括的话，那么就应该把小红书这个去掉，然后将刷新检查连接改为检查连接，然后自动检查 B 站和小红书。这个环境自检的作用是什么，如果没有用的话就把这个东西删掉，如果有用的话这个键长期显示环境已有东西，实质上阻碍。

### AI 解释区

- **前提先纠正：「刷新连接状态」不包括检查连接。** `app.js:2340` 的 `conn-refresh` 只调 `refresh("connections")`（`app.js:250-262` → `GET /platform-connections`）→ `main.py:4573-4582` 只从 DB 读记录返回，**不探测任何平台**。它现在等于「重画一遍页面」。
- 小红书行内「检查连接」（`app.js:1655`、`:2332-2338`）才真检查，但只走壳 `check_session`，只管小红书。
- **B站也有真检查但前端从没用**：`POST /platform-connections/{platform}/check`（`main.py:4761-4818`）对 bilibili 走 `probe_platform()` 并写库；grep `check` 在现行 `app.js` 零命中 → B站「已连接」同样是一条不会被核实的死记录。这正是用户「自动检查 B 站和小红书」要补的缺口。
- **「环境自检」是什么**：`app.js:2341-2343` → `GET /environment/check?check_network=false` → `workflows/preflight.py:61-181`，检查归档磁盘空间、FFmpeg、Python、本地 ASR 运行时／模型目录、以及总结／ASR 密钥是否配置。**与平台连接无关**，放在平台连接页属错位；且同一个按钮在平台连接页（`app.js:1660`）和运维页（`app.js:1669`）**重复出现**。
- **确凿 bug**：前端读 `result.healthy`，而 `EnvironmentCheckResponse`（`schemas.py:38-47`）只有 `status: "ok"|"warning"|"error"`，**没有 `healthy` 字段** → `undefined` 恒为假 → 无论环境多好，点下去永远 toast「环境存在待处理项」。这与原话「长期显示环境已有东西」对应（按语音转写理解为「长期显示环境有待处理项」）。同时它只 toast 一句话，不展示具体检查项，用户无法判断是哪项。
- 「将刷新检查连接改为检查连接」按笔误理解为「把『刷新连接状态』改名为『检查连接』」。
- 需用户裁定的分叉：环境自检在**运维页**是否保留。AI 建议「平台连接页删除、运维页保留并修判定」，因为磁盘／FFmpeg／ASR 对任务执行有实际作用；若用户判定整体无用，则两处都删。

## R1

- **状态**：待批准，未实施。
- **现状**：`Program.cs:4007-4010`／`:4572-4589` 把「没抓到分页响应」直接当原因返回；`app.js:610-611` 丢弃 `status`，三处 catch 不回写连接记录 → 原图01 与原图03 互相矛盾。
- **原因**：失败路径只传 message、不传判定结果；连接记录只由 `check_session`／`open_login` 写，扫描失败不写。
- **方案**：
  1. `ScanFavoritesAsync` 的 `page == null` 分支先区分：登录墙／匿名 → 未登录；可见验证入口 → 需人工验证（已有）；其余 → 已登录但收藏业务响应未捕获。三者返回各自 `status` 与简短原因（不描述内部实现）。
  2. `requestDesktopShell` 在 reject 时把 `result` 挂到 error 上；三个 `startXhs*` 的 catch 中，若 `error.result.status` 属连接类状态，调 `saveXhsSession(result)` 写回 DB 并 `refresh("connections")`，让设置页与导入结果一致。
  3. 弹窗错误态继续展示 `state.message`（现有 `renderAccountImport`），不改版式。
- **验收**：自动 — 源码契约断言覆盖「失败回写」「三分支原因」、`node --check`、`dotnet build`、定向 pytest。人工 — 真实账号复现失败后，弹窗给出可判断原因，设置页状态与原因同步，不再出现「已连接」却导入失败且无说明。

## R2

- **状态**：待批准，未实施。
- **现状**：`Program.cs:1775-1780` `open_login` 无回执；`:4534-4548` 窗口内「重新检查」丢弃结果；`:1931-1950` 关闭窗口才重跑整套 `CheckSessionAsync()`（`:3825` 多段 12 秒串行、`_checkGate` 无超时）；`app.js:2325-2328` 固定 toast「连接状态已更新」。
- **原因**：登录窗口与产品前端之间没有同步回执通道，唯一回执挂在「关闭窗口后重新检查」这一慢路径上。
- **方案**：
  1. `XhsLoginForm` 缓存最近一次 `CheckSessionAsync` 结果；窗口内「重新检查」拿到结果后，若 `_pendingLoginRequestId` 存在，立即 `SendProductMessage` 回传并清空 pending（通过既有事件／回调，不新增消息类型）。
  2. `OnXhsLoginUserRequestedClose` 优先回传缓存结果，不再重跑整套检查；无缓存时才跑一次（`check_session` 保持可手动触发）。
  3. `app.js` 的 `conn-toggle` 发起 `open_login` 后立刻把连接行置为「核实中」（不再显示「未连接」）；收到 result → `saveXhsSession` → `refresh` → 渲染；toast 按 `result.status` 给明确结果。
  4. 状态更新路径**不调用** `scan_favorites`、不 `Show` 壳窗口；壳窗口只在用户主动导入时出现。
- **验收**：自动 — 契约断言覆盖「窗口内检查回传」「关闭优先用缓存」「核实中占位」「状态更新不触发扫描」、`node --check`、`dotnet build`。人工 — 打开连接看到已登录账号后退出，设置页立即给出核实结果且可直接导入，不再先显示未连接、不再延迟突变、不再弹新窗口重跑任务。

## R3

- **状态**：待批准，未实施；含一个待用户裁定的分叉。
- **现状**：`app.js:1655`（小红书「检查连接」）、`:1659`（「刷新连接状态」，只读 DB）、`:1660` 与 `:1669`（两处「环境自检」）四个入口职责重叠／错位；`:2342` 读不存在的 `healthy`，恒报「环境存在待处理项」；B站 `POST /check` 从未被调用（`app.js:2327` 只调 `/connect`，而 `main.py:4736-4737` 对 bilibili 直接返回 409「B站请使用二维码登录」，即 B站「连接」按钮本身也是失效入口）。
- **原因**：「刷新」被当成「检查」命名，但实现只重画页面；环境自检被放到平台连接页，且前端字段与响应模型不匹配。
- **方案**：
  1. 删掉小红书行内「检查连接」（`app.js:1655` 及 `conn-verify` case）。
  2. `app.js:1659` 的「刷新连接状态」改为「检查连接」：执行 B站 `POST /platform-connections/bilibili/check` + 小红书壳 `check_session` + `saveXhsSession`，完成后统一 `refresh("connections")` 并渲染；结果按平台分别呈现，不做全局成功／失败的笼统提示。
  3. 平台连接页删「环境自检」；运维页保留，判定改为 `result.status === "ok"`，并展示具体待处理项（不新增说明性文案）。**若用户裁定环境自检整体无用，则两处都删**。
- **验收**：自动 — 契约断言覆盖「按钮数量」「全局检查调用两个平台」「不再出现 `healthy`」、`node --check`、定向 pytest。人工 — 点一次「检查连接」，B站与小红书状态都被真实核实并即时显示；平台连接页不再出现误导性的环境提示。
