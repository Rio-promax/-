## 产品问题

### 产品问题 1：a=true 会随资料量线性失控

**用户原话区（逐字）**

> 禁用a=true的逻辑，未来知识库数量增大，这个绝对不行。

> 这里的 a 等于 true 能不能直接删除啊？

**AI 解释区**

`a=true`（用户说了"全部/所有/每个"）会让 `_validate_route:2472` 把整句问题塞进 `semantic_conditions`，然后 `rag.py:669` 进入 `scan_contents_semantically`，对**每条内容单独调用一次模型**判断是否命中。

实测代码事实（`rag.py:1945-1984`）：

| 项 | 值 |
| --- | --- |
| 每条输入上限 | 8000 字节 |
| 每条输出上限 | 1200 token |
| 单条一次模型调用 | 是（`items` 数组内只放 1 条） |
| 硬性中断 | `batch_calls >= 5` 即暂停（1946 行） |
| 总时长上限 | 58 秒（1946 行） |

所以 34 条资料的实际表现不是"跑 34 次"，而是**跑 5 条就停，返回 `status="paused"`，要用户点 7 次继续**。资料到 1000 条时需 200 轮交互，且期间任何中断都会让已扫描部分作废。

**能否直接删除**：能，但涉及 7 处，不是删一行：

| 位置 | 内容 | 处置 |
| --- | --- | --- |
| `rag.py:42` | schema `required: ["t","g","a","s","f"]` | 移除 `"a"` |
| `rag.py:46` | `"a": {"type": "boolean"}` | 删除该属性 |
| `rag.py:2431` | `_strict_keys(route, {...})` | 移除 `"a"` |
| `rag.py:2437-2438` | `a` 类型校验 | 删除 |
| `rag.py:2469` | `completeness = "all" if route["a"] else "sample"` | 改为恒 `"sample"`，或整个字段移除 |
| `rag.py:2472-2473` | 生成 `semantic_conditions` | 删除，恒为 `[]` |
| `rag.py:669-681` | 消费 `completeness`/`semantic_conditions` 的分支 | 整段删除 |
| `_ROUTE_RULES` 约 128-129 行 | "a 只表示是否要穷尽当前范围…" | 删除该句 |

**风险**：契约测试与 `route` 结构快照可能引用 `a`/`completeness`，须同步改测试。

### 产品问题 2：代码代选工具，语义在翻译中丢失两次

**用户原话区（逐字）**

> 推理代码选择工具和模型选择工具有什么不同，最终达到的效果都是根据用户的输入来判断下一步做什么。

> 那可以选择就选择电用工具这一栏，电用工具的话不仅是之前的技术。罗列还有证据层检索、内容层检索以及图表的检索，最初的预想它不是有个轻量化关系图表吗？有很多东西可以从轻量化关系图表中获得一些范围。

**AI 解释区**

最终效果相同（都是按用户输入决定下一步），差别在**判断时手里有多少信息**：

| | 判断依据 | 压缩次数 |
| --- | --- | --- |
| 现状 | `route["granularity"]` 字符串 | 语义 → 字段 → 动作，两次 |
| 工具化 | 用户原话 + 工具描述 | 语义 → 动作，一次 |

代码层并非在"判断"，它在执行一个**早已判好的结论**——真正的判断发生在 P-ROUTE 那一次调用里。代码只是把 `"detail"` 翻译成 `search_original`。翻译时会丢信息：用户说"谁说过这句话"，"谁"在变成 `detail` 时就不见了。

**产品已有的工具层（已核实，9 个全部实现）**：

| 工具 | 能力 | 当前调度 |
| --- | --- | --- |
| `inspect_scope` | 范围与规模 | 代码 |
| `resolve_catalog` | 主题/细标签解析 | 代码 |
| `query_contents` | 结构化筛选（媒体/平台/作者/时间/主题/标签） | 代码 |
| `expand_content_links` | 内容关联扩展 | **0 调用点** |
| `search_summaries` | 摘要层混合检索 | 代码 + 模型补查 |
| `search_original` | 原文/字幕层检索 | 代码 + 模型补查 |
| `read_chunks` | 按块读取 | **0 调用点** |
| `scan_contents_semantically` | 逐条语义扫描（即 a=true 那条） | 代码 |
| `compute_result` | 计数 / 列表 / 分组计数 | 代码 |

另：`rag.py:132` 定义了 `_TOOL_NAMES`（九工具名整串），**全项目零使用**——曾计划把工具交给模型但未走通。

**关于"轻量化关系图表"**：已存在，但性质与预期不同。

| 项 | 事实 |
| --- | --- |
| 后端 | `rag_store.graph_view()`，接口 `GET /api/v1/dev/rag/graph`（`include_in_schema=False`） |
| 前端 | `dev-rag.js` 完整实现了查询、分页、关系覆盖统计、节点/边渲染 |
| 节点 | content + 属性节点（主题 topic / 细标签 detail_tag / 收藏夹 / 用户标签） |
| 边 | content → 属性 |
| 性质 | **内容-属性关系投影，不是内容-内容语义关联** |

所以它能回答"哪些内容属于人工智能主题""哪些内容在同一收藏夹"，**不能**回答"哪些内容提到西红柿"。它适合用来**缩小范围**（先按主题/标签把 34 条收到 5 条再检索），不适合替代语义检索。

当前状态：**只在开发调试页可用，问答链路完全没有调用它**。

### 产品问题 3：语义同义命中（西红柿 / 番茄）

**用户原话区（逐字）**

> 如果用代码作为调用工具的话就有个问题比如用户问西红柿，但是实际上标题是番茄，这种语义型好像无法进行命中，比如他说内容库中有西红柿的文章有几个。那就是工具数量不够这种该如何来进行解决，以及轻量化图表如何加快这个简化流程减轻检索的负重，本产品的工具参数是写死的，这个或许可以修改一下。

**AI 解释区**

事实确认：`count` 分支走 `compute_result` / `query_contents`，两者都是 **SQL 精确筛选**，确实无法处理同义词。当前只有一条同义词通道：`_retrieval_query_aliases`（`rag.py:136`）——里面**硬编码了且仅有一条规则**：`RAG` ↔ `检索增强生成`。

即：产品对同义词的全部处理能力，是代码里写死的一个特例。

三种解法，成本与覆盖度递增：

| 方案 | 做法 | 延迟 | 覆盖 | 依赖 |
| --- | --- | --- | --- | --- |
| A 别名表 | 维护 `番茄↔西红柿` 等词表，计数前先扩词 | 0ms | 仅收录过的词 | 人工维护 |
| B 主题/标签收窄 | 先用 `resolve_catalog` 把范围缩到相关主题，再计数 | ~10ms | 粗粒度，不解决词级同义 | 现有能力 |
| C embedding 扩词 | 把候选标题/标签向量化，与问题向量比相似度，命中则纳入计数 | ~1.2s（可复用查询向量） | 覆盖未登录词 | 现有 embedding |

推荐 **C 为主、A 兜底**：C 复用已有的 `embed_query` 结果，不需要新依赖；A 用来锁定高频专有名词（比如产品名、缩写），避免相似度抖动。

**"工具参数写死"这条**：属实。`_deterministic_actions` 里 `query` 固定为 `question`、`content_set_id` 固定为范围句柄、`top_k` 取自预算常量。改成模型填参数后，`query` 就可以是模型改写过的检索式（例如把"西红柿"改写成"西红柿 番茄"），这恰好是方案 A/C 的另一种实现路径。

### 产品问题 4：重排代码完整，但从未启用

**用户原话区（逐字）**

> 这里的重排看上去就是设置失败了。我们需要更详细地对其作为做一个计划。

**AI 解释区**

不是设置失败，是**默认关闭且调用方从未传参**：

| 证据 | 位置 |
| --- | --- |
| `search_hybrid(..., rerank: bool = False)` | `ask_index.py:1397` |
| 调用点未传 `rerank` | `rag.py:2186-2191` |
| 每次 trace 都记 `{"status": "not_executed", "reason": "disabled_by_default"}` | `rag.py:491` |
| 重排模型已配好 | `siliconflow_retrieval.py:13` = `Qwen/Qwen3-Reranker-8B` |
| 后端暴露 `rerank_default_enabled: False` | `main.py:4503` |

当前实际排序是 **RRF**（`ask_index.py:1424`，`1.0/(60+rank)`）——只看两路各自排第几，**完全不读文档内容**。

**为什么不能直接打开**：`search_hybrid` 在 `ask_index.py:1404` 把 `candidate_limit` 设为 `max(20, limit*4)`，按当前 `top_k`（24~36）算是 **96~144 条**，全部送 8B cross-encoder 逐对打分，延迟会从 8 秒涨到 11 秒以上。必须先裁候选。

质量收益（公开基准）：`Qwen3-Reranker-8B` 的 CMTEB-R 为 77.45，`Qwen3-Embedding-8B` 的 C-MTEB 为 73.84，**高 3.6 分**。

### 产品问题 5：查询向量化与路由串行

**用户原话区（逐字）**

> 向量化可以进行并行，就是问题的向量化

**AI 解释区**

位置：`rag.py:1244-1269`，`_search_layers` 开头，检索之前串行执行。向量化输入是用户原话（`_deterministic_actions` 写死 `"query": question`），**不依赖路由结果**，可与 P-ROUTE 同时发出。

实测收益：向量化单次约 1.2 秒。代价：`count` 类问题（`metadata` 粒度）不检索，会白算一次向量，费用可忽略（约 ¥0.0002）。

### 产品问题 6：embedding 未使用 instruction 前缀

**用户原话区（逐字）**

> 这里 instruction 前缀感觉可以用一下。

**AI 解释区**

`siliconflow_retrieval.py:51` 的请求体只有 `model / input / dimensions`，没有指令。而 `embed_query`（78 行）就是 `embed_documents([query])[0]`——query 与文档用完全相同的方式嵌入，没有任何区分。

Qwen3 官方说明：该系列是 instruction-aware，query 侧前置任务描述可提升 1~5%，且**指令用英文写效果最好**。

**代价（必须算清）**：改动会导致已存向量全部失效，必须全量重建。当前库规模：

| 项 | 值 |
| --- | --- |
| 索引块总数 | 36682 |
| 内容数 | 34 条 indexed / 3 条 deleted |
| 索引 profile | 6 个（3 个 fts5 + 3 个 vec，成对） |
| 单 profile 块数 | 890 / 8569 / 8882 |
| 需要重算的向量 | 约 18341 条（按 vec profile 合计） |

按 embed batch 32 计约 573 次 API 调用；按 34 条内容重算则更快。**这是本轮唯一会触及索引重建的改动**。

**附带发现**：3 个 profile 并存，说明历史上至少切换过两次索引配置，旧 profile 未被清理。建议在重建前先确认哪一个在生效。

### 产品问题 7：翻译成英文是否值得

**用户原话区（逐字）**

> 第一，这里我指我我说的翻译。还可以走 JEV 和阿里云的两个，这样的话收益够不够多，但是如果翻译成英文的话和后续中文文案的 embedding 会不会有影响？

**AI 解释区**

结论：**不划算，且有损。**

| 项 | 事实 |
| --- | --- |
| embedding 模型 | `Qwen/Qwen3-Embedding-8B`（`siliconflow_retrieval.py:12`） |
| MTEB 英文 | 75.22 |
| C-MTEB 中文 | 73.84 |
| 中文与英文差距 | **1.4 分**，不是 20~30% |
| 跨语言能力 | 支持 100+ 语言同空间，但跨语言检索有精度损耗 |

文档是中文的。把中文问题翻成英文去检索中文文档，等于主动制造跨语言错配。同时多一次模型调用（+0.5~1 秒），且翻译本身可能引入偏差。

**若一定要走英文**：只在路由侧（Jev 的工具描述用英文），检索侧保持中文。两件事要分开，不能一起翻。

## R1：删除 a=true

**状态**：已实施（2026-11-02）

**现状**：`a=true` 触发逐条模型扫描，最多 5 次后暂停，34 条需 7 轮交互。

**原因**：该路径为"穷尽枚举"设计，成本随资料量线性增长，与"知识库会变大"的产品方向冲突。

**方案**：

1. 移除 schema 中 `a`（`rag.py:42`、`:46`）
2. 移除 `_strict_keys` 与类型校验中的 `a`（`:2431`、`:2437-2438`）
3. `completeness` 恒为 `"sample"`，或整体移除该字段
4. `semantic_conditions` 恒为 `[]`（`:2472-2473`）
5. 删除消费分支（`:669-681`）
6. 删除 `_ROUTE_RULES` 中关于 `a` 的说明（约 128-129 行）
7. 同步更新引用 `a` / `completeness` 的测试

**保留**：`scan_contents_semantically` 工具本身不删，只是问答链路不再自动触发；未来若做"用户手动确认的范围扫描"可复用。

**验收**：问"列出所有提到 X 的资料"，不再返回 `paused`，走正常混合检索；`grep` 代码中不再有 `route["a"]` 读取。

## R2：查询向量化与路由并行

**状态**：待授权

**现状**：`rag.py:1244-1269` 在路由返回后才开始向量化，串行。

**方案**：

1. P-ROUTE 发起的同一时刻，用用户原话发起 `embed_query`
2. 路由返回后若动作含 `search_*`，复用该向量；若为 `count`/`metadata`，丢弃
3. 保证取消信号能同时中断两者，异常需合并上报（不能因为向量失败就吞掉路由结果）

**验收**：trace 中 `embedding_calls` 与 `calls`（P-ROUTE）时间区间重叠；总耗时下降约 1 秒。

## R3：重排启用

**状态**：待授权

**现状**：`rerank` 参数存在但调用方不传，排序仅靠 RRF。

**方案（分三步，必须按序）**：

1. **裁候选**：`execute_tool` 调用 `search_hybrid` 时把送重排的候选限制到 20~30 条（当前是 `limit*4` 即 96~144）
2. **打开开关**：传 `rerank=True`，并给 `search_hybrid` 增加独立参数 `rerank_limit`，把"召回候选数"与"送排条数"解耦
3. **实测校准**：同一批问题在开/关重排下各跑一轮，比较引用命中率与耗时，确定 `rerank_limit` 的最优值

**必须验证的风险**：`siliconflow_retrieval.py:1438-1445` 拿到 `ranking` 后直接 `[:limit]` 切片，**未按 score 排序**。若硅基流动返回顺序非降序，结果会错。R3 必须补一次显式排序。

**验收**：trace 中 `rerank.status` 为 `executed`（不再是 `not_executed`）；同一问题的引用相关性人工抽查有提升；总耗时增幅不超过 0.6 秒。

## R4：embedding instruction 前缀
