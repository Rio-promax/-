## 产品问题

### 产品问题 1 · 问答检索这个配置看不懂

**用户原话区（逐字）**

> 图一这个是什么意思，是需要进行什么的配置，说明不清

**AI 解释区**

图一那个 tab 配的是**检索用的向量模型**，不是回答用的对话模型——这是产品里最容易混的一对：

| tab | 配什么 | 干什么 |
|---|---|---|
| 回答模型 | 对话模型（任意 OpenAI 兼容） | 拿到检索结果后组织语言回答你 |
| **问答检索** | 硅基流动的 embedding + rerank | 把你的 34 条归档切成块，转成 1024 维向量存进本地 `sqlite-vec`，让"回答模型"能找到依据 |

所以它只在保存那一刻工作一次（给已有归档重建索引），之后每次问答调用它做检索。**不填的后果不是"问答变慢"，而是问答直接报「未配置硅基流动 API Key」不可用。**

界面上现在只有「硅基流动 API 密钥」七个字，用户既不知道这是干什么的，也不知道不填会怎样。这不是文案啰嗦的问题，是**缺状态位**。

### 产品问题 2 · 跳到 B 站以后回不来

**用户原话区（逐字）**

> 图二是从产品跳转到 B 站之后的页面存在跳转之后无法返回，点点返回就直接返，退出到了这个软件，没办法返回到正常的页面

**AI 解释区**

两个独立缺陷叠加，缺一个都不会这样：

1. **壳没有返回键逻辑**。Capacitor 8 的 `BridgeActivity` 不处理 `onBackPressed`，`MainActivity` 也没补。任何页面按返回 = 关掉整个 App，连"从设置退回内容接入"都做不到。
2. **B 站链接被塞进壳里打开**。`allowNavigation` 白名单把 `*.bilibili.com` 圈进来了，于是点链接是把 B 站 H5 加载进同一个 WebView，产品页被顶掉。图二那个页面带「打开App」按钮，正是 H5，不是 B 站 App。

按用户裁决 A：B 站这类链接一律**交系统外部打开**，壳的 WebView 原地不动。返回键另外补逻辑，用于产品内部的层级回退。

### 产品问题 3 · 分享流程简陋到不能用

**用户原话区（逐字）**

> 然后从 B 站分享到产品的流程 AI 过于简陋，返回显示已纳入队列之后就直接退出了。这是不符合规定规则的，应该纳入之后先是有一个符合产品页面的弹窗，显示正在保存中，然后保存成功之后会显示，然后下面就会提供两个，是第一是停留在产品，第二个是返回 B 站

**AI 解释区**

现在的 `ShareReceiverActivity` 是一张**独立白底 Activity**，跟产品主题毫无关系，而且拿到结果后 `AUTO_CLOSE_DELAY_MS = 2500` 自动 `finish()`——用户看到「已纳入队列」的同时它已经在关了，连点按钮的机会都不存在。

用户要的是一条完整的状态机：**保存中 → 成功 → 两个出口（留在产品 / 返回 B 站）**。归属明确：这是壳的职责，不改服务端。

### 产品问题 4 · 手机端忽略了顶部状态栏

**用户原话区（逐字）**

> 3，就像图一一样在设计手机端前端 UI 的时候忽略了手机的上方状态栏

**AI 解释区**

`index.html:5` 开了 `viewport-fit=cover`，但 `style.css` 里 `env(safe-area-inset-top)` 一次都没用。底部做了（`:4573`、`:4604` 两处 `safe-area-inset-bottom`），顶部漏了。

Android 15 起强制 edge-to-edge，所以不是"某台手机上偶发"，而是**所有 15+ 设备必然顶进状态栏**。图一「设置」标题与时间日期几乎重叠就是这个。

### 产品问题 5 · 手机端仍有大量 UI 不适配

**用户原话区（逐字）**

> 第四，手机端依旧存在大量的 UI 不适配的情况进行核实检查

**AI 解释区**

图一已经暴露一处确定的：设置页 7 个标签在 360dp 宽度下横向滚动，首尾必被裁。10-27 / 10-30 两轮改造只覆盖了知识库页与底部导航，**设置页、任务页、问答页从未按手机宽度校过**。

本轮先修确定项，同时把"逐页核查"单列为 R6，产出清单不直接改——因为核查本身要占一整轮，混进来会让这轮的验收不可判。

## R1 返回键接管与应用内逐级返回

**状态**：已实施

### 现状

`MainActivity.java`（140 行）与 `BridgeActivity`（Capacitor 8.6.0）均未重写返回键处理。结果：任何页面按返回 → `finish()` → 整个 App 关闭。

### 原因

壳工程直接继承 `BridgeActivity` 而没有补返回键。Capacitor 把"返回"完全交给宿主应用决定，宿主没决定，就是默认关掉。

### 方案

| 项 | 设计 |
|---|---|
| 壳侧 | `MainActivity` 用 `getOnBackPressedDispatcher().addCallback(...)` 注册（不重写已废弃的 `onBackPressed()`） |
| 判定顺序 | 先问前端 `window.__kbBack()`；前端返回 `"handled"` → 已回退一级，什么都不做 |
| 前端返回 `"root"` | 当前已在根视图 → 壳显示「再按一次退出」Toast，2 秒内再按才 `finish()` |
| 前端未就绪 | `evaluateJavascript` 回调为 `null` / 异常 → 直接按根视图处理（避免白屏死锁） |
| 前端侧 | `app.js` 新增 `window.__kbBack`，按 `state.currentView` 决定退到哪一级 |

前端逐级规则：

| 当前视图 | 退到 |
|---|---|
| `settings` | `state.settingsReturnView`（沿用既有字段，`app.js:7234` 同源） |
| `result` | `state.returnContext.sourceView`，无上下文则 `history` |
| `batch-detail` | `history` |
| `intake` / `tasks` / `history` / `ask` | 返回 `"root"` |

### 验收

**自动**

1. `index.html` + `app.js` 语法检查通过（`node --check app.js`）
2. 契约测试：`window.__kbBack` 存在且对 6 种 `currentView` 返回预期值（新增 `tests/test_1101_mobile_back_contract.py`，读源码文本断言）

**人工（1/0）**

1. 设置页按返回 → 回到内容接入，不退出 App
2. 详情页按返回 → 回到知识库列表
3. 在知识库再按一次返回 → 出现「再按一次退出」，第二次才退出
4. 手机上点 B 站链接 → 打开 B 站 App（或浏览器），产品页仍在原处

## R2 外链出壳

**状态**：已实施

### 现状

`capacitor.config.json` 的 `allowNavigation` 含 `*.bilibili.com` / `*.zhihu.com` / `*.xiaohongshu.com`，链接被 WebView 内部加载。

### 原因

这三个域名当初进白名单的理由是"让用户能在壳里看原页"，实际证明是错的：B 站 H5 在 WebView 内不能登录、播放器多半不可用，还把产品页顶掉。

### 方案

| 项 | 设计 |
|---|---|
| 壳侧 | `ShellWebViewClient.shouldOverrideUrlLoading`：`http(s)` 且 host 不是产品域名 → `Intent.ACTION_VIEW` 交系统，返回 `true` 吞掉在壳内的加载 |
| 产品域名 | 取 `ShellConfig.SERVER_ORIGIN` 的 host，不新增常量 |
| 非 http(s) | 保持既有行为（`kb-shell://` 命令拦截；其余交 `super`） |
| 配置 | `capacitor.config.json` 的 `allowNavigation` 清空为 `[]` —— 白名单在这里已无意义，壳只认产品域名 |
| `onReceivedError` 边界 | 出壳后的失败不会进壳的 WebView，错误页只对产品自身加载失败生效 |

### 验收

**人工（1/0）**

1. 知识库点 B 站链接 → 跳出到 B 站 App；按返回 → 产品仍停在知识库那一屏
2. 知乎 / 小红书链接同样出壳
3. 产品自身页面（同域名）仍在壳内正常跳转，不误跳外部

## R3 分享结果弹窗

**状态**：已实施

### 现状

`ShareReceiverActivity`：白底独立页，`AUTO_CLOSE_DELAY_MS = 2500` 自动关闭。

### 原因

按"能用就行"写的，没做产品化。

### 方案

| 项 | 设计 |
|---|---|
| 形态 | 改成**对话框式 Activity**：`Theme.AppCompat.Dialog` 派生主题 + 圆角卡片 + 半透明遮罩，不再是全屏白底 |
| 配色 | 直接对齐产品白天主题：底 `#fffaf0`、边 `#c8a47a`、正文 `#2d2019`、次要 `#6b5744`、主按钮 `#b76d2d`（取自 `style.css:5174` 起的 `--theme-*`） |
| 状态机 | `保存中`（进度条 + 链接）→ `已加入队列`（可补一句取回提示）→ 失败（显示原因） |
| 出口 | 成功后两个按钮：**留在产品**（启动 `MainActivity`）/ **返回 B 站**（`finish()` 回来源 App） |
| 自动关闭 | **删除** `AUTO_CLOSE_DELAY_MS`，改成用户显式选择 |
| 失败态 | 只留「关闭」一个按钮，不提供"留在产品"（失败时进产品没有意义） |
| 取消 | 弹窗期间按返回 = 留在当前 App 的入口页，不静默丢弃 |

### 验收

**人工（1/0）**

1. B 站分享 → 出现产品风格弹窗，显示「正在保存」
2. 保存成功 → 显示成功文案 + 两个按钮，**不会自己消失**
3. 点「留在产品」→ 进入 App 并停在内容接入
4. 点「返回 B 站」→ 回到 B 站 App
5. 服务器不可达时 → 显示失败原因 + 关闭按钮

## R7 云端分发 APK

**状态**：已实施（2026-11-01 23:0x）

### 现状

- 服务器无任何 `.apk`（`find ~ -name '*.apk'` 为空），壳无版本检查，`versionCode` 仍为 1。
- 后果：壳层改动只能靠数据线 `adb` 或微信传文件，用户每次都要在电脑上找包。
- 页面层不受影响：壳加载 `server.url`，`/`、`/ui` 路由带 `Cache-Control: no-store`，改完刷新即生效，不必换包。

### 原因

只做了「壳 + 云端页面」这一层，缺「壳自身的分发渠道」。与代码无关，属于部署缺口。

### 方案

- nginx `:8080` 增 `location /download/`：`alias /var/www/kb-download/`、`default_type application/vnd.android.package-archive`、`Content-Disposition: attachment`。
- 沿用 server 级 `auth_basic`，下载点不额外开公开通道。
- 目录 `/var/www/kb-download` 属 `www-data`；不用家目录，因为 `/home/ubuntu` 为 `750`，`www-data` 无法穿越。
- 链接固定：`http://123.206.227.238:8080/download/multisourcekb.apk`。发新包覆盖同名文件，链接不变。
- 不做：应用内自动更新（需 `REQUEST_INSTALL_PACKAGES` + FileProvider + 版本接口），壳改动频繁期性价比低。

### 验收

- `nginx -t` 通过，`nginx -T` 含该 location（已通过）
- 服务器 APK md5 `d9b8548d50eccd588afeb4111ac5fe44` 与本地一致（已通过）
- 无凭据请求返回 `401` + `WWW-Authenticate: Basic`（已通过）
- 手机浏览器带凭据下载 → 安装成功（待人工）
