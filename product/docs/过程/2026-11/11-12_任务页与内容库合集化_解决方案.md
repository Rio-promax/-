**AI 解释区**

前两点已由裁定 C、裁定 D 落定，本轮按该版本实施；第三点按用户要求**不新增网络重试或登录阻断功能**，只在 R6 用已有 `error_code` / `error_message` / `recovery_suggestion` 显示真实原因，不用笼统文案。

只读侦察（`main` @ `fe7c3a0`，`/api/v1/jobs` 实测 79 条）得到的事实：

- **父子数据原本不存在**：`JobResponse` 只有 `batch_id`（`import_batch_id`）、`batch_item_number`、`batch_total`，前端一次都没读过；`/jobs` 实测 6 个批次，最大一批 50 条且序号 1–15 重复 3 轮 —— 重试任务继承了原批次号，直接按批次聚合会让 15 条视频显示成 50 行。这是裁定 B 要求「合集优先 + 批次回退 + 重试去重」的直接原因。
- **合集信息在扫描阶段存在、在提交阶段丢失**：`enumerate_season_videos` 返回 `season_videos / season_total / season_title`，扫描记录带 `season_id`，但 `confirm_scan_import` 只把 url 交给 `confirm_link_query`，`job.metadata` 里没有任何合集字段。本轮补这条传递链。
- **阶段与进度数据已具备**：`GET /api/v1/jobs/{job_id}/events` 返回 `stage / state / progress / message / occurred_at`，`JobResponse` 另有 `progress / checkpoint / last_stage / resume_stage`。R6 只做展示，不新增采集。
- **总结配置后端已就绪、前端全是非法值**：合法风格为 `general, course_notes, academic, tutorial, sharing, task_oriented, business, meeting_minutes`，合法强度为 `quick, standard, deep`；`index.html` 当前写的是 `concise / detailed / examples` 与 `brief / standard / deep`，且 `intakeSubmit` **根本不读取这两个 select**，所以配置一直是默认值。R8 是「接上真值」而不是新增能力。
- **重新总结接口本就支持配置**：`POST /api/v1/contents/{id}/resummarize` 接受 `summary_style` 与 `strength`；前端 `doc-regenerate` 现在直接发空 body。R5 只需补弹窗与传参。
- **内容详情来源卡是 `<a target="_blank">`**：在桌面壳内点开可能落回壳内导航。R13 改由系统默认浏览器打开，失败时给反馈并复用已有复制能力。

## 统一范围与实施顺序

**范围**：上表 R1～R13 全部实现。**不做**：网络重试与登录阻断的新增机制；`_legacy/` 下任何代码；`app/domain/jobs.py` 状态机；`app/db/models.py` 表结构；`Program.cs` 与小红书收藏夹相关未提交改动；不新增持久化设置（不得引入 `localStorage` / `sessionStorage`，契约测试已断言）。

**合集字段定义（历史口径；当前采用上方最新方案）**

| 字段 | 取值顺序 | 为空时 |
|---|---|---|
| `collection_id` | 历史实现：`season_id` → `import_batch_id`；当前：只来自受信任合集扫描的 `season_id` | 不聚合，任务平铺 |
| `collection_title` | 当前：真实 season 扫描记录中的合集名 | 缺失时前端按实际合集内容数展示 |
| `collection_total` | 当前：真实 season 扫描返回的总数 | 缺失时按实际合集内容数展示 |

**重试去重**：同一合集内按 `content_id`（无则 `source_url`）去重，保留 `created_at` 最新的一条任务；父集完成量分母用 `collection_total`，不用组内条数 —— 避免 15 条视频因重试变成 50 行。合集关系只在可信 season 扫描时建立，并在重复复用、重试、重新总结中继承。

**实施顺序**：M1 后端字段与传递 → M2 任务页（R1/R2/R3/R6/R9/R10）→ M3 内容库与详情（R4/R5/R11/R12/R13）→ M4 内容接入（R7/R8）→ M5 契约、验证、提交与回填。

**任务拆分模式说明**：R1～R13 是同一张任务列表的连续改动，多项共享同一渲染函数，按需求逐条单独提交会互相覆盖。提交按「后端字段」「任务页」「内容库与详情」「内容接入」四个可验证整体切分，每段完成后立即验证。

### M1 后端合集字段

- **状态**：初版已实现；合集定义与导入字段来源按最新方案修正。
- **现状**：`JobResponse` 无合集字段；`confirm_scan_import` 丢掉 `season_id` / `season_title` / `season_total`。
- **原因**：父任务没有稳定聚合键，前端无法区分「一次导入的一批」与「真合集」。
- **方案**：三个 `JobResponse` 合集字段保留；公共 `LinkQueryConfirmRequest` 不接受任意合集字段；只有受信任的 season 扫描向任务写 `season_id`，导入批次独立存为 `batch_id`。
- **验收**：`/jobs` 响应保留三个字段；合集扫描任务 `collection_id == season:<season_id>`；导入批次和多 P 不产生合集字段。

### M2 任务页

- **状态**：实施中。
- **现状**：无排序、无父集、无展开、无阶段进度、无全选；列表高度用 `calc(100vh - 320px)` 硬算；单行暂停写死 `toast("已暂停")`。
- **原因**：v3 重写版只做到六图静态构图，未接任务数据的时间与层级维度。
- **方案**：
  - R1 排序：状态序 `running/switching → failed → waiting → paused → completed → cancelled`；同状态内 `created_at` 降序；`completed` 内按 `completed_at` 降序；排序只影响展示，不发任何执行相关请求。重排后保留列表 `scrollTop`、已展开合集集合、已选任务集合。
  - R2 聚合：按 `collection_id` 聚合，父行状态派生 —— 任一子项 running → 进行中；仍有 waiting → 进行中（不能提前结束）；全部 completed → 已完成；结束态混合成功与失败 → 部分失败；全部 failed → 失败；cancelled 不计入成功。
  - R3 展开：默认 4 条，每次 +4；子项按状态排列、completed 沉底、序号取 `collection_item_number` 或全集原始次序；不足 4 条全部显示；全展开后隐藏「继续展开」。
  - R6 阶段：点开单条任务拉 `/jobs/{id}/events`，按 `stage` 顺序渲染阶段与进度条；父行显示 `已完成 N / 共 M`；等待显示 `recovery_suggestion` 或「排队等待前序任务」；失败停在失败阶段并显示 `error_message`；无 progress 数据不渲染百分比；单行暂停/重试按接口返回的 `state` 显示文案。
  - R9 高度：任务页改为 `height: 100vh` 纵向 flex，`.jobs-list` 用 `flex: 1; min-height: 0` 撑满剩余高度，去掉 `calc(100vh - 320px)`。
  - R10 全选：编辑态标题栏出现「全选 / 取消全选」，范围 = 当前筛选结果；勾父集 → 全集子项选中；子项部分选中 → 父集 `indeterminate`；父行与子行不重复计入 `selectedJobs`。
- **验收**：`node --check` 通过；8765 实测任务页按裁定 C 排序、父集可展开、展开数按 4 递增、编辑态全选覆盖筛选结果并联动、空列表与 79 条时底部无大块留白。
