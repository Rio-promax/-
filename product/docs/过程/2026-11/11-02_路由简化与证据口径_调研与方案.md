## 产品问题 1：回答里不要出现 evidence 原文，只要"出自哪篇文章"

### 用户原话区（逐字）

> 嗯，这一步我不希望它获得什么 evidence 之类的。我只希望它作为参考。就是不要说出 evidence 之类的原话，它只需要告诉用户这个放在，就是它的这个找出的观点是放在哪篇文章中的，也不需要碰到字幕层。

### AI 解释区

**要改的三件事**

| 现状 | 目标 |
| --- | --- |
| 回答必须带 `evidence[].quote`，220 字内逐字原文，与库中文本连续比对 | 回答只带"文章来源"，`content_id` + 标题，不出引文 |
| 校验方式是逐字比对（`quote` 必须能在块文本里连续命中） | 校验方式改为归属校验（回答提到的文章必须在本轮证据集合内） |
| `detail` / `mixed` / `requires_original` 会追加字幕层（`transcript:segment`） | 固定只查摘要层（`summary:paragraph`） |

**这个取舍的真实代价，必须写清楚**

现在的产品可信度全部压在 quote 上：`answer` 是模型自己写的话，可以编；`quote` 是从库里取的原文，编不出来。去掉 quote 之后，模型完全可能写出"《某某文章》提到 X"，而那篇文章根本没提 X——归属校验只能保证"这篇文章在本轮检索结果里"，保证不了"这句话是这篇文章说的"。

这不是不能接受，而是要换一个补偿手段。可选的补偿是：

1. 回答里的每个观点必须挂 `content_id`，前端把它渲染成可点击的"出自《标题》"，用户点进去能自己核对；
2. 生成后做一次"归属一致性检查"：把 `answer` 里出现的文章标题与 `content_id` 集合比对，出现集合外的标题直接降级为 partial；
3. 明确在界面上写"回答基于摘要生成，未逐字核对原文"。

**这一条会连带简化路由**：不碰字幕层之后，`granularity` 的四个值（`metadata`/`broad`/`detail`/`mixed`）里，`detail` 和 `mixed` 失去存在理由，只剩"查摘要层"一种动作。等于路由的第二个维度可以直接删掉。

## 产品问题 2：路由过于复杂、过于细致，导致不准确

### 用户原话区（逐字）

> 然后你审核一下定的路由，感觉路由有一点，第一是过于复杂，第二是过于细致，导致有很多问题，就是不准确。感觉很怪，它分了那么多路由判断，分了那么多的类型但是并不清晰感觉，你从 GitHub 上面搜索十个具有此类路由的 RAG 项目，来学习一下它们的路由是怎么进行写的，优先选择高赞。

### AI 解释区：审核结论（基于源码逐行核对）

#### 结论一：8 个 task 里有两对在代码中完全同构

`lookup`、`explain`、`relation`、`synthesize` 这四个词在 `rag.py` 里只出现在 5 个位置：schema 枚举（`:44`）、`complex_path`（`:595`）、`simple_path`（`:801`）、校验白名单（`:2432`）、`_retrieval_budget`（`:2620`）。除此之外**没有任何一处区别对待**。

于是实际形态是：

| task | 实际行为 | 与谁相同 |
| --- | --- | --- |
| `lookup` | 简单路径：20 秒 / 6000B / 2 次调用 | **与 `explain` 完全一致** |
| `explain` | 简单路径：同上 | **与 `lookup` 完全一致** |
| `synthesize` | 复杂路径：45 秒 / 10000B / 3 次调用 | **与 `relation` 完全一致** |
| `relation` | 复杂路径：同上 | **与 `synthesize` 完全一致** |
| `compare` | 保护指定对象；>6 项暂停 | 独立 |
| `enumerate` | 列清单 / 逐条扫描 | 独立 |
| `count` | SQL 计数 | 独立 |
| `clarify` | 直接反问 | 独立 |

也就是说，模型在 `lookup` 和 `explain` 之间做的那次纠结，**对系统没有任何影响**；`synthesize` 和 `relation` 之间同理。这不是"细致"，这是模型在被要求做一个无意义的区分——而做无意义的区分会挤占它做有意义判断的注意力。

#### 结论二：4 个 granularity 只产生 2 种动作

`_deterministic_actions`（`:1209`）的判断是：

- `metadata`、`broad`、`mixed` → 查摘要层
- `detail`、`mixed` → 查原文层
- 兜底 → 查摘要层

所以 `broad` 和 `metadata` 在动作层面**完全相同**，`detail` 和 `mixed` 的唯一区别是前者不查摘要层。四个值实际只是"要不要原文层"的一个布尔。而在用户的新口径下（不碰字幕层），这个布尔恒为 false —— 整个维度归零。

#### 结论三：64 种组合最终只消费 6 条分支 + 3 组预算

理论上 `t`(8) × `g`(4) × `a`(2) = 64 种。实际消费方：

- 分支：`clarify` / `count+metadata` / `enumerate+metadata` / `completeness=all` 且非 metadata / `compare>6` / 其余
- 预算：`_retrieval_budget` 只有 3 档（复杂 / 枚举或原文 / 默认）

**分类维度远大于消费维度**，这是用户"感觉很怪"的直接来源。系统只需要知道"走哪条路"，却先被要求回答"这是什么类型的问题"。

#### 结论四：`a`（是否穷尽）的代价被藏起来了

`completeness=all` 且 `granularity != metadata` 时，`_validate_route`（`:2472`）会把**整个问题的原话**塞进 `semantic_conditions`，随后触发 `scan_contents_semantically`——把 34 条内容**逐条**送模型判断，batch_size 10，这是全系统最贵的一条路径。

而它的触发条件只是用户在问句里说了"全部""所有""每个"。让模型从两个字推断"要花 34 次模型调用"，风险收益完全不对等。这类决定应该由用户显式做（一个"扫描全部内容"的开关），或者由代码在检索命中不足时自行升级。

#### 结论五：规则 prompt 已经在打补丁

`_ROUTE_RULES`（`:124`）1121 字节的自然语言里，已经出现"RAG 不是人工智能别名"这种**针对具体失败案例的补丁**。规则越补越长，模型越容易顾此失彼——这是在用 prompt 修分类体系的设计问题。

### 各项目的具体写法

**dify（问题分类器）**：每个分类只写两样东西——画布上的标题 `class_label`、给模型读的描述 `class_name`（正文）。分几类完全由使用者定，官方示例只有 3 类（售后服务 / 产品使用 / 其他问题），并且**一定有"其他问题"这一类**兜底。分类边界相近时，靠"与……相关""不包括……"这类措辞来区分，而不是增加类别。

**langchain**：`RunnableBranch` 的条件是一个**函数**，不是模型输出。需要模型判断时，才用一次 structured output 拿到枚举值，然后仍由代码分派。LangGraph 同理——条件边是 `add_conditional_edges(state, router_fn)`，`router_fn` 是纯函数、可单测。

**llama_index（RouterQueryEngine）**：这是最值得抄的一个。它**不定义"问题类型"，它定义"有哪些检索器"**：

```python
list_tool = QueryEngineTool.from_defaults(
    query_engine=list_query_engine,
    description="Useful for summarization questions related to the data source",
)
vector_tool = QueryEngineTool.from_defaults(
    query_engine=vector_query_engine,
    description="Useful for retrieving specific context related to the data source",
)
query_engine = RouterQueryEngine(
    selector=PydanticSingleSelector.from_defaults(),
    query_engine_tools=[list_tool, vector_tool],
)
```

选择器收到的是**工具的用途描述**，输出是"选第几个工具"。类别数等于工具数，官方示例就是 2 个。语义是 dispatch，不是 taxonomy。

**haystack（ConditionalRouter）**：路由是一组字典，条件是 Jinja2 字符串，**一行代码不调模型**：

```python
routes = [
    {"condition": "{{ query|length > 10 }}", "output": "{{ query }}",
     "output_name": "ok_query", "output_type": str},
    {"condition": "{{ True }}", "output": "{{ query }}",
     "output_name": "default_route", "output_type": str},   # 显式 fallback
]
```

**semantic-router**：路由是 `Route(name="politics", utterances=[...])`，决策是 embedding 相似度，`fit()` 校准阈值之后，不达标的查询返回 `None`——**"不路由"是一个合法的一等结果**。

**LightRAG / graphrag**：干脆不问模型。`mode`/`search` 是调用方传的参数，系统只提供一个默认值（LightRAG 默认 `mix`）。

### 六个可复用的共性

1. **路由是 dispatch，不是 taxonomy**。输出是"走哪条路"，不是"这问题是什么类型、什么粒度、要不要穷尽"。
2. **类别数 2–5**。没有一个项目是 8 类 × 多维度。
3. **必有兜底**：`{{ True }}`、`None`、`default_route`、"其他问题"。路由失败是预期情况，不是异常。
4. **参数不进路由**：top_k、要不要原文、预算档位，全部由路径内部固定。LightRAG 连 mode 都交给调用方。
5. **能不用模型就不用**：Haystack 用 Jinja2、semantic-router 用 embedding、LightRAG 用参数。只有必须做语义判断时才调模型。
6. **可评估**：semantic-router 有 `fit()` 校准，Adaptive-RAG 报分类准确率。当前项目的路由**没有任何准确率度量**——这是"不准确"这个感受无法被证伪也無法被修复的根本原因。

## 候选方案

### 方案 A：三分类 dispatch（推荐）

路由只回答一个问题：**这次要干什么活**。

```json
{"k": "answer" | "list" | "count", "s": ["可选：拆出的答复点"], "f": ["可选：硬筛选"]}
```

| k | 行为 | 检索 | 是否调模型生成 |
| --- | --- | --- | --- |
| `answer` | 检索摘要层后回答问题，逐观点标文章来源 | 摘要层混合检索 | 是 |
| `list` | 列出命中的资料清单（标题+平台+一句话） | 摘要层，取 top 50 | 轻量 |
| `count` | 计数 | 不检索，走 SQL | 否 |

**删掉的东西**

- `lookup` / `explain` / `synthesize` / `relation` → 全部并入 `answer`（本来就没区别）
- `granularity` → 归零（不碰字幕层，只剩摘要层）
- `completeness(a)` → 删除。改为代码判定：检索命中内容数 < 3 且范围 ≤ 34 时，自动补一次全量摘要扫描；否则不扫
- `clarify` → 从模型类别降级为代码兜底。问题少于 4 字、或检索零命中且无主题线索时，代码返回反问
- `compare` → 并入 `answer`。保护逻辑改为"用户在范围内显式选中 ≥2 项"（`scope.kind == "selected"`），代码可判定，不依赖模型
- `enumerate` → 就是 `list`

**收益**

- 决策空间 64 → 3
- 路由 prompt 从 1121 字节压到约 300 字节
- 路由耗时预计从 ~1.5 秒降到 0.5 秒以内（输出 token 大幅减少）
- 删掉 `a=true` 的隐式全量扫描后，最坏路径从"34 次模型调用"变成"1 次补充扫描"
- 8 个 task 里 4 个纯噪音消失，模型不用再做无意义区分

**风险**

- `compare` 的保护逻辑要重写，依赖 `scope.kind`，需确认前端"选中多项"时确实传 `selected`
- `list` 的 token 预算问题（曾导致 JSON 截断）需要保留现有修复，不能一起删

### 方案 B：零模型路由（最激进，最接近 LightRAG）

完全不调模型做路由：

1. 正则拦截计数类（"多少条/几个/数量/总数"→ `count`）
2. 正则拦截列举类（"哪些/列出/都有什么"→ `list`）
3. 其余全部走 `answer`，统一混合检索摘要层
4. 检索后由**回答阶段**的模型自己决定够不够（现有 `actions` 补查机制已在做这件事）

**收益**：省掉 1.5 秒路由 + 一次调用费，链路少一个失败点。
**风险**：规则拦错了没有退路；"哪些资料提到了 AI 产品经理"这种既像列举又需要语义判断的问题会分错。**不推荐**。

### 方案 C：保留现状但做减法（最小改动）

只做三件不改架构的事：

1. `lookup`/`explain` 合并成 `lookup`，`synthesize`/`relation` 合并成 `synthesize` → task 从 8 降到 6
2. 删掉 `granularity` 的 `detail`/`mixed`（配合不碰字幕层）→ 变成单值
3. 删掉 `a` → 全量扫描改为代码在零命中时触发

**收益**：改动面小，一周内可验证。
**风险**：仍然是"让模型做 taxonomy"，没有解决根本问题，后续还会长回来。

## 推荐

**方案 A**。理由：它是唯一同时满足"决策维度 1 个""类别数 3""有默认分支"这三条业界共性的方案，而且和用户"不碰字幕层"的新口径天然契合（granularity 归零是副产品，不是额外改动）。

方案 C 可以作为 A 的第一步落地（先合并同构类别，验证无回归），再删维度。

## 统一范围与实施顺序

按"先删证据层，再改路由"的顺序，因为删掉字幕层之后路由的 granularity 才有理由归零：

1. **R1 检索层收敛**：`_deterministic_actions` 固定只发 `search_summaries`，`detail`/`mixed`/`requires_original` 不再产生 `search_original`。
