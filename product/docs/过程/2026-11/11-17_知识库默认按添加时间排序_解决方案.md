## 产品问题 2

### 用户原话区（逐字，不许改写）

> 同时在任知识库中内容的排列顺序是什么样子的，为什么新添加的东西反而处在之前添加的东西的后面？默认应该按时间添加顺序的

### AI 解释区

「默认应该按时间添加顺序」结合「新添加的东西反而处在之前添加的东西的后面」，理解为**最新添加的排在最前**（时间倒序），与后端既有默认一致。只读诊断结论：

- **后端默认是对的**：`app/ui/app.js:228` 请求 `/history` 不带参数；`app/api/main.py:4268-4269` 默认 `sort_by=created_at` / `order=desc`；`app/db/store.py:2494-2495` 用 `ContentRow.created_at.desc()`。实测 API 返回 86 行严格时间倒序、零逆序。
- **前端把顺序打断了两处**：① `app.js` 的 `renderLibrary()` 把所有 `groups.collections` 拼在前面、再把所有 `groups.singles` 拼在后面，任何单条新内容都被排到全部合集卡之后；② `libraryGroups()` 把「只有一个成员的降级合集」用 `singles.push(...)` 追加到末尾，破坏了 API 原有的时间顺序。模拟当前数据渲染 74 张卡，存在 **490 / 2701 对时间逆序**。
- **「新添加」与后端口径不是一回事**：11-13 重跑成功的 9 条沿用原 `content_id`，当天新建 content 数为 0，`created_at` 仍是 11-12 14:42，只有 `updated_at` 变成 11-13。按创建时间排，它们落在 11-12 15:50／16:24 那批多 P 内容之后。用户按「刚总结完成」理解，系统按「内容行创建时间」排。
- **折叠副作用**：按 BVID+P 折叠后，重复导入的新 content 不再单独成行；同一 BVID 的多个分 P 收进父集卡，展开前在网格里看不到，也会显得「新东西没出现在前面」。
- **A 只修结构性逆序，不改时间语义**：本轮兑现「严格按 `created_at` 倒序」，但**不会**让 11-13 刚重跑成功的内容跳到最前（它们的 `created_at` 未变）。要那样做是 B 口径，用户未选。这一差别写入验收说明，避免误判为没修好。
- 前端没有可切换的排序控件：`S.libFilters` 只有 `platform / kind / duration / introduction` 四个维度，不含排序。
