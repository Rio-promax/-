## 背景

### 1. 产品目标

把散落在各平台的收藏，变成一处可检索、可复用的个人知识库。

| 层 | 目标 | 当前状态 |
|---|---|---|
| 内容 | B 站 / 知乎 / 小红书 / 抖音的收藏与链接，统一导入，解析成字幕转写 + 总结 + 归档 Markdown | 桌面端已具备（小红书受登录态限制） |
| 使用 | 随时可用，不绑定某台电脑的开机状态 | 能看已达成；能干活未达成 |
| 形态 | 最终是一个装在手机上的软件，不是网页 | 未开始 |
| 分发 | 短期一人自用，长期小范围分发 | 短期方案已定，分发能力未建 |

来源说明：内容层是产品既有定位；使用、形态、分发三层目标来自用户原话，分别见「产品问题 2」「产品问题 5」。

一句取舍贯穿全文：**短期不为多用户做任何事，但凡是"现在改便宜、以后改昂贵"的地方要预留。**

### 2. 产品原本是什么

Windows 本地单用户产品，四件套构成：

- 单进程 FastAPI，`start-product.cmd` 以 `--host 0.0.0.0 --port 8765` 启动（健康检查与桌面壳走 `127.0.0.1`）
- SQLite 单文件，`product/local/knowledge.db`
- 无框架单页前端，`app/ui/index.html` + `app.js` + `style.css`
- WebView2 桌面壳（`product/src/services/desktop-shell`），只为一件事存在：拿平台登录态

数据全在本机。**没有账号、没有权限、没有云、也没有任何"多用户"概念**——`content`、`jobs`、`app_settings` 这些表都没有归属字段，全部数据属于"这台机器"。

### 3. 为什么转向云端

目标里的"随时可用"要求一个不随电脑关机而消失的地址。当前落点：

| 项 | 值 |
|---|---|
| 机器 | 腾讯云轻量应用服务器 · 上海五区 |
| 规格 | 2 核 2GB / 40GB / 3Mbps / 200GB 月流量 |
| 系统 | Ubuntu 24.04.4 / Python 3.12.3 |
| 地址 | `http://123.206.227.238:8080/`（带用户名密码） |
| 到期 | **2026-11-30** |

10-31 夜间已跑通，不再展开：代码与依赖到位、`kb.service` 常驻并开机自启、Nginx `8080` 加密码门且 `8765` 收回本机、103MB 数据库与 2.9MB 归档迁完并改写好 `archive_path`。结果是手机能打开、能看 34 条内容、能点开详情。

### 4. 撞到的墙

一句话：**产品至今假设自己只运行在 Windows 上，密钥存储这一层是硬编码的。**

`app/platforms/secrets.py` 只有 Windows DPAPI 一种实现：

- `:93` `protect_secret` 首行 `if sys.platform != "win32": raise SecretStorageError(...)`
- `:123` `unprotect_secret` 同样

三处调用因此全部失效：`store.py:2048`（`set_secret_setting`）、`:2066`（`set_summary_settings_atomically`）、`:2101-2102`（`save_bilibili_session`）——总结、云 ASR、B 站登录态全都写不进去。

**后果可枚举**：总结、云 ASR、B 站扫码登录，三件事同时不可用；新建任何任务都会失败。这不是配置问题，重装、换 Python 版本都改变不了。

### 5. 因此这一轮要解决什么

不是"再部署一次"，而是让产品不再假设自己是 Windows 桌面。范围要压到最小：**只动密钥存储这一层**（`secrets.py` 的分派、`store.py` 两处前缀判断、`pyproject.toml` 的依赖），其余（抓取链、归档、前端）一律不碰。

## 手机端规划（阶段 0 → 4）

| 阶段 | 目标 | 关键动作 | 依赖 | 当前 |
|---|---|---|---|---|
| 0 能看 | 手机浏览器能打开、能看已有内容 | 云端部署 + 迁移 + 布局 R1/R2 | — | ✅ 已完成 |
| 1 能干活 | 手机上能新建任务、出总结 | **R1 密钥存储跨平台** | — | 未开始 |
| 2 像 App | 桌面图标、全屏、分享菜单能进来 | R3 Capacitor 壳 + ACTION_SEND | R1 | 未开始 |
| 3 稳 | 数据不丢、电脑/服务器换机可恢复 | R2 备份 + HTTPS | — | 未开始 |
| 4 能分发 | 第二个人可以用，数据互不可见 | R4 账号与 owner_id | 阶段 1–3 | 未开始 |

### 每个阶段做完是什么样

- **阶段 1 之后**：手机贴一条 B 站链接 → 出总结 → 详情能打开。产品第一次在手机上"能干活"，而不只是"能看"。
- **阶段 2 之后**：桌面有图标；在小红书/B 站点分享 → 选中「内容知识库」→ 自动建任务。**注意**：分享只递一个 URL，能不能抓到取决于平台，小红书仍然大概率失败（见平台矩阵）。
- **阶段 3 之后**：服务器 11-30 到期、换机器、误删，都能恢复。
- **阶段 4 之后**：可以给别人用。这是唯一需要动数据模型的阶段。

### 形态选择（现在就要定，但不影响 R1/R2）

| 形态 | 开发量 | 分享菜单入口 | 前提 |
|---|---|---|---|
| 手机浏览器 | 0 | 无 | 已具备 |
| PWA（添加到主屏） | 半天 | 无 | **需 HTTPS**，`http://` 下 Chrome 不注册 |
| **APK 壳（推荐）** | 1–2 天 | 有（Android） | Windows 可出包，不需要 Mac |
| 原生 App | 3–6 周 | 有 | 后端上云 + 前端重写 |
| 微信小程序 | 3–4 周 | 微信内分享 | 必须备案域名 + HTTPS，长任务会超时 |

结论：**先 APK 壳**。PWA 看着轻，但在 `http://` 下连安装都触发不了；小程序对长任务抓取是死路。

## 产品问题

### 产品问题 1 · 云端保存不了任何密钥，新建任务必失败

**用户原话区（逐字）**

> 确定失败。可以，先出一轮方案吧，方案中要着重写清楚背景，已有的产品和接下来的手机上要完成的规划

**AI 解释区**

"确定失败"确认的是我在上一轮给出的判断：手机上新建任务一定失败。根因不在抓取链，而在密钥写入被平台判断挡住——`secrets.py:93` 与 `:123` 两行 `if sys.platform != "win32"` 直接抛错。

必须说清一件容易误解的事：**这不是"服务器缺个配置"**。DPAPI 是 Windows 用户账户绑定的，Windows 上加密的那串 `dpapi:` 值，拿到 Linux 上任何办法都解不开。所以修法只能是"给非 Windows 一套自己的加密方式"，而不是"把密钥搬过去"。

### 产品问题 2 · 手机端的最终形态没定，导致后面每一步都可能白做

**用户原话区（逐字）**

> 最终目的为写手机软件，还需要准备什么

**AI 解释区**

形态决定三件事：能不能出现在系统分享菜单、要不要上云、代码能复用多少。三者的分叉见上文"形态选择"。

本轮不建议把它定死到"原生 App"，因为原生 App 的门槛不在 App，而在后端：Python + WebView2 + 归档目录这套东西搬不到手机上。**先做壳，壳能验证"手机上到底要哪几个功能"**，这个信息比提前选技术栈值钱。

### 产品问题 3 · 单机部署没有备份，且服务器 11-30 到期

**用户原话区（逐字）**

> 云端一直开着和一有什么影响吗？然后关于刚刚说的谁都可以进入，能不能加一个密码或者之类的限制？

**AI 解释区**

"一直开着"的真实风险不是电费（包年包月），而是**没有备份**。现在云端是唯一在积累数据的地方，而它只有一个 `knowledge.db` 文件，且 29 天后到期。到期停机、误删、磁盘故障，任何一种都不可恢复。

这是所有缺口里唯一"损失不可逆"的一项，所以排在 R2，而不是等 App 做完再补。

### 产品问题 4 · 公网只有一层共享密码

**用户原话区（逐字）**

> 然后关于刚刚说的谁都可以进入，能不能加一个密码或者之类的限制？

**AI 解释区**

现在挡在公网上的是 Nginx Basic Auth：一个用户名、一个密码、所有人共用、HTTP 明文传输。对"一个人用"够用；对"小范围适用"不够——无法区分谁是谁，也无法单独收回某个人。

真正的修法（账号 + `owner_id` + 按人过滤）属于阶段 4，成本主要不在代码量，而在**数据模型**：现在补约 1 天，等库里有几千条再补，要迁移 + 改几十处查询 + 判定历史数据归谁。所以本文档只登记，不动手。

### 产品问题 5 · 短期的目标是"一个人"，长期是"分发"

**用户原话区（逐字）**

> 暂时不备案，按照一人使用为短期目标，长期目标为分发。

**AI 解释区**

这句话决定了所有取舍的方向：短期不为多用户做任何事（不做账号、不做配额、不做审计），但**凡是"现在改便宜、以后改昂贵"的地方要预留**。当前符合这个标准的只有一处：`owner_id` 字段。

备案的判断也由此而来：IP 直连不需要备案，一旦要用域名指向这台大陆服务器就需要，周期 1–3 周。所以在"一个人用"阶段用 IP，是正确的选择。

## 统一范围与实施顺序

**顺序：R1 → R2 → R3。R4 只在"分发"启动时做。R5 可随时插入，不阻塞。**

理由：

1. **R1 必须第一**。它是"能不能用"的分水岭。R3 的壳做完如果密钥还存不了，壳里看到的仍然是个只读展示柜。
2. **R2 排第二，而不是最后**。它是唯一能防住不可逆损失的一项，且与 R1 无依赖，可以并行做，但不要拖到 App 之后。
3. **R3 排第三**。它提升的是"用起来像不像 App"，不改变能力边界。
4. **R4 单独一档**。它会动数据模型，而数据模型一旦动，前面的备份策略也要跟着改，所以放最后。

**最小可用定义**：R1 完成 = 手机能干活。R2 完成 = 数据不会丢。R3 完成 = 有图标、能分享。

## R1 密钥存储跨平台

**状态**：已实施（2026-11-01）

### 现状

| 位置 | 现象 |
|---|---|
| `secrets.py:93` | `protect_secret` 在非 win32 抛 `SecretStorageError("当前系统暂不支持…的本地安全存储")` |
| `secrets.py:123` | `unprotect_secret` 同上 |
| `store.py:2044` `set_secret_setting` | 写入 → `protect_secret`，保存任何 key 的必经之路 |
| `store.py:2050` `set_summary_settings_atomically` | 写入 → `protect_secret`，总结配置页 |
| `store.py:2097` `save_bilibili_session` | 写入 → `protect_secret`，B 站登录态 |
| `store.py:2024` `get_setting`（分支在 `:2026`） | **读取**：只有 `dpapi:` 前缀才解，其余原样返回 |
| `store.py:2089` `get_secret_setting`（直通在 `:2093`） | **读取**：`if not protected.startswith("dpapi:"): return protected` |
| `store.py:2119` / `:2123` | **读取** B 站 cookie / refresh token，同样只认 `dpapi:` |

> 行号按 2026-11-01 01:10 实测。这些文件近期有变动，执行前按函数名 grep 现查，不要直接按行号跳转。

### 原因

产品最初只面向 Windows 桌面，密钥保护直接用 DPAPI，且把"平台不匹配"写成硬失败而不是降级。这是合理的桌面假设，在云端不成立。

### 方案（A 推荐，B 兜底）

**方案 A：Fernet 对称加密 + 本机密钥文件**

| 项 | 设计 |
|---|---|
| 前缀分派 | `dpapi:` → Windows DPAPI（现状不动）；`fernet:` → 本机密钥 |
| 密钥文件 | `parents[5]/local/secret.key`——Windows 仓库布局下就是 `product/local/secret.key`，服务器上就是 `~/kb/local/secret.key`（与 `knowledge.db`、`knowledge-root/` 同目录）。`Fernet.generate_key()` 生成，写入时 `os.chmod(0o600)`。**首次创建必须独占**：`open(path, "xb")`，遇 `FileExistsError` 就去读已有文件——否则两个线程同时判定缺失会各生成一份，先写的那条密文永久解不开，且表现为「保存成功、读取报错」 |
| 路径推导 | 复用现有约定：`Path(__file__).resolve().parents[5] / "local"`（与 `main.py:318` 的数据库路径、`main.py:6320` 的 `_local_asr_runtime_project_root()` 同源），不新增配置项 |
| 新依赖 | `cryptography>=42,<46`，加入 `pyproject.toml`；wheel 约 4MB，3Mbps 下 20 秒内装完 |
| 代码落点（写） | `app/platforms/secrets.py`：`protect_secret` 按平台分派，新增 `_fernet()` 惰性加载（缺依赖时给可读错误，不是 traceback） |
| 代码落点（读） | **不新增函数**：把前缀分派放进 `secrets.unprotect_secret` 内部（`dpapi:` → DPAPI、`fernet:` → Fernet、其它仍抛「格式无效」）。`store.py` 保持现有的 `unprotect_secret` 导入与调用，只把两处前缀判断从 `startswith("dpapi:")` 放宽为 `startswith(("dpapi:", "fernet:"))`：`get_setting` 的 asr 分支、`get_secret_setting`。`get_bilibili_session_cookie` / `get_bilibili_refresh_token` 本来就直连 `unprotect_secret`，不用改 |
| 为什么不新建函数 | 4 个既有测试文件共 6 处用 `monkeypatch.setattr(..., "unprotect_secret", ...)` 打桩这条读路径（`test_api.py:628/694`、`test_asr_settings.py:37/112`、`test_governance.py:80`、`test_link_import.py:2111`）。改走新函数会让打桩静默失效或报 `AttributeError`，直接冲掉既有测试 |
| 不动的边界 | `unprotect_secret` 对无前缀值仍抛「格式无效」。**不要为了兼容去放宽它**——放宽会让明文被更多调用点当成凭证接受 |

**方案 B（零依赖降级，仅在 A 装不上时启用）**

非 Windows 下直接返回 `plain:` + 原文，读取时剥前缀。**B 同样要改上面那四个读取点**，否则 `plain:` 会连同原文一起被当成 key。代价是密钥以明文存在 SQLite 里——而这个库正在被 `scp` 拷贝、将来还要做备份，明文密钥会跟着备份扩散。所以 B 只作兜底。

**选 A 的理由**：多 4MB 依赖 + 约 20 行代码，换掉"密钥随备份扩散"这个风险，不划算的反面。

### 迁移影响（必须提前知道）

1. **Windows 上已加密的记录不能跨系统解密**。DPAPI 绑定 Windows 用户账户，`dpapi:` 值在 Linux 上无解。所以不存在"把密钥搬过去"这条路。
2. 云端那 4 条 `dpapi:` 记录已于 2026-10-31 夜间删除（`summary_api_key`、`ai_ask_siliconflow_api_key`、`bilibili_session_cookie`、`bilibili_refresh_token`），数据库备份在 `~/kb/local/knowledge.db.bak`。
3. R1 完成后需要**在云端重新录入**：总结模型 key、（可选）AI 问答 key、（可选）云 ASR key，并重新扫码登录 B 站。这是必付的一次性成本。
4. **桌面端零影响**：Windows 上仍走 DPAPI，已有记录照常解密。
