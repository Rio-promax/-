## 产品问题 1

### 用户原话区（逐字，不许改写）

> 导入小红书收藏的过程中，导入时间极，获取导入的时间极长，并且没有导入到收藏内容。这是问题，同时牵扯到的相关条件失效，比如在小红书的平台连接中有些检查环境，检查环境的可，我不是，可能是去检查连接是否还成功，但是点检，点击检查环境之后显示环境正在使用中

### AI 解释区

三个现象，按用户叙述顺序：

1. **导入耗时极长且没有结果**：点「小红书收藏」后，弹窗停在「正在读取…」，长时间不出现收藏夹或候选条目，最终也没有导入到收藏内容。
2. **关联条件失效**：同一时间，平台连接相关检查入口被判为「环境正在使用中」，用户自己也不确定该入口是「检查环境」还是「检查连接是否仍成功」。
3. **截图**：弹窗标题「小红书收藏」，正文「正在读取…」，右下「取消」。

**不确定项（不臆断）**：代码内**没有**与「环境正在使用中」完全一致的文案（全工作区检索零命中）。最接近的两处是桌面壳的「小红书收藏扫描正在进行」与「请先关闭小红书登录窗口后再执行其他操作」。用户点的是平台连接面板「环境自检」、登录窗口「重新检查」，还是其它入口，**仍待用户确认**；本轮按「占用态被互斥挡住」这一共同机制处理，未擅自改动检查入口文案。

### 现状与原因（实施前只读核对证据）

**A. 前端只等 120 秒，超时后丢弃已取得结果** — `app/ui/app.js`（行号为实施前）

- 原 `requestDesktopShell`：小红书扫描全部走 WebView2 消息桥；120 秒超时即移除 `message` 监听器、发 `cancel_favorites`、reject「小红书收藏读取超时」。
- 只接受 `CONNECTED` / `PARTIAL`。监听器移除后，壳随后回传的 `PARTIAL`（可带已抓候选）**无人接收** → 「没有导入到收藏内容」。
- `renderAccountImport`：`step` 非 `folders`/`candidates` 时只渲染 `state.message || "正在读取…"`，扫描期间没有任何阶段、进度或连接状态 → 截图状态。
- `startXhsScan` 首步固定 `scope: "directory"`，目录读取完成前不会进入选择界面。

**B. 壳内串行等待叠加，单次扫描容易超过 120 秒** — `desktop-shell/Program.cs`

- `CheckTimeoutMilliseconds = 12000`；`NavigateAndWaitAsync` 与 `WaitForResponseAsync` 每次最多等 12 秒。
- `ScanFavoritesAsync` 串行经过：初始化 → 导航 ExploreUrl → 等 `/user/me` → 导航收藏页 → 等首部分页 → 目录/笔记扫描；目录扫描另有 20 秒 deadline，专辑点击另有 20 秒。
- 分页循环每页滚动后再等一个 12 秒，且 `idleRounds >= 3` 才退出（最多 3×12 秒空等）。

**C. 占用互斥在前端超时后没有立刻释放，检查入口被挡** — `Program.cs`

- `_checkGate = new SemaphoreSlim(1, 1)`；`CheckSessionAsync` 与 `ScanFavoritesAsync` 都要拿这把锁，扫描在 `finally` 才释放。`CheckSessionAsync` 的 `WaitAsync()` 没有超时。
- `_favoriteScanRequestId` 扫描期间非空；`ScanFavoritesAsync` 开头若非空直接返回「小红书收藏扫描正在进行」。
- `CancelFavoritesScan` 只置标志+唤醒 waiter，前端发完取消不等壳确认。
- 窗口级 `_pendingLoginRequestId` 非空时，所有 `check_session` / `scan_favorites` 直接返回「请先关闭小红书登录窗口后再执行其他操作」。

**D. 本功能是首次真实账号实测**

- `product/docs/基线/需求/11-12_账号收藏快捷导入_解决方案.md` 的 R3 写「真实收藏页候选尚未取得」，R4 写「非空专辑条目字段与实际选择提交尚未验收」，「人工验证是否通过」列仍为空。

### AI 解释区

**问 1：那些等待时间的 DDL 有什么用？**

它们是「防止永远挂起」的兜底，不是产品能力：

- 需求正本 §约束规定「只处理平台页面已经发出的收藏业务响应，不发送 Cookie，不构造签名请求」，所以壳**不能主动请求**小红书数据，只能被动等 WebView2 的导航完成事件与页面自己发出的业务响应。
- `NavigateAndWaitAsync` 和 `WaitForResponseAsync` 都用 `Task.WhenAny(事件, Task.Delay(12000))`——等不到就返回空，避免某个事件永不触发导致线程永久挂起。
- 两处 20 秒 deadline 是等收藏专辑 DOM 出现、等专辑链接跳转生效的轮询窗；`idleRounds >= 3` 是判断「滚动后不再有新分页」的收敛条件。
- **用户判断成立**：调这些数值只能改「多久放弃」，既不会让账号连接状态变得可见，也不会让收藏数据在壳里变得可选。R1~R3 因此降级为内部支撑项，不作为本轮主修复。

**问 2：为什么用户察觉不到小红书账号是否已连接？**

因为原前端**没有任何路径去核实**连接状态，界面上的「已连接 / 未连接」是一条不会被更新的数据库记录：

- 设置面板用 `conn.status === "CONNECTED"` 渲染「已连接 / 未连接」；工具区只有「断开 / 连接」「刷新连接状态」「环境自检」。
- 「环境自检」请求 `/environment/check?check_network=false`，查的是磁盘空间 / FFmpeg / Python / ASR，**与小红书会话无关**；「刷新连接状态」只是 `GET /platform-connections`，返回静态 DB 记录。
- 原 `app/ui/app.js` 中 `check_session`、`open_login`、`browser-login` **零命中**。完整链路只存在于旧版 `app/ui/_legacy/app.js`：`check_session` → 壳 `CheckSessionAsync` → `POST /platform-connections/xiaohongshu/browser-login` 写回状态。
- 后端端点都在：`GET /platform-connections`、`POST /connect`（只写 `NOT_CONNECTED`）、`POST /check`（对浏览器会话平台返回静态记录）、`POST /browser-login`（**唯一**把状态写成 `CONNECTED` 并更新 `last_checked_at` 的入口）。
- 结论：UI 重构把壳会话检查链路留在 `_legacy/` 未迁入新 `app.js` ⇒ 点「连接」不会真的弹壳窗口、状态不会被核实、导入前也不会校验 ⇒ 用户看到的状态与真实登录态无关。这是「相关条件失效」的真正落点，比超时更靠前。

**问 3：为什么不能通过壳打开里面的收藏数据来选择内容进行导入？**

技术上**已经在壳里打开了收藏页**，只是用户看不见、也拿不到中途结果：

- `ScanFavoritesAsync` 确实导航到 `?tab=fav&subTab=note` 与 `?tab=fav&subTab=board`，并监听页面业务响应解析候选。
- 但壳窗口 `Show(this)` **只在 `open_login` 时调用**；`scan_favorites` 分支直接执行扫描，窗口保持隐藏。
- 候选由 `SendProductMessage` **一次性**回传，中间没有分批回传也没有阶段反馈；产品弹窗只能显示「正在读取…」。
- 也就是说：原架构是「后台隐藏窗口抓取 → 一次性结构化候选 → 产品弹窗里选」，**不是**「壳内可见浏览并勾选」。一旦中间卡住，用户既看不到收藏页、也拿不到任何候选，连是否已登录都无从判断。

**本轮动作（对应「请继续完成未完成的任务」与「b」）**：把上述两个产品级问题补进方案、把主修复轮从「调超时」改为「连接状态可核实 + 壳内收藏可见可选」，按用户裁定的 **B** 形态实施 R4 / R5，并提交 `28135eb`。交互形态 A/B 已裁决（2026-11-13，用户回「b」→ B）。
