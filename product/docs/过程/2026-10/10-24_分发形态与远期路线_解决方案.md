## 产品问题 1 · 本地形态与"分发出去"的远期目标冲突

**用户原话区（逐字，不许改写）**

- U-R1-01 · 初始提出

  > 对，目前 PRD 中结构性存在部分错配，这部分需要修改，因为它的远期目标一直都是分发出去而非本人本地去使用，因此需要设置一个远期的方案。

**AI 解释区**

- 需求编号：R1。
- 现状：`00_总PRD.md` 把"本地优先"写进 §3 定位假设，§6.2 把云端与多端列为明确不做，§4.2 又声明"本机产品不以注册用户作分母"。三处合起来，一个**阶段手段**被写成了**产品身份**。
- 原因：产品的远期目标是分发；本地只是当前绕开平台授权与服务器成本的手段。
- AI补全/假设：把"本地优先"降级为 S0–S2 的阶段取舍，不承诺未来一定上云，也不承诺永不上云。
- 判断：这是 PRD 里唯一的**结构性**错配。其余三处（指标口径、合规性质、成本结构）都是它的派生。

## 产品问题 2 · 三条分发路是否存在共性

**用户原话区（逐字，不许改写）**

- U-R2-01 · 初始提出

  > 关于你提到的几个东西，它是否存在一定的共性？比如如果我要实现开源或者托管，或者依托它处分发，那么我需要进行哪些部分的更改？

**AI 解释区**

- 需求编号：R2。
- 现状：产品是单体本地程序；`adapters/sources/*` 负责取数、`app/workflows/analyze.py` 负责理解、设置页 + DPAPI 负责凭证，三层混在同一条本地调用链里。
- 原因：只跑一种形态时，混着最省事；换形态就要重写。
- 判断：**有共性，且只有四处接缝。** 三条路不是三个产品，是同一内核换三个壳。所以现在不需要选路，只需要留缝。

| 接缝 | 现在在哪 | 为什么必须切开 | 三条路各自怎么接 |
|---|---|---|---|
| A 内容对象与证据锚点 | 02 信息对象结构 + 归档 writer | 换形态不能重写归档层 | 三条路共用，**冻结不再改** |
| B 取数适配器 | `adapters/sources/*`，凭证由设置页/全局配置提供 | 插件与云端都没有你的设置页 | 改为 `fetch(ref, credentials)`，凭证从入参注入 |
| C 理解服务 | `workflows/analyze.py` 内直接调 ASR/LLM，本机 torch 常驻 | torch 搬不进浏览器，也不该进云端镜像 | 本地 / 自建网关 / 厂商直连三态可换 |
| D 凭证仓库 | 本机 DPAPI | 三种宿主三种存法 | 只定接口：本机 keyring / 云 KMS / 宿主 cookie（插件可直接不经过你） |

- 推论：**"依托他处分发"最省改动，因为它把接缝 D 直接外部化给宿主**——用户的登录态从来没进过你的程序。
- 推论：开源与托管只在接缝 D 上真正分家；B 与 C 的改动量相同。

## 产品问题 3 · 本地 API 集合与集中采购转订阅

**用户原话区（逐字，不许改写）**

- U-R3-01 · 初始提出

  > 关于本地的语音识别，这个都可以使用 API。我能不能把它作为一个本地 API 的集合？因为可能本地 API 比较贵，但是我可以去集中地采购，然后用户来进行订阅。

**AI 解释区**

- 需求编号：R3。
- 现状：ASR 有本地 torch 路径与外部 API 路径两套（设置页 ASR 分区已分开选用）。LLM 走用户自填 Key。
- 原因：原话把两件事压在了一句里，必须拆开，否则会做出一个"本地跑着却收不到钱"的东西。
- AI补全/假设：原话"本地 API 比较贵"按上下文理解为"单用户零散购买额度单价高、本地算力投入大"，集中采购有议价空间；此解释未经用户确认。

**拆成两件事**

1. **形态**：把 ASR/OCR/LLM 包成本机 HTTP 服务（`127.0.0.1`）。这是接缝 C 的一种实现，好处是插件与外部程序也能调用；代价是多一层进程管理与端口占用。
2. **商业模式**：集中采购 + 转售订阅。这**必须有服务端**（账号、额度账本、限流、退款），与本机服务无关。本机服务解决不了计费。

**三种"集中采购"的落地，按你要背的责任排序**

| 方式 | 你要做什么 | 用户看到什么 | 代价 |
|---|---|---|---|
| (a) 转售充值码 | 批发买额度、发码 | 仍自己填 Key，只是从你这里买 | 不碰内容，最轻；厂商条款可能禁止转售 |
| (b) 自建推理网关 | 部署网关、按账号记额度 | 填你的 Key 或登录你的账号 | 内容经过你，隐私承诺改写；需防滥用、限流、退款 |
| (c) 纯 BYOK | 只做"去注册 + 填 Key"引导 | 自己去厂商注册 | 零责任、零收入、流失高 |

- 建议：**S0–S2 用 (c)，要收钱时先试 (a)**。(b) 的固定成本（网关 + 风控 + 退款流程）在还没有付费用户时最贵。
- 必须记下的成本真相：ASR 走 API 后，每条视频都是真金白银。定价下限 = 单条成本 × 预估条数 × 安全系数，**这个数必须实测**。测法：取 3/10/30/60 分钟各 2～3 条真实样本，各跑一次，记录时长、token 与账单差额，得出分钟单价。
- 必须记下的口径变更：ASR 走 API 后，**音频一定离开本机**。"本地优先"只剩"归档内容不落别人服务器"这一半。§7 的隐私承诺必须同步改口径，否则构成虚假宣传。

## 产品问题 5 · 模板先行与"只做插件不满足"

**用户原话区（逐字，不许改写）**

- U-R5-01 · 初始提出

  > 因为我下一步打算肯定不是第一时间得到需求之后去分发，我可能会先优先将自己的一个制定的一个草稿制成一个模板进行上线，来进行一个小团内的一个分析。然后在比较大的这个范围内，就是得到一致的好评之后，再慢慢的看能不能制成一个独立软件，如果只做做成插件的话，个人是不会进行满足的。因为我这个软件不会弄的很大，因此它的风险不会那么高，同时我核实过目前网上有许多类似的产品，这一步我们还是先进行调研，以或者说问调研前的准备，以及对目前的 PRD 进行一定程度的修改。

**AI 解释区**

- 需求编号：R5。
- 现状：阶段顺序是"先验证产物、再验证留存、最后做交付"，与建议一致。
- 原因：先把最容易做的做出来换反馈，符合个人开发者的资源现实。
- 三处需要修正的判断：

  1. **模板阶段验证的是"产物"，不是"产品"。** 模板得到的好评绝大多数是"内容不错"，不是"我愿意装、愿意付费、愿意交登录态"。若模板阶段不同时收交付容忍度与付费锚，S2 会一片好评，S3 装机崩掉。
  2. **插件与独立软件不是二选一。** 插件是**入口**（负责分发与唤起），独立软件是**仓库**（负责归档与留存）。两者共用接缝 A/B/C，只换 D 与壳。用户的诉求与分发效率不冲突。
  3. **"竞品很多"不是风险低的证据，是差异化难的证据。** `social-content-knowledge-base` 的 Strongest objection 已经写明：把不打算重看的收藏变成维护成本更高的仓库，采集越顺、积灰越多。"软件不大"只降低维护风险，不降低需求风险与合规风险。

## 产品问题 6 · 平台原生能力：B站视频笔记已经做了同一件事

**用户原话区（逐字，不许改写）**

- U-R6-01 · 初始提出

  > 以及在 PRD 中对 Bilibili Note 的一些反思。

**AI 解释区**

- 需求编号：R7。
- 现状：PRD §3 的竞品表只列了第三方（Cubox、Readwise、NotebookLM、BiliNote 系），**没有一个"平台自己"的对手**。而 B站视频笔记已经提供：时间戳绑定、点一下跳回片段、多端云同步、汇总到「我的笔记本」、公开／私有、笔记内关键词检索（2026-10-25 检索公开使用说明，非官方文档）。
- 原因：原先把"竞品"理解成"另一个产品"，忽略了"平台自带功能"——它不收费、不用装、还跟着 App 一起打开，是最强的替代方案。
- 关键事实（决定产品边界）：

| B站视频笔记有 | B站视频笔记没有 |
|---|---|
| 时间戳与跳转、多端同步、我的笔记本、公开/私有、图片 | **只对知识区或 UP 主授权的视频开放**，娱乐/影视多无入口；**不支持原生导出**，只能逐条复制 |

- 判断：**"给 B站视频记笔记"这个卖点已经不成立**，站得住的只剩三段：① 平台没开放笔记入口的视频；② 跨平台统一（小红书／抖音／知乎没有等价物）；③ 本地长期留存与导出。
- 推论：任何"复刻平台笔记编辑器"的设计（公开笔记、评论互动、时间轴样式）都是正面竞争，且随平台改版同步失效——**明确不做**。
- 落点：PRD §3.3 新增平台原生能力对照，§7 新增一条风险（v8.2）；调研题库 B1–B10 专测这一块；N1–N3 测认知、试用与弃用。
- AI补全/假设：把"Bilibili Note"理解为平台自带的视频笔记，而非第三方产品 BiliNote。两者都在 §3.2 表里，此处按上下文取"平台原生"义；若用户本意指第三方 BiliNote，需另开一轮。

## 产品问题 7 · 什么时候问功能、什么时候问需求，定价什么时候测

**用户原话区（逐字，不许改写）**

- U-R7-01 · 初始提出

  > 其中对于问题我还有一些问，对这些问题我还有一些问题，比如比如有的是功能性问题目前我们走的走的是电脑端，之后肯定要在电脑端分发出去，然后并且弄成手机端，手机端应该是这个世界的主流，但是你是否愿意为手机端来单独使用，感觉这个问题好呆逼。

- U-R7-02 · 初始提出

  > 然后收费是我现在还没有具体想到它的收费是多少。那对于这样的问卷，我是不是应该先问自己想好的一些问，先对需求进行提问呢，然后再对功能收费。就是我不知道什么时候用功能收费，什么时候用需求收费，还是说都应该集中在这个问卷中。就是我现在如果以一个产品的流程和逻辑来看，我是应该在制定产品之前把这些全都弄清楚，还是先把产品的需求弄出来，然后再慢慢的去补功能呢？

**AI 解释区**

- 需求编号：R8。
- 现状：调研工具里同时混着需求题、功能题、付费题，没有分阶段规则。
- 原因：把"一次问卷问完所有事"当成了效率，实际会让每道题的证据强度都下降。
- 三个判断：

**① 功能不问"要不要"，只问"你现在为它做了什么替代动作"。**

| 想问的 | 废题（会得到愿望清单） | 有效题（会得到工作流） |
|---|---|---|
| 手机端要不要 | 你愿意为手机端单独使用吗 | 你手机上存的东西，后来在电脑上找过吗？找到了吗 |
| 自动打标签要不要 | 你需要自动分类吗 | 你现在存完会手动分类吗？分几类？分完还找得到吗 |
| 导出要不要 | 你需要导出功能吗 | 你有没有把平台上的笔记复制到别处？复制到哪了 |

- "你愿意为手机端单独使用吗"是三处毛病叠在一起：问意愿（不是行为）、问不存在的东西（还没做）、双重问题（手机端／单独／使用）。用户说"呆逼"是准确的。
- 更根本的一点：**手机端不是要不要的问题，是能不能做的问题。**单人 + Python + 本地模型，手机端只有三条路——重写原生、走云端、做 PWA／分享入口。这是成本表决定的事，不是投票决定的事。

**② 顺序是「入口 → 需求 → 功能」，不是「需求 → 功能 → 入口」。**

- 功能是增量，入口是结构。加功能改的是代码，换入口改的是产品。
- 现在的入口动作是"打开电脑 → 跑 cmd → 粘链接 → 等处理"。这个动作决定了它是工具而非产品；手机端、插件、分享面板都是换入口，不是加功能。
- 所以**功能可以后补，入口不能后补**——先想清楚"它靠什么动作被用起来"，再谈要哪些功能。

**③ 定价分两步：S0 只测形态，S2 才测数字。**

| 阶段 | 测什么 | 怎么测 | 不做什么 |
|---|---|---|---|
| S0 问卷 | 买断／年费／按量，哪种形态更能接受 | P2 单选 | 不问"你愿意付多少"，没有产品时问价格等于问想象 |
| S0 访谈 | 过去一年为这类工具花过多少、值不值 | 事实回溯 | 不做 Gabor-Granger 阶梯报价 |
| S2 小范围 | 具体数字 | 预售／早鸟价，真收钱 | 不靠问卷数字定价 |

- 理由：只有掏钱的动作是真的。S0 阶段能拿到的可靠价格信息只有一个——**他过去已经为同类工具付了多少**（S3 已收）。

**④ 功能题不该进这份问卷。**

- 这份问卷的唯一任务是决定分发形态与需求是否成立，共六个决定（见调研文档第一节）。每加一道功能题都在稀释它。
- 功能需求在"没有产品"时问不出来，真实信号只出现在三处：他现在的笨办法、他为此付的钱、原型给他用之后的强制取舍。
- 落点：功能类问题全部移入访谈第五段「只能留三个」与 S2 原型测试；问卷只保留 P3 一道"只能做一件事"的强制单选。

## 产品问题 8 · 始源目的是面试，其次才是真正运行

**用户原话区（逐字，不许改写）**

- U-R8-01 · 初始提出

  > 在思考的过程中也可以考虑到我的一个目的，它的始源目的应该是为了面试，应该是为了突出自己的产品功能，或者说产品经验，其次才是将这个产品真正进行运行

**AI 解释区**

- 需求编号：R9。
- 现状：此前所有方案（分发路、调研、收费）都按"要真正运行"来排序优先级。若首要目的是面试，排序需要改。
- 原因：面试考察的不是用户数，是**判断过程**——怎么定义问题、怎么验证、砍掉了什么、错在哪。
- 判断：**这不改变调研要做什么，改变的是"什么算做得好"。**

| | 产品视角 | 面试视角 |
|---|---|---|
| 样本量 | 200 份才够判阈值 | 200 和 300 没区别，和 20 有区别 |
| 最值钱的产出 | 比例与区间 | 具体的人、具体的话、具体的取舍 |
| 失败案例 | 要藏 | **最值钱** |
| 定价 | 必须验证 | 讲清逻辑比给出数字得分高 |
| 功能清单 | 越准越好 | 越能说明"砍了什么、为什么"越好 |
| 分发 | 要传得开 | 能讲清"为什么现在不做分发"就够 |

- 三条结论：

  1. **一次调研，两份产出。** 同一批数据，产品侧出比例表，面试侧出"原话摘录 + 决策记录"。不额外做一轮。
  2. **付费样本的优先级下调。** 面试官会问"这些人你从哪找的"。面板上买来的陌生人答不出完整故事，讲不圆。预算先给"自己渠道里约到的 10 场深度访谈"——那能产出一句被记住的原话。
  3. **必须记录被否决的选项。** 面试里最有说服力的不是"我做了什么"，而是"我本来要做 A，因为 X 改成 B"。所以本方案每个"待决策"最终都要有裁决记录和理由，不能只留结论。

- 一条纪律：**PRD 里不写"本产品用于面试"。** PRD 是产品文档，写动机会让它失去专业性；动机记在本文件的产品问题里，两份文件不混。

- 状态：待执行（S0 未开始）。
- 现状：无分发阶段划分，仅有取数能力的五个阶段。

| 阶段 | 做什么 | 验证什么 | 退出条件（量级估算，非承诺） |
|---|---|---|---|
| S0 调研 | 问卷 300 + 访谈 10 | 该不该做、给谁做 | 2～3 周，拿到分层比例与付费锚 |

1. 问卷"不敢交登录态" > 50% → 放弃托管，走开源 + 宿主入口。
2. 付费意愿 >100 元/年 的比例 < 20% → 不做订阅，走开源 + 赞助或买断。
3. S2 十四天回访率 < 30% → 停在模板/插件，不投独立软件。
4. 实测分钟单价 × 预估月条数 > 最低档年费的 10% → 必须做额度或限流。

## R8 · 提问时序规则：入口 → 需求 → 功能，定价分两步

- 状态：已落地于调研文档（第七节、第十节判定线）；规则本身在本节。
- 现状：调研工具里需求题、功能题、付费题混在一起，没有阶段规则；用户不确定何时问什么。
- 原因：把"一次问卷问完所有事"当成效率。
- 方案：

| 阶段 | 该问 | 不该问 |
|---|---|---|
| S0 问卷 | 需求是否发生、交付能不能过、付费**形态**（买断/年费/按量） | 功能清单、具体价格数字 |
| S0 访谈 | 现在怎么绕过去、为什么不用现成方案 | "你想要什么功能" |
| S1 模板 | 产物值不值得要第二次 | 装载形态、定价 |
| S2 小范围 | 原型下的强制取舍（删到三个）、预售真收钱 | 满意度评分 |
| S3 独立软件 | 装机、Key、崩溃恢复 | 新功能 |

- 两条硬规则：**功能不问"要不要"，只问"你为它做了什么替代动作"；需求不问"重不重要"，只问"上次发生是什么时候"。**
- 顺序判断：**入口 → 需求 → 功能**。功能是增量、入口是结构；换入口要重写，加功能只是加。所以"功能可以后补，入口不能后补"。
- 验收：[自动] 调研文档 L1 中无"你需要 X 功能吗"型题目；[人工] 用户确认"手机端由成本表定，不由问卷投票定"。

- 原因：用户 2026-10-25 说明始源目的是面试，其次才是真正运行。
- 方案：不改变调研内容，改变评价标准。三条：① 一次调研出两份产出（比例表 / 原话与决策记录）；② 付费样本优先级下调，预算先给自有渠道的 10 场深度访谈；③ 每个待决策最终必须有裁决记录与理由。

- 验收：[自动] 调研文档存在"两用设计"一节且 PRD 全文无"面试"字样；[人工] 用户确认这条分层不会让产品文档变形。
