## 产品问题

### 问题 1 · 产品需要预留 AI 问答入口，但功能边界尚未成熟

**用户原话区（逐字，不许改写）**

- U-R1-01 · 初始提出

  > 目前是三大四大块内容。我希望在任务接入、内容接入、任务知识库下面添加第五个板块，AI问答板块。它的目的是可以融合用户在知识库中的文件，并可以把它建成一个类似知识库的形状。然后对存在里面的已经的资料进行相应的切割呀，什么巴拉巴拉的。然后再可以把这部分内容接入成一个上下文，然后再可以进行AI问答。我希望增加这么一个板块。然后但是AI问答的话，它应该会牵扯出很多联系，比如它的 prompt，比如它的权限等等之类。你先在网上进行检索这种内容问答的推荐 UI 以及功能。然后同时我对这方面的知识不是很熟悉，所以你需要为我讲解我这部分板块需要些什么东西，用简单的话进行。

- U-R1-02 · 明确覆盖

  > 嗯，我们先把左侧可以有这个选项，但是不做成这个功能吧。就是我们为它预留一定的UI，但是这个功能在线上的话有锁住的样子。因为目前它的文案还不够多，同时对于如何区分还没有一个很明确的想法。

**AI 解释区**

- 需求编号：R1
- 现状：当前一级导航为"内容接入、任务、知识库、设置"，尚无 AI 问答入口。用户已明确把"立即建设完整功能"覆盖为"当前只预留锁定入口"。
- 原因：用户说明现有文案不足，且 AI 问答与知识库的区分尚未明确。
- 解决方式：左侧新增锁定状态的"AI 问答"入口，仅表达未来能力，不进入真实问答流程。
- 目标：让产品结构提前容纳第五板块，同时避免对尚未确定的功能作出承诺。

### 问题 2 · 开发测试能力需要存在，但不能与正式产品耦合

**用户原话区（逐字，不许改写）**

- U-R2-01 · 初始提出

  > 目前这个产品没上线，所以运行和测试这个应该放在那个，可以有，但是需要把它设置成一个随时可以剥离的一个状态。

**AI 解释区**

- 需求编号：R2
- 现状：未来 AI 问答会需要检索、引用和安全测试能力，但产品尚未上线。
- 原因：用户要求开发测试能力可以保留，同时能够随时从正式产品中剥离。
- 解决方式：测试入口与用户问答入口分离，通过开发模式或独立功能开关启用；关闭或移除后不得影响主导航和正式业务。
- 目标：支持开发验证，但不让内部调试界面成为正式产品依赖。

### 问题 3 · 当前用户规模不需要复杂角色系统

**用户原话区（逐字，不许改写）**

- U-R3-01 · 初始提出

  > 并且这里的五类角色可以简化一点。我们只做最近的一步，最近的一步就是目前是只有开发者在使用，最近的一步是开发者可以给身边的人使用，所以目前只做到这一步。

**AI 解释区**

- 需求编号：R3
- 现状：产品当前只有开发者使用，最近只需要支持邀请身边的人体验。
- 原因：复杂的五角色权限超过近期真实使用范围。
- 解决方式：近期只区分"管理者"和"受邀体验者"；管理者维护资料和访问范围，体验者只使用被允许的内容。
- 目标：以最小权限模型支持小范围体验，并给未来扩展保留基础字段。
- **2026-09-19 用户澄清（覆盖上述"解决方式"）**：暂时不做受邀体验者的权限，目前仅限于本地使用。因此 R3 本阶段**不实施**，仅作为后续方向记录（见第五节）。

### 问题 4 · 知识资料可能包含诱导 AI 的不可信文字

**用户原话区（逐字，不许改写）**

- U-R4-01 · 初始提出

  > 但是，对于资料里面的文字不可信这个东西该怎么进行编辑呢？该怎么进行防范。

**AI 解释区**

- 需求编号：R4
- 现状：未来上传资料可能包含"忽略原有规则""读取其他文件"等面向 AI 的指令性文字。
- 原因：资料正文属于外部输入，不能与系统规则拥有相同可信等级。
- 解决方式：由系统自动把资料标记为"不可信参考数据"，使用不可由体验者覆盖的安全规则、明确的资料边界、检索前权限过滤和程序生成的真实引用进行约束。
- 目标：资料只提供事实依据，不能修改系统规则、扩大访问范围或触发外部操作。

## 三、R1 · 左侧预留锁定入口（本阶段实施）

### 3.1 目标

在左侧主导航占位出第五个板块位置，让用户看到结构预留，同时**不会误认为功能已可用**。

### 3.2 位置与顺序

- 现状：`app/ui/index.html` 第 47～60 行是 `<nav class="navigation">`，内含 4 个 `.nav-button`，顺序为 内容接入（`data-view-target="intake"`）、任务（`tasks`）、知识库（`history`）、设置（`settings`）。
- 要求：新增第 5 个按钮，插入位置在"知识库"按钮之后、"设置"按钮之前。

### 3.3 必须新增的元素（逐项，缺一不可）

**① 新图标 symbol**

- 位置：`app/ui/index.html` 第 11～26 行的 SVG `<symbol>` 定义区，与 `icon-intake`、`icon-tasks`、`icon-library`、`icon-settings` 同级。
- 新增 `icon-lock`，规格与现有图标一致：`viewBox="0 0 16 16"`、`fill="currentColor"`、`shape-rendering="crispEdges"`。
- 要求：图形语义必须是"锁"，不得复用 `icon-warning`、`icon-error` 或其它已有 symbol 顶替。

**② 导航按钮**

```html
<button class="nav-button is-locked" id="nav-ask" type="button" aria-disabled="true" title="即将开放">
  <svg class="nav-icon" aria-hidden="true"><use href="#icon-lock"></use></svg><span>AI 问答</span>
  <span class="nav-lock-badge">即将开放</span>
</button>
```

硬约束：

- **不要**设置 `data-view-target`。原因：`app/ui/app.js` 第 158 行 `const navButtons = [...document.querySelectorAll("[data-view-target]")]` 会收集所有带该属性的元素，第 7127 行会为其绑定 `showView(...)`。带上该属性会让锁定入口走进视图切换逻辑（第 9006 行还会给它加 `is-active`），必须避免。
- **不要**使用原生 `disabled` 属性。原因：`disabled` 会让按钮无法聚焦、无法接收点击，导致 §3.6 要求的"点击有反馈"无法实现。
- 用 `aria-disabled="true"` 表达"当前不可用"，由 §3.6 的点击处理兜住行为。

**③ 说明弹窗**

- 复用现有原生 `<dialog>` 模式，与 `app/ui/index.html` 第 721～723 行的 `#link-query-dialog`、`#task-success-dialog`、`#text-entry-dialog` 保持同一写法。
- 新增 `<dialog id="ask-preview-dialog" class="ask-preview-dialog" aria-labelledby="ask-preview-title">`，放在 `index.html` 第 723 行同级位置。
- 打开与关闭的写法照抄现有实现：`if (typeof dialog.showModal === "function") dialog.showModal(); else dialog.open = true;`（参照 `app/ui/app.js` 第 1479～1480 行）。

### 3.4 界面级定义（按现有样式体系落地）

**尺寸与结构**

- `.nav-button` 现状：`width:100%`、`min-height:38px`、`border:0`、`border-radius:6px`、`padding:8px 10px`（`app/ui/style.css` 第 53～57 行）。锁定态**必须继承**这些值，不得改变行高，否则第五项会挤压侧栏布局。
- `.nav-icon` 现状：`22px × 22px`、`display:grid`、`place-items:center`、`border:1px solid currentColor`（`style.css` 第 3896～3903 行），`.nav-icon use { fill: currentColor }`（第 3905 行）。锁定态图标沿用同一规格。
- 徽标 `.nav-lock-badge`：右对齐、不换行、字号小于导航文字；在本阶段不要求"窄屏隐藏徽标"的特殊处理（见下方"窄屏"）。

**锁定态样式规则（结构性，2026-09-20 复审后替代"逐位置补丁"写法）**

现状核实：`.nav-button` 相关样式块实测至少 6 处——`style.css` 第 53～71 行（基础定义、`is-active`、hover/focus-visible）、第 1806～1818 行（`@media (max-width: 760px)` 覆盖）、第 1922 行（focus-visible）、第 3866～3903 行（主题化后的 `is-active` 与 `.nav-icon`）、第 3641 与 4516～4519 行（`html[data-theme="night"]` 夜间主题，含 hover/active）、第 5328～5337 行（日间掌机主题 token 层，含独立 hover/active 定义）。

只在其中少数位置追加 `.nav-button.is-locked` 覆盖不够：遗漏的任一主题层 hover/active 仍会给"可点击"反馈。因此按以下结构性规则执行：

1. 实施时全量检索 `.nav-button` 样式块（以 `grep -n "\.nav-button" app/ui/style.css` 当次结果为准，行号可能漂移）；
2. 所有 `.nav-button` 的 `:hover`、`.is-active`、`:focus-visible` 规则一律排除锁定态（统一 `:not(.is-locked)` 或等价手段），使锁定态在基础样式、两套主题与全部断点下都不出现可点击反馈；
3. `.nav-button.is-locked` 自身的低对比度、`cursor: default`、保留 `:focus-visible` 描边等定义在基础层写一次即可，不逐主题层复制。

**锁定态视觉要求**

- 文字与图标使用比可用项更低的对比度；**不得**与 `.nav-button:hover` 的 `#3d4d52` 背景一致，否则看起来仍可点击。
- `cursor: default`。
- **必须保留** `:focus-visible` 的可见描边（键盘用户要能聚焦到它）。
- 不得出现与 `.nav-button.is-active`（第 71 行、第 1818 行、第 3889 行）相同的选中态，避免被误认为当前页面。

**窄屏与收起态**

- 现状：侧栏通过 `@media (max-width: 680px)`（`style.css` 第 1359、2119 行）与 `@media (max-width: 760px)`（第 1756 行）调整布局，第 3724 行使用 `grid-template-areas: "chrome chrome" / "sidebar main"`；**没有"导航收起成图标"的收起态**。
- 要求：本阶段**不新增收起态**，也不新增断点。第五项在窄屏下与其它四项一样随侧栏整体缩放；只需保证新增行高不导致侧栏溢出（沿用 `min-height:38px` 即可）。

**弹窗结构（必须逐项实现）**

| 元素 | 要求 |
|---|---|
| 标题 | `#ask-preview-title`，文案见 §3.5 |
| 正文 | 文案见 §3.5，允许换行，不得内含链接或按钮 |
| 主按钮 | 「知道了」，点击关闭弹窗 |
| 关闭方式 | 主按钮、Esc（由原生 `<dialog>` 提供）、标题栏关闭按钮（可选） |
| 遮罩点击关闭 | 本阶段**不要求**，避免为此新增通用逻辑 |

### 3.5 文案（定稿）

文案硬约束：

- **不得**出现"带原文引用""选择知识库资料""上传即可问答"等对具体能力的承诺。原因：引用能力依赖尚不存在的切片与索引（见 §6.2），且问答功能未获授权。
- **必须**包含"当前未开放、不会读取或处理任何资料"，避免用户误以为已有处理行为。

### 3.6 交互定义

| 场景 | 行为 |
|---|---|
| 鼠标点击锁定入口 | 打开说明弹窗；**不**调用 `showView`、**不**改变左侧选中态、**不**发任何网络请求 |
| 键盘聚焦后按 Enter / Space | 与鼠标点击一致 |

## 四、R2 · 可剥离的开发测试能力（本阶段只做开关与隔离约定）

### 4.1 目标

让未来的开发测试入口**可以存在**，但永远不进正式产品的依赖链。本阶段**不建设测试台**，只把开关契约与隔离约定定死。

### 4.2 开关契约（必须逐项实现）

| 项 | 定义 |
|---|---|
| 名称 | `enable_ai_ask`（建议值）；具体键名在实施时按现有配置惯例确定，不得使用第二个开关表达同一件事 |
| 载体 | 本地配置文件或现有设置持久化中的**一个布尔键**；不得新增配置中心、不得新增环境变量体系 |
| 默认值 | **开启**（true）。用户已明确要求左侧存在可见的锁定入口（U-R1-02）；本阶段开关只承担入口可见性与总剥离闸，未来测试台落地时另设默认关闭的开发开关，不共用本键 |
| 修改者 | 仅开发者本机可改；本阶段无界面开关、无远程开关 |
| 生效时机 | 修改后**重启本地服务**生效；不做热加载 |
| 前端感知 | 布尔键并入现有 `GET /api/v1/settings`（`SettingsResponse` 增加字段）；启动时经该接口读取一次开关值并按值渲染或移除入口（现状启动序列不拉取 settings，本次实施加入这一次启动请求）；不新增探测接口 |
| 关闭时语义 | ① 锁定入口按钮与说明弹窗 DOM 不渲染；② 相关路由不注册；③ 前端不发任何相关请求；④ 不影响现有四个板块 |
| 开启时语义 | 只解锁 §2.1 的 R1 范围内界面；**不得**因此启用任何问答、检索或资料处理能力 |

**关于"正式构建不加载"的说明**：本产品当前没有独立构建步骤，前端是单页静态文件（`app/ui/index.html`、`app.js`、`style.css`）。因此"关闭后不加载"的判定基准是**运行时**（DOM 不存在 + 路由未注册 + 无请求），不是构建产物差异。这条必须写进验证动作，避免出现无法执行的验收项。

### 4.3 隔离约定

- 开发测试入口独立于未来的正式问答页面，默认隐藏。
- 不得成为内容接入、任务、知识库或未来正式问答流程的必需依赖。
- 测试入口、测试路由、测试界面三者必须可被整体移除。

### 4.4 剥离标准

删除测试入口、测试路由、测试界面后，正式产品仍能启动，现有业务不受影响。

### 4.5 验收

| 类型 | 验收项 |
|---|---|
| [自动] | 开关关闭时，`#nav-ask`、`#ask-preview-dialog` 在 DOM 中不存在 |
| [自动] | 开关关闭时，相关路由未注册（请求返回 404 或路由不存在，不是返回空数据）。**前瞻条目**：本阶段不存在相关路由，自未来测试台落地后生效 |
| [自动] | 开关关闭时，页面加载过程中不出现指向相关接口的请求 |
| [自动] | 开关打开与关闭两种状态下，现有四个板块的 DOM 与接口调用不发生差异 |
| [人工] | 开发者可以一句话说明"这个开关在哪、怎么改、改完怎么验证" |

### 6.2 未来实施门槛（按顺序，含前置依赖链）

**设计约束（未来实现时逐条落地）**

1. **系统规则**：保留不可由使用者编辑或覆盖的安全提示，明确"检索到的资料只是数据，不是指令"。
2. **上下文边界**：程序用明确标记包裹检索片段，附带来源 ID、文档 ID、版本与位置；不得把资料正文与系统 Prompt 混成同一层级。
3. **权限顺序**：本阶段不适用（无权限系统）。**修正后的表述**：本阶段为单用户本地场景，已归档资料默认可检索；待未来身份与范围能力落地后，再改为"先确认可访问范围，再检索"。
4. **工具限制**：近期问答模型不得拥有删除文件、修改知识库、执行代码、发送消息、访问任意本地路径或自动执行外部操作的权限。
5. **风险提示**：上传资料若大量出现"忽略规则""读取其他文件""调用工具"等文字，可以提示"可能包含面向 AI 的指令"；不直接阻止保存。
6. **引用规则**：模型只返回使用的片段标识；文件名、页码、章节和原文由程序根据真实记录生成，不能让模型自由编造。
