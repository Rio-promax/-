## 六、R1 · 样本集与基线清点

- **状态**：待实施。
- **现状**：`xhs-30/images` 下 30 个笔记目录、96 张 webp，`notes.jsonl` 有 `imageFiles` 顺序，但没有分类、没有尺寸与体积清单，也没有"哪些图里有字"的事实记录。
- **原因**：没有分类就无法按类统计错字率与误检噪声，实测结论只能给一个笼统数字。
- **方案**：
  1. 生成 `ocr-samples.json`：每条记录 `note_idx / note_id / title / image_index / path / bytes / width / height / category`。
  2. `category` 三值：`scenery`（风景/装饰，预期无文字）、`text`（文字稿/长图，预期成段）、`ui`（界面演示截图，预期碎片）。分类**先按人工粗标**，标注者为本文件；不确定标 `unknown`，不计入分类统计。
  3. 生成缩略图索引（长边 ≤ 320，webp），供 R7 展示与人工复核。
  4. 样本清单与分类结果同时写一份 markdown 表，便于人工改标。
- **验收**：
  - [自动] `ocr-samples.json` 覆盖 96 张图，`image_index` 与 `notes.jsonl` 的 `imageFiles` 顺序一致。
  - [自动] 三类各自张数非零，`unknown` 张数单独统计且不混入分类指标。
  - [自动] 缩略图 96 张全部生成且长边 ≤ 320。
  - [人工] 分类与人对这 96 张图的判断一致。

## 八、R3 · 前处理管线

- **状态**：待实施。
- **现状**：样本是 webp，尺寸差异大（3.8KB–252KB），同一张图可能被多条笔记重复引用；OCR 与将来的 VLM 都需要同一套归一处理，目前没有。
- **原因**：缩放与去重直接影响耗时与重复计费，且是两层共用的能力，先建好不返工。
- **方案**：
  1. `decode`：统一解码为 RGB（webp 由 Pillow 承担，受管 venv 已有）。
  2. `resize`：长边上限先取 **1280** 作为实测起点（该值是起点而非结论，R5 可对比 1024 / 1280 / 原图三档）。
  3. `hash`：内容 sha256，作为去重与后续重跑的键。
  4. 输出统一 JSON 行，供 R4/R5 复用。
- **验收**：
  - [自动] 96 张全部解码成功，无一抛异常。
  - [自动] 缩放后长边 ≤ 设定值，宽高比不变。
  - [自动] 相同内容得到相同 sha256；`xhs-30` 与 `xhs-all` 两份重复目录的哈希一致率可统计。
  - [人工] 缩放后的图仍可辨认文字（抽样 5 张）。

## 九、R4 · 判定规则（不用 Jev）

- **状态**：待实施。
- **现状**：链路需要三个判定——图里有没有字、文字成不成段落、值不值得继续处理。目前都没有实现。
- **原因**：这三条当前都能用确定性规则表达，不需要决策服务；先跑规则才能拿到"规则错在哪、错多少"的证据。
- **方案**：
  1. **有无文字**：检测框数量 < 阈值 N（起点 N=3）判 `empty`。阈值由 R5 实测校准。
  2. **成段 vs 碎片**：用几何特征——行高中位数的一致度、行间距规律性、连续行数、每行字符数。判据与阈值写死在配置里，代码里不留魔法数。
  3. **判定依据落盘**：不只记结论，记判定用了哪些数值（框数、离散度、字符数），便于复盘。
  4. 不引入 Jev，不引入任何外部决策调用。
- **验收**：
  - [自动] 三类样本的判定结果与人工分类对照，产出混淆矩阵。
  - [自动] 每个判定结果都可追到具体数值（落盘字段齐全）。
  - [自动] 代码库中无外部决策服务调用（grep 无相关依赖）。
  - [人工] 判错的样本集中在哪一类、是否呈现可修的规律。

## 十一、R6 · demo 壳接线

- **状态**：待实施（依赖 R5）。
- **现状**：`login-shell` 有平台按钮、「打开我的收藏」「自动滚动（拟人）」「抓取本页内容」「刷新状态并写报告」，没有 OCR 入口；抓取产物目录已有 `notes.jsonl`。
- **原因**：需要一个真实入口验证"抓完就能看图内文字"，而不是只在脚本里跑。
- **方案**：
  1. 工具栏新增按钮「识别本页图片」，点击后对当前抓取目录下的图片调用 OCR。
  2. C# 通过子进程调用 Python OCR 脚本，JSON 进 / JSON 出，超时可中断，失败只标记当前图不中断整批。
  3. 子进程契约（与 09-20 P5 契约兼容，是其超集）：

```json
输入：{"images":[{"index":1,"path":"images/01_xxx/01.webp"}]}
输出：{"engine":"<引擎名>","engine_version":"<版本>",
      "items":[{"index":1,"status":"ok|empty|failed",
                "text":"…","score":0.93,
                "boxes":[[x1,y1,x2,y2]],
                "elapsed_ms":820}]}
```

  4. 结果落盘 `ocr.jsonl`，每条含 `note_id / image_index / status / text / score / boxes / engine / engine_version / sha256 / created_at`。**引擎名与版本必须落盘**，这是将来换引擎能批量重扫的唯一依据。
  5. `status` 三态严格区分：`empty`（图里确实没字，正常结果）与 `failed`（处理出错）不得混为一谈。
- **验收**：
  - [自动] 图片顺序与 `imageFiles` 一致，未被改变。
  - [自动] 单张失败不影响其余图片，失败项被标记且不静默转空文本。
  - [自动] `ocr.jsonl` 每条含 `engine` / `engine_version` / `sha256`；同哈希重复输入只处理一次。
  - [自动] 子进程超时与异常被捕获，shell 不崩溃。
  - [人工] 点击按钮后能在合理时间内看到结果，进度可见。

## 十二、R7 · 可回溯展示

- **状态**：待实施（依赖 R6）。
- **现状**：OCR 文本若只以纯文本呈现，用户无法判断它识别得对不对；OCR 的错误是静默的（不报错，只给错字）。
- **原因**：可回溯是让人敢信这套结果的唯一机制，也是发现引擎选错的唯一手段。
- **方案**：
  1. 壳内新增结果面板：左列图片缩略图（按 `image_index` 排序），右列对应文本行与其 `score`。
  2. 低置信度行（阈值由 R5 实测给出起点）在界面上有可见标记，不静默丢弃。
  3. 选中一条文本时，在缩略图上绘制对应坐标框，实现"点字回原图"。
- **验收**：
  - [自动] 面板条目数与 `ocr.jsonl` 一致，顺序一致。
  - [自动] 每条文本都能取到坐标框；框坐标在原图范围内。
  - [自动] 低置信度行有标记且未被丢弃（数量可核对）。
  - [人工] 点击文本能在图上看到对应位置，能据此判断识别是否正确。
