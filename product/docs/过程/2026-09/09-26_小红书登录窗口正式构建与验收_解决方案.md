## 产品问题

### 问题 1 · 已关闭旧壳后需要把新版构建到正式路径

**用户原话区（逐字，不许改写）**

- U-R1-01 · 初始提出
  > 已关闭，需要进行重新构建吗
- U-R1-02 · 补充并授权执行
  > 构建步骤为：你按需要构建的内容构造一个清单，一个完善方案，一个能够让C执行者按照进行执行的方案。做完之后，然后让C执行者按照该方案去执行。

**AI 解释区**

- 需求编号：R1～R4
- 现状：新版源码已经提交并在独立输出目录编译成功，但此前运行中的旧 `LoginShell.exe` 锁住正式 Release 输出，标准路径中的程序尚不能据此确认已更新。
- 原因：Windows 不允许构建过程覆盖正在运行的可执行文件；用户现已关闭旧产品壳。
- 解决方式：由 C 执行者确认进程已退出，使用 x64 .NET SDK 构建到正式 Release 路径，运行定向测试并核对产物，然后记录结果和本地提交。
- 目标：`product/start-product-shell.cmd` 下次启动时使用本轮新版 `LoginShell.exe`。

## 构建执行清单

### R1 · 构建前门禁

- 确认没有运行中的 `LoginShell` 进程。
- 使用 `C:\Program Files\dotnet\dotnet.exe`，避免 PATH 优先命中无 SDK 的 x86 dotnet。
- 检查当前 HEAD、工作树与本轮两个实现提交仍存在；保护所有无关未提交改动。
- 不删除 `bin/`、`obj/`，不执行 Git reset、clean 或全量暂存。

### R2 · 正式 Release 构建

- 执行：`C:\Program Files\dotnet\dotnet.exe build product/local/experiments-platform-shell/login-shell/LoginShell.csproj -c Release`。
- 正式产物必须写入：`product/local/experiments-platform-shell/login-shell/bin/Release/net10.0-windows10.0.17763.0/LoginShell.exe`。
- 预期：退出码 0、0 error。既有 NuGet 漏洞源不可达或 WindowsBase 版本冲突 warning 如未升级为 error，可如实记录但不伪称已消除。
- 若仍提示文件被占用，定位占用进程并停止，不强杀未知进程；无法确认归属时停止并报告。

### R3 · 自动验证

- 执行定向测试：`product/.venv/Scripts/python.exe -m pytest product/src/services/core/tests/test_0916_ui_interaction_contract.py -q`，预期 11 项通过。
- 检查正式产物存在、修改时间晚于本轮构建开始时间且文件大小大于 0。
- 运行 `git diff --check`，只检查本轮方案/进度记录可能产生的差异。
- 不以源码字符串检查代替真实构建成功；不把自动测试通过当作桌面人工验收通过。

### R4 · 记录、提交与人工验收交接

- 在本文末尾新增“进度总结记录”，仅记录自动验证是否通过，人工验证栏保持空白。
- 本轮若只有本文记录变化，只精确暂存本文并创建本地 commit；不得纳入其他工作树改动。被忽略的构建产物不提交 Git。
- 不自动启动产品壳。构建完成后交给用户通过 `product/start-product-shell.cmd` 启动。
- 人工验收：确认小红书窗口显示“复制当前链接”和“重新检查”；普通页面不误报人工验证；真实验证页面能显示明确提示；复制得到当前页面 URL。
