- 本轮已核实并更正的事实（写入本方案，替代此前对话中的口头结论）：

  3. **产品的 ASR 本地化流程界面层面已完成**：设置页已有「本地 / 云端 ASR」引擎选择、本地模型的下载（含进度与状态）、导入、发现、校验、查更新、删除，以及独立的「安装本地运行时」入口；`app/adapters/asr/` 下已有本地与云端两个适配器。用户 U-T3 中"云端 asr 和本地 asr 下载配置还没做"不成立。

## R1 · 桌面外壳与内嵌浏览器凭证读取验证

- 状态：**已实施，自动验证通过，待人工验收**。
- 现状：产品没有桌面外壳；`product/start-product.cmd:48` 起本地 uvicorn 服务，`:42` 用 API 契约版本做健康检查，`:59` 调用系统浏览器打开 `http://127.0.0.1:8765/`。产品界面与接口同源，前端 `app/ui/app.js:133` 在同源时使用相对路径（`API_ORIGIN` 为空串），后端 `app/api/main.py:1294` 挂 `/ui` 静态目录、`:1297` 根路径返回 `index.html`——**界面在与外围形态无关这一点上已经具备条件**。
- 需要回答的两个问题：
  1. 桌面外壳的原生层能否读到内嵌浏览器里的第三方站点 Cookie（含 HttpOnly）。
  2. 桌面外壳的原生层能否读到页面自身发出的接口响应，从而**不必自行计算平台签名**。
- 方案：在 gitignore 已排除的 `product/local/experiments-platform-shell/webview2-spike/` 下建立一个最小实验外壳（.NET 10 WinForms + Microsoft.Web.WebView2），**不新增产品依赖、不修改任何产品代码**。
  - 依赖：`Microsoft.Web.WebView2` 1.0.4191.47（NuGet）；浏览器引擎直接使用机器上已安装的 WebView2 运行时，**不需要下载 Chromium 内核**。
  - 目标站点：B站、知乎、小红书。
  - 采集口径：Cookie 只记录**名称与标志位**，不记录值；响应只记录 URI、状态码、字节数与 JSON 顶层键名，不记录正文内容（对应用户既有的"凭证不得出现在响应、日志、任务元数据中"约束）。
- 实测结果（2026-09-20 22:19）：
  - 浏览器引擎版本：`153.0.4234.32`（机器已安装，零下载）。
  - **Cookie 读取：三个站点全部成功，各 13 条，值均非空。**
    - 小红书存在 `a1` / `gid` / `webId` / `web_session`；其中 `web_session`、`acw_tc` 标记为 **HttpOnly**。
    - 知乎存在 `d_c0` / `_zap` / `SESSIONID` / `_xsrf`；其中 `captcha_session_v2` 标记为 **HttpOnly**。
    - B站存在 `buvid3` / `buvid4` / `b_lsid` / `b_nut` / `_uuid` 等（未登录态，故无 `SESSDATA`）。
    - **关键结论：原生层可以读到 HttpOnly 会话 Cookie**——这是浏览器扩展在页面上下文里做不到的。
  - **响应读取：成功。** 共观察到 96 条接口响应（含状态码与 Content-Type），其中 15 条成功读取正文；已确认读到真实 JSON 正文的例子：
    - 知乎 `/api/v3/account/api/login/qrcode` → `expires_at` / `link` / `token`（138 字节）。
    - 知乎 `/api/v3/oauth/sms/supported_countries` → `count` / `data` / `version`（11741 字节）。
    - B站 `cm.bilibili.com/cm/api/receive/content/pc` → `code`（10 字节）。
    - 同时观察到小红书 `/api/sns/web/v2/user/me`、`/api/sns/web/v1/login/qrcode/create`、`/api/sns/web/v1/login/activate`、`/api/sns/web/v1/config`、`t2.xiaohongshu.com/api/v2/collect` 等端点，**全部由页面自身携带签名发出**。
  - **附带结论**：小红书与知乎的登录二维码端点都在页面自身流量中直接可见，说明"在外壳内直接承载平台登录页"即可完成授权，**无需逆向二维码流程**。
- 已知限制（下一轮必须处理，不得在 R2 直接沿用）：
  1. 部分响应正文读取返回 `COMException`（`WebResourceResponseReceived.Response.GetContentAsync()` 对流式或已被渲染进程消费的响应不可靠）。R4 需改用页面内注入 hook 或 CDP `Network.getResponseBody` 兜底。
  2. 本机为跑通该实验，浏览器参数需带 `--disable-gpu --no-sandbox`，且需把环境代理显式传给引擎（Chromium **不读** `HTTP_PROXY`/`HTTPS_PROXY` 环境变量）。其中风险参数属于本机沙箱特有，**产品化时不得默认带上 `--no-sandbox`**；代理则是一项真实的产品考虑（需在设置中可配）。
  3. 自动化轮次未验证真实登录态（未扫码、未登录）；已由用户在人工轮次补验，见下。
- 人工验证结果（2026-09-20 23:01–23:03，用户在壳内自行操作）：
