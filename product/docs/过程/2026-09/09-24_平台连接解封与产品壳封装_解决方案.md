### 问题 2 · 产品要装进壳里，是 demo 还是产品级

**用户原话区（逐字，不许改写）**

- U-V1 · 2026-09-24

  > 壳的话，我现在想把我们的产品先封装到壳里面，这能做一个demo吗？还是说如果封装了？就不是一个demo级别，就是整个产品级别。

**AI 解释区**

- 需求编号：N2。
- 现状：产品当前是「本地 web 应用」——`product/start-product.cmd` 起 uvicorn（127.0.0.1:8765），然后 `start "" http://127.0.0.1:8765/` 用**系统默认浏览器**打开；壳（`LoginShell.exe`）是**完全独立的另一个程序**，只知道 xiaohongshu.com / bilibili.com / zhihu.com 三个外站，产品代码里 grep `webview2|LoginShell` **零命中**。
- 原因：用户想把这两件事合成一个「双击即用」的桌面应用。
- **结论（分界线在此）**：做成 demo **可以，而且「嵌入」这一步本身极便宜**——壳已经是 WebView2 宿主（`ShellForm` 持有 `_view`，`Dock = Fill`），把导航目标从外站换成 `http://127.0.0.1:8765/` 加一个模式开关即可。真正决定「demo 还是产品级」的**不是嵌入**，而是三件事：

  | 维度 | demo 级 | 产品级 |
  |---|---|---|
  | 后端进程归谁管 | 人手动双击 `start-product.cmd`，壳只负责显示 | 壳自己拉起 / 守护 / 退出清理 |
  | 登录桥 | 有（这是需求本体，必须做） | 同左，另加超时、重试、失败可读文案 |
  | 交付形态 | exe + `.cmd`，依赖本机已装的 .NET 10 Desktop Runtime | self-contained 发布 / 安装包，双击即用 |

- **AI 建议**：**demo 级封装 + 产品级登录桥**。理由：登录桥是本需求价值的全部，做浅了要重做；后端托管与发布形态可以后补，且不影响功能正确性。
- AI补全/假设：「封装到壳里面」按 **把产品界面载入 `LoginShell` 的 WebView2 窗口** 理解，**不是**把 Python 后端编译进 exe。
- 环境事实（2026-09-24 查证，供交付形态决策用）：本机 `C:\Program Files\dotnet` 已装 `Microsoft.WindowsDesktop.App 10.0.10`，壳可直接跑；`C:\Program Files (x86)\dotnet` 只有 5.0.17（无关）。**换一台机器就没有这个运行时**——这是 demo 与产品级在交付上的唯一硬差别。

## 六、三条封条怎么改 & 壳怎么用

### 6.1 P4-1（不写库）的改法

三处门禁的判断依据从 `checker_available` 换成新的合成判定 `_is_connectable(definition)`。**B站 分支一行不动。**

### 6.2 P4-3（0 控件）的改法

`app/ui/app.js:5984` 的 `else` 分支从「一律只读」改成「按连接可用性分级渲染」。**未接入的平台仍 0 控件**——09-20 P4-3 对它们**依然成立**，测试只换平台清单，不改断言。

> 省一处改动：响应体 `PlatformConnectionResponse.supported` **已经存在**（`app/api/schemas.py:892`），当前值就是 `definition.checker_available`（`main.py:5467`），而前端从未读过它（grep `\.supported` 在 `app.js` 零命中）。R7 不必新增字段，只需把 `supported` 的取值改成 `_is_connectable` 并在前端用起来。

### 6.3 壳的三个分叉（已裁定）

| 分叉 | 选项 | AI 建议 | 理由 |
|---|---|---|---|
| ① 壳的身份 | (a) 单窗口切换；(b) **一个壳进程、两个窗口**（产品主窗口 + 按需弹出的登录窗口） | **已选 (b)** | 产品页保持不动；登录窗口与主窗口共用同一 WebView2 user data 目录，由同一进程管理生命周期 |
| ② 登录态存哪 | (a) **留在壳自己的 WebView2 profile 目录**；(b) 抽出来写进产品 `browser_profile` 字段 | **(a)** | 产品只记 profile 的**路径**，cookie 永不进产品库，与「凭证不外泄」契约天然一致 |
| ③ 后端归谁管 | (a) **保持手动**（双击 `start-product.cmd`），壳只负责显示；(b) 壳自己拉起并守护 uvicorn | **已选 (a)** | 本轮不引入端口占用、崩溃重启、退出清理和日志托管 |

**裁定结果（2026-09-25）**：仅放行小红书；后端手动启动；壳使用**单进程双窗口**。产品主窗口通过 WebView2 `WebMessageReceived` 接收前端的登录、检查和断开动作，壳在同一进程内创建登录窗口并把非秘密结果回传产品页；不再由后端启动第二个 `LoginShell.exe`。

### 6.4 缺口空缺的具体形态

不新增任何 UI 组件。风控命中时：`connect` / `check` 落 `RISK_CONTROLLED`（**已有值，不新增常量**），`message` 给一句可读文案（如「小红书要求人工验证，请在登录窗口中处理后再检查」）。**壳不会自动弹窗。**

  4. `probe_platform()` 保持「无检查器即 `UNSUPPORTED`」的现状，**不改它**；分级判断放在 API 层，避免动到 P4 已验收的探测路径。
  5. 若 `/api/v1/capabilities` 的能力矩阵是按定义字段投影的，同步把新字段纳入投影；否则不动。

## 八、R2 · 后端分级放行

- **状态**：待实施（依赖 R1）。
- **现状**：`main.py:3779`（connect）与 `:3818`（check）对非 B站 平台直接 `probe_platform` 退回只读；`:5408` `_connection_or_default` 对 `checker_available=False` 的平台忽略存量行。
- **原因**：门禁用错了变量——`checker_available` 表达的是「有没有服务端检查器」，不是「能不能连接」。

  1. 新增判定 `_is_connectable(definition) -> bool`：`definition.checker_available or definition.browser_session_available`。

  4. **B站 的 `qrcode_session` 专属流程、`_save_bilibili_status`、二维码三端点全部不动。**
  5. 小红书 `connect` 本轮的行为 = **建立/更新一条 `NOT_CONNECTED` 记录**（真正登录由 R6 的壳完成）；**不得**在没有登录证据时落 `CONNECTED`。
- **验收**：
  - [自动] 小红书 `check` 返回 200，状态为 `NOT_CONNECTED`（**非** `UNSUPPORTED`），且**未**写入 `CONNECTED`。
  - [自动] 知乎 / 抖音 / 微信 `check` 仍返回 `UNSUPPORTED` 且不写库（09-20 P4-1 对它们**仍成立**）。
  - [自动] B站 全部既有测试原样通过。

## 九、R3 · 状态语义与缺口空缺

- **状态**：待实施（依赖 R2）。
- **现状**：09-20 把小红书可落状态限定为 `NOT_CONNECTED` / `UNSUPPORTED`；`RISK_CONTROLLED` 虽已定义但只被 B站 用到。

  3. 不新增弹窗、不新增「等待人工处理」中间态、不新增端点。
- **验收**：
  - [自动] 涉及的状态常量集合与 `connections.py` 既有定义完全一致（无新增字符串）。
  - [自动] 命中 `RISK_CONTROLLED` 时前端显示「需要人工验证」（复用 `app.js:5740` 既有映射）。

## 十二、R6 · 登录桥（产品 ↔ 壳）

- **状态**：待实施（依赖 R4）。
- **现状**：产品代码里**没有任何**启动桌面壳的能力；设置页对小红书没有任何可点控件；壳没有「只登录、不抓取」的模式。
- **原因**：这是本需求的核心——设置页点「连接小红书」要能弹出登录窗口，登录完关窗即完成连接。
- **方案**：
  1. 产品页向宿主发送 `open_login` / `check_session` / `disconnect_session` 三类 WebView2 message；不在浏览器端启动 exe。
  2. 壳在同一进程内打开小红书登录窗口，关闭后执行平台级有效性检查。**cookie 名称或数量只能证明会话材料存在，不能单独落 `CONNECTED`**。
  3. 小红书有效性检查必须同时满足：加载约定的需登录页面未跳回登录页，并命中壳内维护的已登录页面标志；任一条件不满足落 `NOT_CONNECTED` 或 `REAUTH_REQUIRED`，命中风控落 `RISK_CONTROLLED`。
  4. 壳只向产品页回传状态枚举、可读 message 和 `browser_profile` 路径；cookie 名、cookie 值和请求头均不回传。产品页再调用通用端点 `POST /api/v1/platform-connections/{platform}/browser-login` 持久化结果。
  5. 小红书 `/check` 不再调用无检查器的 `probe_platform()`；设置页“检查连接”先请求壳执行 `check_session`，再用同一通用端点更新状态。脱离桌面壳访问时明确返回“请在桌面壳中检查”，不得伪造 `CONNECTED`。
  6. “断开”先请求壳清除小红书域 cookie 并复验会话无效，成功后才删除产品连接记录；清除失败则保留原记录并显示失败，不得呈现“已断开”。
  7. 用户未登录直接关窗 → 落 `NOT_CONNECTED`，**不报错、不 5xx**。
  8. 凭证契约不变：WebView2 message、API 响应、日志、状态文件和 DB 均不得出现 cookie 值（沿用 09-20 P4-5 的断言口径）。
- **验收**：
  - [自动] 状态文件与全部 API 响应中不含 cookie 值（沿用 `test_connection_responses_do_not_leak_credentials` 的检查方式）。
  - [自动] 仅有 cookie 名/数量时不得落 `CONNECTED`；有效页面标志通过后才可落 `CONNECTED`。
  - [自动] 壳被用户直接关闭（未登录）时接口返回 `NOT_CONNECTED`，非 5xx。
  - [自动] 断开会清除小红书域 cookie；清除失败时连接记录不删除。
  - [自动] 端点清单检查：新增路径只含 `{platform}` 占位，无平台字面量。
  - [人工] 设置页点「连接小红书」→ 弹登录窗 → 登录 → 关窗 → 状态变「已连接」。
