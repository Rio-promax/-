## 三、产品问题

### 问题 1 · 部署前景从"本地个人"扩展到"云 + 小程序 + 手机"

**用户原话区（逐字，不许改写）**

- U-V1 · 2026-09-23

  > 还是从产品前景来出发吧，目前产品虽然是本地个人部署，但是后期希望能够部署到云端，甚至弄成小程序或者手机软件。其次，O西亚它的作用应该是与文字一起如果还是考虑到。一定的模型理解能力的话，用什么项目比较好啊？就大概理解能力是，比如用户发个风景，然后配图是山的话，能够理解这是山和风景。同步进行。

**AI 解释区**

- 需求编号：N1。
- 现状：v1 的选型（RapidOCR 本地推理、备选 `Sdcb.PaddleOCR` 纯 C#）都是按"本地桌面单用户"这一形态做的，前景一变，这两个前提都不再稳固。
- 原因：部署形态决定了"模型能不能跟着走"。小程序运行环境不允许内置 GB 级模型；手机端内存与耗电有硬上限；云端则相反——算力充足但数据要出本机。
- AI补全/假设：语音输入中"O西亚"按 **OCR** 理解。
- 影响：**"绑死本地原生推理"不再是最优解**，选型标准从"本地能不能跑"改为"这条能力链在四种形态下都站得住"。

### 问题 2 · 要的是"类别级对齐"，不是"生成一段描述"

**用户原话区（逐字，不许改写）**

- U-V1 · 2026-09-23（同上条的后半段）

  > 就大概理解能力是，比如用户发个风景，然后配图是山的话，能够理解这是山和风景。同步进行。

**AI 解释区**

- 需求编号：N2。
- 现状：此前讨论默认把"理解图片"等同于"调用视觉语言模型生成描述"。
- 原因：这个例子不需要生成——"图是山 / 配文是山 / 两者对得上"是**类别级对齐**，只要图和文落在同一个向量空间算相似度，或做零样本分类（给一组候选词挑最高分）即可。生成式 VLM 是它之上的能力，代价是秒级（云）到分钟级（本地 CPU）。
- 结论：**N2 由第 ② 层满足，不需要第 ③ 层**。这也与用户对第 ③ 层"太慢"的判断一致。

### 问题 3 · 第 ③ 层（图文理解 / 描述）本轮不做

**用户原话区（逐字，不许改写）**

- U-V2 · 2026-09-23

**AI 解释区**

- 需求编号：N3。
- 现状：L3（生成式图文理解）此前在方案里是"预留字段位但实现推迟"。
- 原因：用户判断延迟不可接受（本地 CPU 上一张图可达分钟级；云端也要秒级），且 N2 已由 L2 满足。
- 结论：**L3 本轮不实现、不实测、不接 API**；只在契约层保留方法位与能力位 `image_caption_available`，恒为 `false`。
- AI补全/假设："云API I"按 **云 API** 理解；"V1、V2、V3"按本文件的 **L1 / L2 / L3 三层**理解。

### 问题 4 · 能不能一个云 API 同时包含 L1 / L2 / L3

**用户原话区（逐字，不许改写）**

- U-V2 · 2026-09-23（同上条后半段）

  > 然后。这里的。云API I的话，能不能做到上传一个API的话，就同时包含V1、V2、V3功能呢？

**AI 解释区**

- 需求编号：N4。
- 现状：三层能力在当前讨论里是分散提到的（OCR 一个项目、embedding 一个项目、VLM 一个项目），用户希望收敛。

## 五、统一范围与实施顺序

### 5.1 三层能力定义

| 层 | 输出类型 | 典型延迟 | 本轮状态 |
|---|---|---|---|
| **L1 · 取文字** | 结构化文本 + 坐标框 + 置信度 | 毫秒 ~ 数百毫秒 | 实施中（v1 R1–R8） |
| **L2 · 图文对齐** | 定长浮点向量（图 / 文同一空间） | 毫秒 ~ 百毫秒 | **本轮实施（R10–R12）** |
| **L3 · 图文理解** | 自由文本（生成） | 秒级（云）~ 分钟级（本地 CPU） | **本轮不做**（仅留契约位） |

### 5.2 部署形态矩阵（选型必须同时满足四列）

| 层 | 本地桌面（当前） | 云端 | 手机 App | 小程序 |
|---|---|---|---|---|
| L1 | RapidOCR（onnxruntime，纯离线） | 云 OCR 或同一引擎容器化 | onnxruntime 有移动端实现 | **只能走服务端** |
| L2 | 本地 SigLIP2（数百 MB，离线） | 云多模态 embedding | 小模型可端侧 | **只能走服务端** |
| L3 | 端侧小 VLM（慢，可接受才做） | 云 VLM | 端侧小 VLM | **只能走服务端** |

**硬事实**：微信小程序的运行环境不允许内置 GB 级模型，**小程序形态下三层必然全部走服务端**。因此任何"把能力写死在某个本地引擎"的设计，将来上小程序都要重写。

### 5.3 明确不做

- 不做 L3（生成式描述 / VLM 问答）：不接 API、不实测、不写实现。
- 不改 v1 的 R1–R8 任何一条；不改 09-20 的 P5 定义与 `image_ocr_available` 门禁。
- 不引入 Jev 或任何外部决策服务（2026-09-21 裁决仍生效）。
- 本轮不动产品 `app/` 代码、不动 `.venv`、不动 `asr-runtime`。
- 不建向量库 / 检索服务（L2 本轮只产出向量与实测结论，检索是后续独立议题）。

### 5.4 实施顺序（一轮一提交，可独立回退）

**第 ① 层**：沿用 v1 的 R1–R8（本文件不重复，不改动）。
**第 ② / ③ 层（本文件新增）**：

R9 三层契约与三个能力位 → R10 L2 后端可替换适配层 → R11 L2 实测（96 张图） → R12 demo 接线 → R13 回填 09-20 与 v1。

**R9 是 R10 之后所有轮次的前提**：契约未定死之前，不接任何具体引擎。

## 六、D4 裁定 · 一个云 API 能否同时包含 L1 / L2 / L3

### 6.1 结论（三句）

1. **"一个端点三合一"：不成立。** 三层输出类型不同（坐标化文本 / 定长向量 / 自由文本），模型架构与训练目标不同，没有哪个 API 一次调用同时返回这三类东西。
2. **"一个供应商 + 一个 Key + 一套 SDK 全覆盖"：成立，已查证。** 阿里云百炼（DashScope）是目前覆盖最完整的一家，火山方舟覆盖 L2/L3 但不自带 VLM-OCR。
3. **但架构上仍应保持三个能力位分离**——理由见 6.4，这是本轮最需要记住的一条。

### 6.2 已查证的事实（2026-09-23，价格与端点以官方文档为准）

**阿里云百炼 DashScope —— 一个 Key 覆盖三层**

| 层 | 模型 / 端点 | 关键事实 |
|---|---|---|
| L1 | `qwen-vl-ocr-latest`、`qwen3.5-ocr`；端点 `.../api/v1/services/aigc/multimodal-generation/generation` | 内置任务（`ocr_options.task`）：`text_recognition` / `advanced_recognition`（**带坐标框**）/ `key_information_extraction` / `table_parsing` / `document_parsing` / `formula_recognition` / `multi_lan`。北京地域定价：输入 ¥0.3 / 百万 token，输出 ¥0.5 / 百万 token（batch 半价）。`qwen3.5-ocr` 支持直接传 PDF 解析 |
| L2 | `tongyi-embedding-vision-plus-2026-03-06`（1152 维，文本/图/视频/`multi_images`）、`qwen3-vl-embedding`（维度可选 256–2560，默认 2560）；端点 `.../api/v1/services/embeddings/multimodal-embedding/multimodal-embedding` | 支持**独立向量**（每个输入各一个向量）与**融合向量**（图文融为一个向量）。图片可传公网 URL 或 base64 Data URI |
| L3 | `qwen3-vl-plus` / `qwen3-vl-max` 等；OpenAI 兼容端点 | **本轮不做** |

**火山方舟 —— 覆盖 L2/L3，L1 需另接**

- L2：`doubao-embedding-vision-251215`，端点 `https://ark.cn-beijing.volces.com/api/v3/embeddings/multimodal`，文本/图/视频混合输入，支持稠密 / 稀疏 / 多向量输出。
- L3：豆包视觉理解系列。
- L1：未查见原生 VLM-OCR 端点，需另接专用 OCR 产品。

### 6.3 能合并的与不能合并的

- **L1 与 L3 可以同源**：`qwen-vl-ocr` 本身就是 Qwen-VL 训练出的 OCR 模型，二者是同一族。所以"用一个 VLM 系列同时抽字和描述"技术上成立。
- **L2 永远不能并进生成式调用**：向量必须是专门的 embedding 模型输出，生成式模型给不出可比较的稳定向量。**L2 必然是独立一次调用。**

### 6.4 为什么架构上仍要分成三个能力位（不要追求一次调用全包）

1. **失败模式不同，必须分别降级。** OCR 失败 → 该图标 `failed`；向量失败 → 图不可检索但文字仍在；VLM 失败 → 直接跳过，零损失。合成一次调用，一次失败三种能力全丢，且无法归因。
2. **成本与延迟差一个数量级。** OCR/embedding 是毫秒到百毫秒，VLM 是秒级甚至分钟级。合成一次调用无法分别设超时、分别重试、分别计费归因。
3. **可替换性是本轮的核心目标。** 本地形态 L1 用 RapidOCR、L2 用 SigLIP2；云形态换成百炼同一套契约。合成一个调用等于把"换后端"这件事做死——这正是 N1（后期上云/上手机）要避免的。

### 6.5 因此真正要定死的是契约，不是 API

产品侧定义 **一个网关、三个方法**，实现可插拔：

```
VisionGateway
  ├─ ocr(image)      -> {text, boxes, score, engine, engine_version}    # L1
  ├─ embed(image|text) -> {vector, dim, engine, engine_version}         # L2
  └─ caption(image)  -> {text, engine, engine_version}                  # L3（本轮恒不可用）
```

三个能力位各自独立开关：`image_ocr_available`（09-20 已有，P5 验收前恒 false）、`image_embedding_available`（新增，R11 验收前恒 false）、`image_caption_available`（新增，本轮恒 false）。

**换供应商 = 换一个 adapter，业务代码不动。**

## 七、R9 · 三层契约与三个能力位

- **状态**：待实施。
- **现状**：09-20 只有 L1 的单层契约 `[{index,text,status}]`；L2/L3 连字段名都没有；"后端可替换"此前只在 v1 的 D1 里以"demo 怎么接 OCR"的形式讨论过，没有升级为架构约束。
- **原因**：前景变成云 + 小程序 + 手机后，唯一稳定的是契约，不是引擎。契约不先定死，R10 接任何一个具体引擎都会把形态绑死。
- **方案**：
  1. 定义 `VisionGateway` 三个方法签名与返回结构（见 6.5），**只写契约文档与类型定义，本轮不落产品代码**。
  2. 三个能力位独立：`image_ocr_available` / `image_embedding_available` / `image_caption_available`，各自有独立翻牌条件，不得联动。
  3. 每个方法的返回必须带 `engine` + `engine_version`，与 v1 R6 的落盘要求一致——**这是换引擎能批量重扫的唯一依据**。
  4. 强制约束：业务代码只能依赖 `VisionGateway`，**不得直接引用任何具体引擎的包名或端点**（grep 可查）。
  5. L3 本轮只定义签名，不实现；`image_caption_available` 恒 `false`。
- **验收**：
  - [自动] 契约文档含三个方法的完整输入/输出定义，L3 标注"未实现"。
  - [自动] 三个能力位名称与各自翻牌条件写入文档，无联动表述。
  - [自动] grep 确认本轮未引入任何引擎包（代码零改动）。
  - [人工] 用户确认契约覆盖了 N1–N4 四条需求。

## 八、R10 · L2 后端可替换适配层（两套实现）

- **状态**：待实施（依赖 R9）。
- **现状**：没有任何图文向量能力；本地形态要求离线、云形态要求可迁移，两者选型不同但没有统一入口。
- **原因**：先在 demo / 独立 runtime 上把两套实现都跑通，才能证明"同一个契约、换后端不改业务"这件事是真的，而不只是文档上的说法。
- **方案**：
  1. **本地实现**：`SigLIP2`（开源、多语言、自托管跨模态检索的常用选择），落在独立 runtime，不污染产品 `.venv` 与 `asr-runtime`。
  2. **云实现**：百炼 `tongyi-embedding-vision-plus-2026-03-06`（1152 维，支持独立向量；图可走 base64）。**默认关闭**，需显式配置 Key 才启用。
  3. 两套实现输出同一结构：`{vector, dim, engine, engine_version}`；向量维度不同由 `dim` 字段承载，业务侧不得硬编码维度。
  4. 云实现的失败必须能降级为"该图无向量"，不得中断整批（与 v1 R6 的"单张失败不拖垮整条"同款约束）。
  5. 选型参照 **MIEB 榜**（跨模态能力），不看 MTEB（MTEB 主要测纯文本，反映不出跨模态）。
- **验收**：
  - [自动] 两套实现对同一张图都能返回 `{vector, dim, engine, engine_version}`，`dim` 一为本地维数、一为 1152。
  - [自动] 业务侧调用方代码在切换实现时零改动（同一函数签名，替换注入对象即可）。
  - [自动] 云实现在无 Key / 网络失败时返回可识别的失败态，不抛未捕获异常、不中断整批。
  - [自动] 本地实现的依赖体积与峰值内存被记录。
  - [人工] 同一张图的两套向量在语义上可用（人工抽 5 组图文对判断相似度排序是否合理）。

## 九、R11 · L2 实测（96 张真实图）

- **状态**：待实施（依赖 R10）。
- **现状**：用户举的例子（图是山、配文是山 → 系统知道这是山和风景）没有任何实测支撑；此前所有关于"L2 能不能做到"的判断都是推断。
- **原因**：这一层的能力边界只能实测给出，且样本天然带真值——`notes.jsonl` 的 `title` 就是配文，图与文成对出现，不需要人工标注。
- **方案**：
  1. 用 `xhs-30` 的 30 条笔记 / 96 张图，构造 **图文配对真值集**：每条笔记的标题与其下所有图互为"应当相近"的正样本，跨笔记随机配对为负样本。
  2. 跑两项指标：
     - **图文检索**：以标题向量检索其自己的图，统计 top-1 / top-3 命中率（与随机基线和"按笔记序号猜"的基线对比）。
     - **零样本分类**：给候选标签集（山 / 海 / 城市 / 美食 / 人物 / 室内 / 其它，标签集由实测时按样本实际内容调整），看图向量与哪个标签的文本向量最近，人工抽样核对准确率。
  3. 本地实现与云实现各跑一遍，对比精度与耗时；云实现同时记录 token 消耗与费用估算。
  4. 产出错例清单（错得最离谱的 10 组，附原因归类：图太小 / 多图混排 / 标签集不覆盖 / 抽象图 / 其它）。
- **验收**：
  - [自动] 96 张图全部产出向量，无静默失败；失败条目带原因。
  - [自动] 两项指标均落盘为 JSON + markdown 表，含随机基线对照，无"待补"。
  - [自动] 本地 / 云两套实现的精度、单图耗时、内存峰值、估算费用对比完成。
  - [人工] 零样本分类抽样核对结果与自动统计一致；错例归类合理。

**门禁规则**：R11 未产出前，`image_embedding_available` 不得翻 true，也不对 L2 效果下任何结论。

## 十、R12 · demo 接线（L2）

- **状态**：待实施（依赖 R11）。
- **现状**：demo 壳只有抓取与报告入口，没有任何图文能力展示位；v1 的 R6/R7 只接 L1。
- **原因**：需要一个真实入口验证"搜一张图能找到配文、搜一段话能找到图"，而不是只在脚本里跑数字。
- **方案**：
  1. 壳内新增「图文索引」按钮：对当前抓取目录建索引（图向量 + 标题向量），落盘 `embeddings.jsonl`，字段含 `note_id / image_index / sha256 / dim / engine / engine_version / created_at`。
  2. 新增一个简单检索框：输入文字，按向量相似度返回最相近的若干张图（缩略图 + 相似度分数）。
  3. 与 v1 R6 共用同一套前处理（缩放、sha256 去重），不重复实现。
  4. 索引可重跑：`sha256 + engine + engine_version` 三者决定一条记录是否需要重算。
- **验收**：
  - [自动] 索引条目数与图片数一致，顺序与 `imageFiles` 一致。
  - [自动] 同哈希重复图只索引一次。
  - [自动] `embeddings.jsonl` 每条含 `engine` / `engine_version` / `sha256` / `dim`。
  - [自动] 检索接口在索引为空时返回可识别的空态，不崩溃。
  - [人工] 输入一个词能找回语义相关但与词面无关的图片（或明确记录做不到）。

## 十三、风险与不确定处

- 百炼的价格与端点为 2026-09-23 查证值，**可能变动**；正式接入前须以官方控制台为准。
- 云 embedding 意味着**图片要出本机**。这与"本地私密"的卖点冲突 → 必须做成配置开关，默认关闭，且在 UI 上有明确提示。
- 本地 SigLIP2 的依赖体积、CPU 上的单图耗时**未实测**，R10 的第一个验收点就是它。
- 百炼 `tongyi-embedding-vision-plus` 的维度固定 1152（不可配）；若将来要统一维度，需选 `qwen3-vl-embedding`（256–2560 可配）——**换模型会导致历史向量全部失效**，必须与 `engine` / `engine_version` 一起记录才能重算。
- 第三方模型授权需留意：`jina-embeddings-v5-omni-nano` 虽为 CPU/边缘设计，但授权是 CC-BY-NC，**将来商业化要绕开**。
- R11 之前关于 L2 效果的一切判断都没有依据，本文件不预设结论。
- 本轮不动产品代码，产品测试基线（当前 360 passed）不受影响。
