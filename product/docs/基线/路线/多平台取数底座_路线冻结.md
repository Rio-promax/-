# 多平台取数底座：路线冻结

> 用途：把 Web 端「按链接取内容 / 扫描收藏并勾选抓取 / 授权界面」三个体验目标的**底座选型**固化为基线，作为后续调研与实施的前提。
> 性质：**路线冻结，不构成代码授权**。任何实施改动仍需另出 `product/docs/MM-DD_功能或问题名称_解决方案.md` 并获用户批准。

**文档状态**：2026-09-20 首次冻结。第一节至第六节为**已冻结基线**；第七节及以后为**本轮新调研，尚未冻结**。

---

## 一、Web 端三个体验目标（冻结）

| 编号 | 目标 | 用户原话要点 |
|---|---|---|
| 目标 1 | 按链接拿到小红书、抖音、知乎的**内容** | 「能根据链接拿到小红书、抖音或者知乎的内容」 |
| 目标 2 | 查看这些平台的**个人收藏**，扫描里面有哪些内容，并选择进行抓取 | 「能够查看这些地方的收个人收藏，来扫描里面有哪些内容，并选择进行抓取」 |
| 目标 3 | 有登录要求的页面/能力，统一放到**登录界面**实现；不一定是登录账号 | 「如果有登录页面项的内容，或者说登录页面的要求则放到登录界面，它可以不一定是登录账号，但是功能会在那个地方进行实现」 |

**目标 3 的性质判定**：它不是独立功能，**它就是底座本身的操作面板**。用户说的「不一定是登录账号」，对应的实现形态就是受控浏览器会话（产品只拿 session，不接触账号密码）。

## 二、底座四条路线（冻结）

| 编号 | 路线 | 做法 | 冻结结论 |
|---|---|---|---|
| **A** | 纯算签名 | 用 Python 自己算出平台的请求校验码 | **可接受**（用户 2026-09-20 明确「45 天以后也可以接受」），但不作为首选 |
| **B** | 跑混淆 JS | 把平台算签名的混淆代码下载后用 Node.js 跑一遍，取其结果 | 不推荐 |
| **C** | **驱动页面 + 拦截响应** | 开真实浏览器加载平台页面，监听页面自身发出的 XHR 响应 | **主线** |
| **D** | **挂本机已开的浏览器** | CDP 连接用户本地已运行的 Chrome | **兜底** |

**C / D 的共同性质（关键）**：产品只拿到 session，**永远不接触账号密码**。这是底座的安全性基础。

**A 路线的真实代价（需与「45 天」区分）**：
- 「平均 45 天更新一次」= **维护频率**问题，用户已表示可接受。
- 「2026 年手工构造签名成功率 <12%」= **可用性**问题，与维护频率无关，是 A 路线的真正障碍。
- 若选 A，必须先把成功率实测出来，不能只按维护频率判断。

## 三、术语通俗说明（冻结）

### 3.1 签名 / 签名难度

平台的网页在发请求时，会额外附上一组校验码，用来证明「这个请求是真的从我的网页发出来的，不是脚本伪造的」。这组校验码就是**签名**。

**签名难度**指的是：你想绕开浏览器、自己用 Python 调接口，就必须自己算出**一模一样的值**——这件事有多难。

- 难在**算法不公开**：要靠逆向把平台的 JS 读明白。
- 难在**算法会变**：平台定期换算法，你的代码就要跟着改。
- 难在**算法被故意写乱**：平台会把算签名的代码混淆（见 3.3），让人读不懂。

三平台对照：小红书 `x-s` 高；抖音 `a_bogus` 最高；知乎 `x-zse-96` 中。

### 3.2 纯算签名（路线 A）

**不启动浏览器**，用 Python 把签名自己算出来，再直接用 Python 发请求。

- 好处：轻、快、省资源——不用跑浏览器进程。
- 坏处：平台一改算法（小红书平均 45 天一次）你就得跟着改代码；且成功率是独立风险，见第二节。

### 3.3 跑混淆 JS（路线 B）

"混淆"指平台把算签名的代码**故意写乱**：变量名变成 `a1`/`b2`、逻辑拆成一堆跳转、正常的可读性被彻底破坏。

"跑混淆 JS" = **不试图读懂它**，而是把这段代码原样下载下来，用 Node.js 执行一遍，让它自己把签名算出来，再把结果拿去用。

- 好处：不需要逆向理解算法，算法改了重新下载即可。
- 坏处：必须装 Node.js 环境；混淆代码里通常带有「检测自己是不是在真浏览器里」的逻辑，需要"补环境"（伪造 `document`、`window`、`navigator` 等对象）骗过它，这部分维护量不小。

### 3.4 驱动页面 + 拦截响应（路线 C）

**既不自己算签名，也不跑别人的 JS。**

做法：开一个真实浏览器打开小红书/抖音的页面，然后

- 要么驱动它点击、滚动（像人一样操作）；
- 要么干脆"看着"它——浏览器自己会去请求数据，我们**只监听它收到的回复**，把回复里的数据抄下来。

本质是**借浏览器的手办事**：签名、Cookie、设备指纹全部由浏览器自己搞定，产品一行都不用管。

- 好处：几乎不用维护——平台改签名算法完全不影响。
- 坏处：要跑一个浏览器进程，重、慢；平台改**页面结构**时，"点哪里"要跟着改。

### 3.5 挂本机已开的浏览器（路线 D）

通过 Chrome 调试端口（CDP）连接用户**已经打开着**的 Chrome，直接复用其中现成的登录态。

- 好处：连登录流程都不用做。
- 坏处：**只有本地能跑**。云端没有"用户的本机"，服务器够不到用户的 Chrome（见第五节）。

## 四、建设顺序（冻结）

用户列的是 1 → 2 → 3，但**技术上必须 3 → 2 → 1**：

```text
目标 3（授权面板 → 拿到会话）
→ 目标 2（用会话读本人收藏，扫描并勾选）
→ 目标 1（用会话读单条链接）
```

理由：目标 2 与目标 1 都需要会话作为输入，会话只能由目标 3 产出。

## 五、部署形态（冻结）

| 形态 | 会话底座 | 路线 D（挂本机浏览器） | 架构改动 | 合规风险 |
|---|---|---|---|---|
| 本地单用户（当前形态） | 能跑 | 可用 | 无 | 低 |
| 每用户自部署 | 能跑 | 可用 | 无 | 低 |
| 共享多租户云 | 能跑 | **失效** | **重做** | **高** |

**核心判据**：会话底座不排斥云端，它排斥的是**"多个不相干的人共用一个后端"**。

共享多租户云下会坏的具体环节：

| 环节 | 后果 |
|---|---|
| 路线 D | 直接失效，必须切回路线 C |
| 会话存储 | 需按用户隔离 + 加密；现状 `user_id` 默认值为字面量 `"local"`（`app/db/models.py:90`），是占位符而非账号体系 |
| 出口 IP | 多用户共用服务器 IP，易被判定为爬虫农场，需独立代理（有成本） |
| 资源 | 每个浏览器上下文数百 MB 内存量级（估算），单台普通服务器只能支撑个位数并发 |
| 扫码登录 | 反而最顺，复用 B站 现有 `generate → poll` 形状 |
| 合规 | **分界线**：本地单用户 = 个人研究；多租户 SaaS = 对外提供批量数据获取服务 |

**项目自身文档的既有结论**（`product/docs/基线/路线/产品的长期计划.md`）：

- 第 259 行：「平台是否允许批量读取、长期保存和**商业化处理**」——列为「其他问题」第 1 条，**至今无结论**。
- 第 246 行：云端只是「桌面产品关闭后无法持续同步」的候选方案之一，**不是产品形态**。
- 第 255 行：「Cookie、OAuth Token 等凭证必须加密保存，不能进入模型提示、日志或导出文件」——**加密保存这一半已满足**：B站 Cookie 先经 Windows DPAPI 加密（`app/platforms/secrets.py`，落库值为 `dpapi:` 前缀），再写入 SQLite；接口响应不回传明文。「不得进入导出文件」这一半未单独核验。
  - 【2026-09-20 更正】本节与第 279 行此前记为「B站 Cookie 直接落库」，经读码核实为**错误说法**，已改。
- 五阶段规划（识别 → 统一存储 → B站自动同步 → 多平台同步 → 跨平台整理）中**没有云端或多用户阶段**。

**结论**：分发应走**每用户自部署**，不走共享多租户云。

## 七、补充候选路线（本轮新调研，尚未冻结）

在 A/B/C/D 之外，另有四条可行路线。**其中 E 与当前产品形态（本地桌面单用户）匹配度最高。**

### E. 浏览器扩展（用户侧采集）

把采集逻辑做成一个 Chrome 扩展，**在用户自己已经登录的页面上运行**。

已验证的开源实现（可直接参考其结构）：

- `PCPrincipal67/xhs-favorites-exporter`：读首屏 `__INITIAL_STATE__` SSR 数据 → monkey-patch `XMLHttpRequest` 拦截 `/api/sns/web/v2/note/collect/page` → 扫描 DOM 卡片 → 自动滚动 → 三源去重合并 → 导出 JSON。
- `JayHome137/xhs-dy-favorites-exporter`：一个扩展同时支持小红书与抖音，按站点自动加载对应采集逻辑；抖音侧扫描网页版收藏页已渲染的视频卡片并自动滚动。
- `zhulin025/xiaohongshu-exporter`：具备断点续传、增量导出、指定范围采集。

**两层脚本架构（关键设计）**：

```text
page-bridge.js（页面上下文）
  可访问页面自身的会话；可 monkey-patch XHR
  ↓ postMessage
content-script.js（扩展上下文）
  可访问 chrome.* API；负责滚动、去重、导出
```

**为什么这条路线重要**：

| 维度 | 表现 |
|---|---|
| 新增产品依赖 | **无**（不需要 Playwright / Chromium） |
| 签名逆向 | **不需要**——签名由页面自身 JS 生成 |
| 服务器登录态 | **不需要**——用用户自己浏览器的现成登录态 |
| 风控 | 最轻，是真人浏览器环境 |
| 代价 | 需要用户手动操作（打开收藏页 → 点采集），不能全自动 |

**与本产品的对接方式**：产品本地 API 常驻 `127.0.0.1:8765`，扩展采集后可 POST 到该地址直接建任务，形成「在收藏页点一下 → 自动进产品」的闭环。

**已实测的风控细节（重要）**：扩展导出的链接若直接从外部点开会触发风控要求扫码；先访问任意一次该平台页面即可正常打开。平台的校验对象不是单条链接，而是「当前标签页有没有跑过初始化流程」。

### F. 第三方商业 API

以 TikHub 为代表：单一 API Key 覆盖 16+ 平台，1000+ 端点，按次计费（约 $0.001–0.01/次，阶梯折扣最高 50%），免费额度约 50 次，另提供 MCP 与 Chrome 扩展。

- 已确认存在用户收藏端点：`/api/v1/xiaohongshu/app_v2/get_user_faved_notes`（小红书，游标分页）。
- 另有 Apify 等同类服务（如 `rednote-xiaohongshu-favorites-scraper`，读取公开收藏，无收藏时返回空）。
- 优点：稳定、零维护、无需处理签名与登录。
- 缺点：**按次付费**、依赖外部服务、用户收藏属私密数据，**是否可交给第三方存在隐私与合规问题**（待裁决）。

### G. RSSHub（自部署聚合服务）

`/xiaohongshu/user/:user_id/collect` 路由已存在，可订阅用户收藏。

- 需要配置 `XIAOHONGSHU_COOKIE` 环境变量。
- 需要额外部署 `browserless/chromium` 才能渲染 JS 页面。
- 本质仍是爬取，反爬严格，维护成本不低；适合"订阅新内容"而非"全量扫描历史收藏"。

### H. 官方开放平台 API

- 小红书：有开放平台，但需资质审核，且仅用于自有内容/授权场景。
- 抖音：开放平台主要面向自有账号内容管理，需企业资质。
- 知乎：无面向个人的内容读取开放平台。
- 微信公众号：自有公众号可用 AppID/AppSecret 走官方接口；单篇文章直接抓 HTML 即可，**无需登录**。

**结论**：官方路线对"读取用户自己收藏"这件事基本不适用，**H 路线对本需求无效**。

## 八、目标 2「如何拿到收藏」的具体做法（本轮新调研）

### 8.1 前置事实

**小红书收藏默认私密，仅本人登录后可见**（公开专辑为例外）。因此目标 2 必然等于**扫描我自己的收藏**，不是扫描他人收藏。合规压力因此低于"读公开内容之外的数据"。

### 8.2 三条可行路径

| 路径 | 做法 | 依赖 | 自动化程度 |
|---|---|---|---|
| **E** | 浏览器扩展在收藏页运行，读取 SSR + 拦截分页 XHR + 扫 DOM | 无新增依赖 | 半自动（用户点一次） |
| **C** | 受控浏览器打开收藏页，驱动滚动并拦截 XHR | Playwright | 全自动 |
| **D** | 挂用户本机已开的 Chrome，在收藏页执行同上 | CDP | 全自动（仅本地） |

**当前推荐：先用 E 打通闭环**。理由：零新增依赖、零签名维护、即刻可验证数据是否拿得到；验证通过后再评估是否需要 C/D 提供的全自动化。

### 8.3 各平台收藏接口（已实测）

| 平台 | 接口 | 备注 |
|---|---|---|
| 抖音 | `GET /aweme/v1/web/collects/list/`<br>`GET /aweme/v1/web/collects/video/list/?collects_id=&cursor=&count=`<br>`POST /aweme/v1/web/aweme/listcollection/` | 2026-08 实测；实现方式为驱动页面点击「收藏 → 收藏夹」并拦截 XHR |
| 小红书 | `/api/sns/web/v2/note/collect/page` | 实测 250 条 / 90 秒 |
| 知乎 | `/api/v4/people/{user}/collections` → `/api/v4/collections/{cid}/items` | 仅需 `z_c0` Cookie |
| B站 | 已有实现 | 作为参考 |

## 九、高风险选项（知情列举，未推荐）

用户表示「可以考虑要不高风险的东西」。以下为技术上存在、但代价显著的路线，**仅作知情列举**：

| 选项 | 做法 | 主要代价 |
|---|---|---|
| 账号池 / 养号 | 准备多个平台账号轮换使用 | 账号封禁；平台用户协议明确禁止；一个身份被封会牵连同批账号 |
| 住宅代理池 | 按请求轮换出口 IP 以规避风控 | 持续付费；本地单用户场景下成本收益比极差 |
| 打码/验证码识别服务 | 自动通过验证码挑战 | 付费；部分平台风控已升级到设备指纹级，打码无效 |
| 云手机 / 真机农场 | 在真实移动设备上跑采集 | 成本最高；对本地单用户产品完全不适用 |
| 移动端 App 接口逆向 | 抓包 App 流量并逆向其签名 | 工作量最大；App 签名通常比 Web 更严；升级即可失效 |

**共同判断**：这些选项的服务对象都是"规模化多账号采集"。**本产品是本地单用户工具，读取的是使用者本人的收藏**，用不到这一档手段；引入它们会同时抬高成本、封号风险和合规风险，且收益有限。

**不建议采用。** 若后续确有多账号需求，需单独评估并明确知情同意。

## 十、成本与风险汇总

| 项 | 内容 |
|---|---|
| 新增依赖 | 路线 C/D 需 Playwright + Chromium，约 150–250MB；路线 E 无需新增依赖 |
| 会话保鲜 | 小红书约 1 年 / 抖音约 10 天 / B站 约 3 天 / 公众号 token 2 小时。需要「过期检测 + 引导重新授权」 |
